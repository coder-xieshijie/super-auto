## 二、助手答复

消息标识：A1。回应：U1。性质：基于此前研究的分析与建议。

**基本对。这是目前证据最一致的短板。** 但更准确地说，你缺的不是“多写一些测试”，而是：

> **需求确认后，稳定地形成“怎样算做对、如何证明做对”的验收标准。**

而且，**验收标准在实现前确定，验证在开发过程中持续执行，交付时核对最终版本。**

### 还需要补充三点

#### 1. 先明确“验证什么”，再选择单测或 E2E

例如“支持更新 Goal”还不够具体，需要明确：

- 空闲时更新，应发生什么？
- 后台任务执行期间更新，应发生什么？
- 后台结束后，应该继续哪个目标？
- 用户界面、持久状态和实际执行是否一致？

这些是**行为要求**。单测、集成测试和 E2E 是证明这些要求的手段。

#### 2. 单测与 E2E 之间，还有集成和契约验证

| 层次 | 主要证明什么 | 你的典型例子 |
|---|---|---|
| 单测 | 局部规则、状态变化、边界条件 | Goal 状态转换、计数规则 |
| 集成／契约测试 | 模块接线、参数传递、接口一致性 | effort 是否进入首轮请求，IDL 与调用方是否对齐 |
| 真实运行验收 | 正常启动和实际入口下，完整行为是否成立 | 默认装配启用、后台结束后 Goal 自动续跑 |

不必每个需求都铺满三层。应针对风险选择最少但充分的验证，避免所有问题都拖到昂贵的 E2E 才发现。

#### 3. 验证必须有独立依据，并对应实际交付版本

需要避免两个问题：

- 实现者根据自己写出的代码，再写一套“刚好能通过”的测试。
- 验证过旧版本，修改或整合后仍沿用原来的 PASS。

因此，验收应对照原始需求，并注明 **代码版本、环境、实际动作和结果**。没有跑到的场景明确标为未验证；独立 reviewer 也不能替代实际运行。

### 你需要亲自给出全部验证细节吗？

**不需要。**

你主要负责确定产品语义、体验取舍和不可妥协的边界。Agent 应根据需求和仓库，补出具体场景、测试层次、运行命令和证据方式；只有无法从现有资料判断的业务问题，才回来找你。

可以把每项需求最小化为四个问题：

1. 用户最终能完成什么？
2. 哪些边界或失败情况必须处理？
3. Agent 如何实际操作并观察结果？
4. 拿到什么证据才能宣布完成？

**另外两个问题也不能丢：下游拿到正确的上游代码与已定决策，以及验证失败后由 owner 自动接续修复。** 否则，即使验收标准完整，你仍会承担传上下文和催推进的工作。

所以优先顺序可以概括为：**验收定义前置 → 真实验证跑通 → 修复闭环接通 → 再扩大并发。**
