## 助手答复（全文）

### 先解释几个词

- **spec**：需求澄清结束后写下的“最终决定清单”，说明这次要做成什么样、有哪些限制。在你的流程里，它一写完需求就冻结，之后所有检查都以它为准。
- **verify.md**：验收文档。写明怎样判断一个实现满足了 spec：做什么操作、应该看到什么、不能出现什么、留下什么证据。
- **plan.md**：实施计划，写明按什么顺序改哪些代码。
- **Skill**：一份写给 AI 的操作说明书。你输入 `/core-verify`，AI 就按里面的步骤工作。
- **场景**：一次具体的检查。例如“剩余额度为 1 时发起任务，第一次请求的结果要被处理，第二次请求不能发出”。
- **基线**：这次改动之前的代码。
- **错误实现**：一个看起来说得通、但违反 spec 的写法。用来检查场景能不能把它拦住。
- **真实入口**：用户实际使用的地方，例如界面按钮、命令行命令、对外接口。与之相对的是代码内部的函数。
- **控制命令和功能地图**：项目里长期维护的两样东西。控制命令让 AI 能启动应用、点按钮、读结果；功能地图记录每个功能从哪里进入、怎么操作、看到什么算成功。这是 Lauren 的做法。
- **cross review**：新开的 AI 会话，只拿 spec 做标准，检查并修改 verify.md 和 plan.md。

### 一、它要解决什么问题

过去有几次，代码交付后你自己用的时候才发现问题：

- 设置页显示了新值，实际发出的请求还在用旧值；
- 每个模块都说自己做完了，正常启动时新功能却没有接上；
- 后台任务结束后，本应自动继续的流程没有继续；
- 文字层面的测试通过了，真实终端里的操作没人验过。

这几次的共同点：局部测试都通过了，但没人从用户实际使用的入口把完整流程跑一遍；而且“怎样算做对”是在代码写完之后才补的，容易跟着实现的思路走，实现漏掉的东西验收也跟着漏掉。

core-verify 的作用：在写计划和代码之前，只根据 spec，把“怎样算做对、怎样证明”写成 verify.md。

### 二、它在流程里的位置

```text
① grill-with-docs 会话（你参与）
     多轮问答，定下决策点
     → /core-spec    写出 spec.md（需求冻结）
     → /core-verify  写出 verify.md          ← 本 Skill
     → 写出 plan.md（依据 spec 和 verify）
② cross review（新开会话）
     只以 spec 为标准，检查并修改 verify.md 和 plan.md，之后两份冻结
③ 实现 → 按 verify.md 验收 → 交付（流程还没定）
```

它只能手动调用，在写完 spec 后、写 plan 前，在同一个会话里输入 `/core-verify`。

### 三、输入和输出

| 项目 | 内容 |
|---|---|
| 必需输入 | spec.md |
| 辅助输入 | 当前会话、ADR、术语表：只用来理解 spec 里的词、找例子，不能从这里加新要求 |
| 辅助输入 | 当前代码：用来找入口、现有测试和观察手段 |
| 输出 | 一个 verify.md，默认和 spec.md 放在同一目录 |
| 不产出 | 测试代码、执行结果 |

### 四、它的五个步骤

**第 1 步：只以 spec 为依据，找出所有要验证的内容**

- 没有 spec 时，先按 core-spec 的规则生成 spec。
- 记下 spec 的路径、内容哈希、代码仓库当前提交，之后能核对验收对应的是哪一版 spec。
- 把 spec 里所有规定性的句子逐条列出来：选定的行为、默认值、条件和例外、不能发生的事、必须保持不变的旧行为、接受的代价。只解释原因的句子不列。
- 对每个涉及的功能，逐个过它的入口（按钮、快捷键、命令行、接口）和状态（默认、加载中、空、出错、禁用、取消、重复触发、并发、重启后），找 spec 没说清的地方。没说清、而且会影响“对还是错”的判断，就按 core-spec 的规则更新 spec；core-spec 在决定还没定时会向你提一个最小的问题。你回答后先改 spec，再写验收。
- 完成标志：spec 里每条规定都有对应的去处；每个相关的入口和状态都已处理。

**第 2 步：把每条规定写成能判断对错的“要求”**

- 每条要求有编号（R01、R02……），写成能观察到的结果，并注明来自 spec 的哪里。
- 一条规定里有几个条件或例外，就拆成几条要求，每个例外都能单独判断。
- 每条要求选一种证明方式：

| 证明方式 | 用在哪 |
|---|---|
| 场景 | 行为、状态、输出、副作用 |
| 评审或静态检查 | 结构上的约束，例如“复用某个已有能力”“不新增依赖”，写明查什么、怎样算不通过 |
| 已有检查 | 仓库里现成的测试、类型检查已经能证明的部分，写明文件或命令 |

**第 3 步：给行为类要求写场景**

每个场景写这些字段：

```text
S02 额度用尽时的边界　覆盖：R05、R06　层次：真实入口　必需
入口：界面发起任务；命令行发起任务
前提：用测试数据把剩余额度设为 1
操作：从两个入口分别发起任务，第一次请求获准并返回结果
必须观察到：这个结果出现在执行记录里；实际发出的请求数是 1
不得出现：第二次普通请求被发出
基线预期：失败（旧代码在额度归零时立即停止，结果没有进入执行记录）
错误实现：拿到结果后才检查额度（这时第二次请求已经发出）
观察方式与证据：执行记录、出站请求记录
执行状态：实现后再补具体命令
```

写场景时遵守这些规则：

| 规则 | 具体要求 | 防止的问题 |
|---|---|---|
| 选层次 | 局部计算用单元测试；模块之间的连接和默认启动用集成检查；用户能看到的流程、跨模块的路径用真实入口 | 所有东西都堆到昂贵的端到端测试，或者只有单元测试 |
| 按改动类型选证明形式 | 命令行改动就运行真实命令；界面改动就在运行中的应用里操作一遍；存储改动写入后从另一个地方读回来；迁移用保存下来的真实输入重放；平台支持在目标平台上运行；性能要求先测旧代码再测新代码，并写明超过多少算失败 | 用同一种测试对付所有改动 |
| 走真实用户路径 | 前提可以用测试数据、配置准备；要验证的结果必须由真实入口上的操作产生 | 调用内部函数“造”出结果，真实入口其实没接上 |
| 看实际结果 | 看实际发出的参数、保存后的数据、默认启动时的状态、最终副作用；界面显示和“函数被调用”只算辅助证据 | 界面显示对了，实际请求是错的 |
| 断言要能失败 | 预期值写 spec 里的具体数字或文字，不用被测代码算出来的值；每条“不得出现”配一条“必须观察到”；检查一下：如果实现什么都不做，这个场景会不会也通过 | 场景什么都没测到，空实现也能通过 |
| 用基线对照 | 新增或改变的行为，在旧代码上应该失败；必须保持的行为，新旧代码上都应通过 | “错误实现”只停在想象中，无法实际运行 |
| 写错误实现 | 旧代码覆盖不到的关键风险，再写一个看似合理但违反要求的写法，确认场景会让它失败 | 断言太宽松 |
| 覆盖每个入口 | 同一行为有多个入口时，每个入口都要有场景，或写明不需要的理由 | 只从命令行验过，就当界面也没问题 |
| 只约束 spec 规定的东西 | spec 没规定的内部结构、函数名不写进断言 | 断言写得太死，正确的其他写法也被判失败 |
| mock 的范围 | 模拟对象只放在生产环境里本来就和外部系统隔开的地方；spec 要求真实服务、真实设备、目标平台时，在真实环境上运行 | 模拟通过被当成真实通过 |
| 无法用代码判断的结果 | 模型输出质量、视觉效果等，写明固定样本、参照和评判标准，注明需要单独判断 | 用“看起来还行”代替标准 |

完成标志：每条行为类要求至少有一个必需场景；每个必需场景都有具体的预期值、基线预期和错误实现；每个相关入口都处理了。

**第 4 步：找验证能力，列出工具缺口**

- 先找项目已有的验证能力：验证 Skill、控制命令、功能地图、端到端测试工具、现有测试、日志和数据查询。
- 项目有功能地图时，场景的“入口”直接引用地图里的条目，不在 verify.md 里重写操作步骤。
- 引用的入口必须在当前代码里真的存在；能低成本试跑的，试跑一次。
- 这次才会做的新功能，先写入口类型和观察方式，具体命令等代码写完后再补。
- 现在操作不了或看不到的，写进“验证工具缺口”：缺什么、哪些场景要用。补缺口时补成项目里能长期复用的能力（例如给控制命令加一个读取实际请求的功能），不写只用一次的脚本。plan 会把这些排在功能开发之前。

**第 5 步：写成文档，对照 spec 检查**

verify.md 的结构：

1. 用途与效力，加上来源：spec 路径和哈希、代码仓库和提交、引用的验证能力；
2. 重点：要求数、必需场景数，3–5 个最容易出错的场景；
3. 要求表；
4. 场景；
5. 回归范围：这次改动会碰到、但 spec 没要求改变的旧行为，这些场景在新旧代码上都应通过；
6. 验证工具缺口；
7. 完成条件：全部必需场景在交付的那一版代码上通过，证据对应那一版；工具缺失时如实标为受阻，不能用更低层次的检查代替。

交付前检查四件事：

- spec 里每条规定都有要求和证明方式，默认值、例外、不能发生的事都没丢，每个入口都有着落；
- verify.md 里没有 spec 以外的要求或标准；
- 每个必需场景的基线预期正确，错误实现会失败，空实现不会通过；
- 还没找到的入口、还没确定的命令都如实标注。

### 五、它不做什么

| 不做的事 | 原因 |
|---|---|
| 写测试代码、运行测试 | 这时还没写实现代码；测试在实现阶段写，验收在实现后跑 |
| 定义通过、失败、受阻这些执行结果 | 属于实现后的验收步骤 |
| 写每个场景的环境、数据清理、超时 | 功能还没实现，大多只能到验收时才确定 |
| 单独再开一个会话检查 verify.md | 你已定由 cross review 按 spec 检查 |
| 加 spec 以外的性能、权限、并发标准 | 只有 spec 规定了才写 |

### 六、和上下游怎么配合

| 环节 | 和 verify.md 的关系 | 目前状态 |
|---|---|---|
| core-spec | 提供唯一依据；spec 有缺口时按它的规则更新 | 已有 |
| plan.md | 按场景编号引用 verify.md，把工具缺口排在功能开发之前，尽早跑通第一条真实入口场景 | plan-for-agents 还没有写明要引用 verify；需要决定改 Skill 还是在调用时说明 |

## 后续：验证力度与拆分规则的依据

用户原话：

> 我现在有问题：
> 1. 具体的 verify 的力度是怎么评估和拆分的？
> 2. 具体的参考和拆分规则是根据什么制定的？有具体的依据吗？

### 助手答复要点（分析，未经确认）

**现状。** 当前 Skill 的拆分有三层：spec 规定 → 要求（按条件和例外拆）；要求 → 证明方式（场景、评审或静态检查、已有检查）；要求 → 场景（至少一个必需场景，多入口逐个覆盖，关键例外单独成场景）。力度（验到哪一层、验多少个）只有一句“按风险选最少且足够的层次”和一张按改动类型选证明形式的表。“风险”没有定义，必需与可选没有判定规则，场景数量没有上下限，验收文档也不记录为什么选这一层。结果是力度主要取决于模型当次判断，cross review 也无从核对。这是当前 Skill 的缺口。

**依据分三档。**

| 规则 | 依据类型 | 具体出处 |
|---|---|---|
| 用基线对照：新行为在改动前应失败 | 原文直接规定 | pstack `tdd`：修复前确认测试因预期原因失败；`multi-phase-plan`、`autopilot-full` 的回归对照 |
| 断言要能失败：字面预期、正向配对、空实现检验 | 原文直接规定 | pstack `principle-test-behavior-not-implementation`：导入函数全部返回 undefined 仍通过的测试要改写或删除，列出五种形态 |
| 覆盖每个入口 | 原文直接规定 | pstack 功能地图示例：跳过的入口不能借另一入口宣称已验；`create-verification-skill`：只驱动一个方便入口的证明不完整 |
| 走真实用户路径、观察动作与结果、写入后读回、mock 只在已隔离的边界 | 原文直接规定 | pstack `create-verification-skill` 的 Evidence 证明标准；功能地图示例 |
| 按改动类型选证明形式 | 原文直接规定 | pstack `docs/guide/06-verify-and-ship.md`“Match the check to the change” |

### 三家怎样划分验收单位（原文）

| 来源 | 验收单位与例子 | 谁验、怎么验 | 何时定、能否改 |
|---|---|---|---|

共同点：验收单位是用户能观察到的一次完整操作及其结果，而不是函数或实现步骤；由 agent 自己驱动真实应用来证明；验收项在写代码前列全，实现方不能改；内部行为通过日志、指标、数据读回变成可观察的，而不是降到单测；结构性要求用机械检查。

### 助手建议的拆分规则（未写入 Skill）

1. 验收项是用户可观察的一次完整操作及结果，写成“用户在某入口做某事，看到或产生某结果”，带操作步骤和若干检查点。默认从真实入口驱动，由实现 agent 自己运行。
2. 拆：结果不同就拆开。spec 的每条规定、每个例外、每个入口、会导致不同结果的状态，各成一项。合：入口、前提、操作流程相同的，合成一项，检查点并列。
3. 从入口观察不到的内部规则（如计数、参数），先补可观察性（日志、指标、链路追踪、只读查询），列为工具缺口，让验收项仍保持端到端；外部依赖的失败用生产边界上的替身触发。
4. 结构性要求用 lint 或结构测试，每个约束一条机械规则，不写成场景。
5. 单元测试属于实现，不写进 verify。
6. 列 2–5 条核心用户旅程作为冒烟集，每个实现会话开始先跑一遍。
7. 工具看不到的部分单独列为覆盖盲区，不能标为已验证。

这取代上一轮提出的 V0–V3 分级中“V1 单元”一层：三家都把验收放在端到端层，Anthropic 明确指出单测和 curl 查不出端到端问题。

### 过细与覆盖不全：两种都会发生

覆盖不全（原文证据）：评估者“倾向浅测、不探边界”，“更深层功能的 bug 没被触及”；生成者会留“只能显示、不能交互”的空壳功能，由 QA 才查出；工具盲区（Puppeteer 看不到浏览器原生弹窗）处的功能 bug 更多；agent 会在未做端到端测试时标记完成；只验一个方便入口不完整。

过细或过重（原文证据）：完整 harness 比单 agent 贵 20 倍以上（$200/6h 对 $9/20min），作者随后逐个拆除组件，模型变强后取消 sprint；“每个组件都编码了一个关于模型做不到什么的假设”；pstack orchestrate：“只是重跑一条命令的验证者是仪式，不是验证”；OpenAI：指导过多会变成无指导。

注意：Anthropic 的 200 多项并未被原文视为过细，它按用户功能拆，目的是防止 agent 过早宣布完成。原文里的“过重”指流程组件和轮次，不是验收项的数量。

控制办法：

- 防覆盖不全：从 spec 一次列全并双向对照；入口和状态逐一过；冻结后实现方只改状态；只有实际运行才能标通过；工具盲区单列；检查点要能识别空壳（断言交互效果，不只断言显示）；需要独立评估时用已知漏检案例校准评估者；交付后发现的漏检写回 verify 模板或功能地图。
- 防过细：按用户可观察结果拆，不按实现步骤拆；同一流程合并检查点；单测、结构约束分别交给实现和 lint；独立评估按任务是否超出模型能可靠独立完成的范围决定；记录验收项数量和运行耗时，每次只增删一个组件。

没有依据的部分：三家都没有给出验收项的合适数量或粒度上限；200 多项、27 条都是单个例子。
