# 需求来了怎么走：完整版与按档位分流

前提：verify-archon（含涉及功能的地图）、core-spec、core-verify、deliver 都已就绪。其中后三者已在 dev-skills main `97c230f` 合入（dev-skills#12）。来源编号见 [design.md](design.md)。

## 一、完整版：一个需求从开始到 MR

| 步 | 你做什么 | agent 做什么 | 产出 |
|---|---|---|---|
| 1 | 在 Archon 的 worktree 里开一个定义 session，运行 `/grill-with-docs`，描述需求，逐轮回答 | 逐个问会影响结果的决定，事实自己去查 | 会话里的决定 |
| 2 | 运行 `/core-verify`，给出需求目录，例如 `.harness/docs/spec/<需求>/` | 没有 spec 时先按 core-spec 写 spec（含目的、非目标、硬约束、交付与授权）；对照功能地图，按入口和状态查缺口；写 verify | spec.md、verify.md |
| 3 | 回答查漏转来的问题 | 用另一家模型开新 session 查漏，最多两轮；问题转成给你的问题 | 更新后的两份文件 |
| 4 | 确认一次 | 记录两份文件的 sha256，此后冻结 | 冻结的 spec、verify |
| 5 | 开一个新 session，运行 `/deliver`，给出两份文件的路径，之后离开 | owner 写 plan.md；逐个里程碑实现，并在应用里跑涉及的场景；全部场景自验；另一家模型独立验证；开 MR；处理 CI 和评审，直到可合入；按授权合入或停在可合入；更新功能地图和专题文档 | 分支、MR、plan.md、evidence/、验证报告 |
| 6 | 看汇报和 MR | 只在三种情况下中途找你：spec 矛盾或缺少会改变判定的决定、缺权限或环境、授权以外的不可逆操作 | — |

你参与的只有两处：第 1–4 步的定义，第 6 步看结果。

## 二、三家怎样应对不同规模

| | 小改动 | 中等 | 大型或人要离开 |
|---|---|---|---|
| OpenAI | 小改动用临时的轻量计划（S1："Ephemeral lightweight plans are used for small changes"）；合入门禁少，PR 存活时间短（S1） | — | 复杂功能和大重构写 ExecPlan（S1、S6："When writing complex features or significant refactors"）；长任务用 `/goal`、连续运行（S2、S3） |
| Anthropic | 范围清楚、改动小（改错字、加日志、改名）直接让它做；"如果一句话能说清改动，就跳过计划"（S7） | 方案不确定、改多个文件、代码不熟时，先探索和计划再写（S7） | 先访谈、写 SPEC.md，再开新 session 执行（S7）；独立评判"只在任务超出当前模型单独可靠完成的范围时值得"（S5）；先用单 agent（S8） |
| Lauren | 普通对话不启用流程；拿不准的小改动用 `blast-radius` 证明它不会弄坏别处 | 按类型选 playbook：bug fix 先在真实界面复现、找根因、做最小修改、在同一界面复验，失败的复现记录放在修复之前；feature 有自己的步骤 | 大型、跨模块，或"人走开之后再来看"的工作，转 `figure-it-out`，"按任务决定严格程度：不可逆、影响面大的步骤更严，可回退、风险低的更松"；多天、多 PR 的项目转 `orchestrate` / `autopilot` |

共同点：
1. **文档和检查的多少，由规模和风险决定**，不是一套流程套所有任务。
2. **有一条不随规模变**：在真实运行的产品上证明改动有效。Lauren 的 bug fix 要求在同一界面复验，只跑单测不算；Anthropic 要求给 agent 能自己验证结果的办法；OpenAI 由 agent 驱动应用验证。
3. **越需要人离开，越需要预先写好的完成标准和独立评判**。

## 三、建议的三档

### 怎样选档

| 看什么 | 直接改（L0） | 快速版（L1） | 完整版（L2） |
|---|---|---|---|
| 一句话能否说清改动 | 能 | 大体能 | 不能 |
| 正确行为是否已经定下 | 已定，没有歧义 | 已定：现有 spec（如 Goal 的 GOAL 编号）或功能地图已有规定，或者只差 1–2 个小决定 | 有多个待定的决定 |
| 涉及范围 | 一处 | 一个功能 | 多个功能或跨模块 |
| 出错的代价 | 低，可回退 | 中 | 高 |
| 你是否要离开等结果 | 否 | 短时离开 | 是 |

**风险优先。** 改动再小，只要涉及数据、权限、并发、持久化或 runtime 契约，就至少走 L1，并加独立验证。Archon AGENTS.md §4 也把这些列为需要充分证据的高风险类别；Lauren 的规则是不可逆、影响面大的更严。

**档位可以升，不能靠降档省事。**
- L0 做着发现改变了用户可见行为 → 升 L1；
- L1 发现要改变已约定的行为、涉及多个功能，或根因是设计问题 → 停下，升 L2，从定义开始。

### 各档怎么走

| | L0 直接改 | L1 快速版 | L2 完整版 |
|---|---|---|---|
| 典型 | 文案、翻译、日志、配置值、改名 | 行为已有规定的 bug；只差一两个小决定的小功能 | 新功能、行为变更、重构、跨模块 |
| session | 1 个 | 1 个 | 定义 1 个 + owner 1 个，另有查漏和独立验证各一个新上下文 |
| 文档 | 无，MR 描述即可 | 不写 spec 和 verify；以现有 spec 或地图为依据；复现步骤和前后证据写在 MR 里 | spec、verify、plan |
| 你的决定 | 开口说一句 | 说明问题；期望行为不清时回答 1–2 个问题 | 定义阶段回答问题，确认一次 |
| 验证 | 相关的检查；影响用户可见行为时，用 verify-archon 实际看一次 | 先用 verify-archon 在真实界面复现，拿到失败证据；修改后在同一入口复验；按地图把这个功能的其他入口也跑一遍 | verify 全部场景，逐个里程碑跑 |
| 独立验证 | 不需要，靠 CI 和常规评审 | 按风险：高风险时由另一家模型复验 | 必须，另一家模型 |
| 地图和专题文档 | 一般不动 | 修复的触发路径写进地图的"坑"或子功能状态 | owner 在 MR 里同步更新 |

用 Archon 的 Goal 提交标题示意（按标题推测，实际档位看当时有几个待定决定、风险多大）：
- L0：如"修复 Goal 空目标提示未随语言切换"；
- L1：如"修复 Goal 延迟等待后无法继续执行"，期望行为已在 GOAL-05 中规定；
- L2：如"Goal 注释纳入目标、编辑后续跑与更新通知"，以及 goal-v2 的服务、存储、装配改造。

多个需求并行、多天、多 PR 的项目，是 L2 之上的规模。三家都在会话外加一层很薄的看管：OpenAI 用 Symphony，Lauren 用 orchestrate / autopilot 的 root。对应到你的环境，就是之前讨论的 Agent Lord 薄 root，由试跑记录决定要不要。

### 需要补的东西

| 档 | 用什么 | 状态 |
|---|---|---|
| L0 | 不需要专门的 Skill；Archon AGENTS.md 已规定 MR、只跑相关测试 | 已有 |
| L1 | 需要一个小 Skill（暂名 `fix`），参照 Lauren 的 bug fix playbook：用 verify-archon 在真实入口复现、找根因、最小修改、同一入口复验、按地图跑这个功能的其他入口、失败复现记录放在修复之前、MR 附前后证据；期望行为不清时问你，复现不了就写明试过什么再停下；按风险决定是否请另一家模型复验 | 没有，依赖 verify-archon |
| L2 | grill-with-docs、core-spec、core-verify、deliver、verify-archon | 前四个已有，verify-archon 待建 |

不建议给 deliver 加一个"快速模式"。deliver 的完成条件依赖冻结的 spec、verify、plan 和独立验证报告；加模式会让一个 Skill 同时承担两种任务，也与 agent-prompt-rules 的写法不符。
