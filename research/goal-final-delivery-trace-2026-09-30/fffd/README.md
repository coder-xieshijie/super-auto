# 坏字符能否就地补回

2026-09-30。用户说明坏字符来自本机所用的接口，不具通用性，E1 改为只在本机用钩子解决；并问钩子是拦下让模型重写，还是能直接还原，有没有办法不让 agent 重写。

## 坏字符是什么

- U+FFFD 是解码器遇到无法解码的字节时放的占位符，原来的字节已经丢了。会话记录里，assistant 的工具调用输入存的就是它，说明 Claude Code 收到时字节已经丢了，本机没有能还原的原始字节。
- 一处丢字表现为连续 2 个或 3 个 U+FFFD，对应恰好一个字：UTF-8 三字节的汉字或全角标点被拆开解码。单个 U+FFFD 在记录里几乎都是命令里有意写的搜索模式，不算丢字。
- 所以严格意义上的还原做不到；但每处丢字都是“补一个字”的定长填空。

## 按上下文猜

`guess_test.py`：从会话全文能确定答案的 214 处里随机取 60 处（结果见 [guess-results-2026-09-30.json](guess-results-2026-09-30.json)），给模型前后各 40 个字，让它回该字的 Unicode 码点（纯 ASCII，回程不会再丢字）。

| 模型 | 猜中 | 一次批量用时 |
|---|---|---|
| `claude-opus-5` | 47/60（78%） | 144 秒 |
| `qw-mid-5` | 45/60（75%） | 298 秒 |

猜错的多是同义替换：“；”猜成“、”，“效果”猜成“结果”，“清除”猜成“删除”，“自己开”猜成“自行开”。少数改了意思：“正文”猜成“本文”，“第四种停下”猜成“第四种况下”。样本里有同一段文字在不同会话里重复出现的情况，错例有重复。

## 结论

- 让 agent 重写也是在猜：它看到的同样是 U+FFFD，只是看到的上下文更多。拦下重写要多一轮；写大文件时要整份重新生成，重写时还可能再丢字。
- 可以就地补：工具执行前先查原文，查不到再让模型猜，把补好的内容换进工具输入再执行，并告诉 agent 补了哪几处、哪几处是猜的。补不出来（调用失败、超时）才拦下让 agent 自己改。
- 直接回复用户的文字不经过工具，钩子改不了。
