# Agent Lord 新增需求验收环节：设计建议

日期：2026-09-28。目标：Agent 完成代码后，能够自己执行与需求对应的验证、修复并重验，减少人工逐项验收。本文是待实现设计，不表示已经接入 Agent Lord，也不表示示例已能运行。

## 结论

新增一个“需求验收”环节，交付一套**验收定义、可执行检查、实际结果与证据**。

验收分两次准备：在需求/方案确定后先定义预期行为；代码完成后检查真实实现和影响范围，补齐执行细节及遗漏场景，然后执行。已有代码任务可以现在补做，但生成者必须重新读原始需求，不只读实现。

全自动放行只针对：范围已确定、所有必需验收有可判断的结果、环境可运行、当前候选版本全部通过。无法验证的地方明确阻塞，不用推测补成通过。缺失且影响结果的产品决定仍需明确；已存在的决定和授权不反复问人。

### 为什么适合你当前的流程

| 已有材料中的发现 | 本方案对应动作 |
|---|---|
| 历史任务中，Goal 续跑、effort 首轮参数、默认装配往往到实际使用时才发现遗漏 | 在验收定义里写真实入口、实际出站参数、状态及副作用；整合后的候选必须运行这些场景 |
| Lauren 的 Feature Map 与控制工具让 agent 可以自己操作产品、观察结果 | 优先补项目现有工具的入口索引及缺失观察能力，使验收能执行 |
| Factory 先定义断言、再实现切片，并为验证和修复保留执行时间 | 需求确定后生成验收定义；最后执行与修复使用同一任务的预算和状态 |
| Anthropic 长任务依靠功能清单、实际测试和持久记录接续 | 保存每次执行结果与版本，让新 session 能继续未通过的场景 |
| Pi 示例声明的部分 QA 脚本没有随公开源码提供 | 生成命令后实际定位并试跑；存在占位符时不得标为可执行 |

## 1. 验证包含哪些部分

### 1.1 每项任务都先检查的内容

| 部分 | 要回答的问题 | 典型证据 |
|---|---|---|
| 需求覆盖 | 每条有效要求、默认值、限制、例外是否都有对应验收？ | 原始需求位置 → 要求 ID → 必需场景/断言 → 结果 |
| 主流程 | 用户从真实入口操作后，能否得到要求的结果？ | UI/CLI/API 动作记录，以及状态、输出或副作用 |
| 边界与失败 | 和本需求相关的空值、非法输入、取消、失败等是否符合约定？ | 明确输入、故障条件、预期错误或“不应发生的事” |
| 组合与默认装配 | 各模块接起来、按实际默认配置启动后能否工作？ | 组合运行、真实路由/注册/配置、关键数据流 |
| 影响范围与回归 | 被这次改动影响的旧功能、调用方、旧数据是否仍然正确？ | 受影响测试、调用方/迁移检查、行为对比 |
| 代码与工程检查 | 项目要求的构建、类型、lint、测试是否通过？ | 命令、退出码、实际测试数、测试结果文件 |
| 验证可信性 | 检查的是哪个版本？检查真的执行并能发现错误吗？ | 代码/测试/环境身份、断言结果、原始证据、必要的反向检验 |

这些是检查维度，不意味着每项需求都新建七套测试。同一条场景可以覆盖多条要求，一条要求也可能需要多个场景。运行已有检查即可证明的部分直接复用。

### 1.2 由需求或变更触发的专项验证

| 出现什么变化 | 增加什么验证 | 不应凭空增加的规则 |
|---|---|---|
| 并发、异步事件、队列 | 顺序变化、重复事件、取消竞态、任务隔离 | 没有规范依据的“必须 exactly-once”承诺 |
| 持久化、重启、恢复 | 重启后状态、重复应用、失败恢复和残留 | 未要求的自动补偿或恢复策略 |
| 权限或隔离 | 允许范围内成功、禁止范围内无副作用 | 用户未要求的新权限等级 |
| 数据/IDL/API 变化 | 新旧数据、调用方契约、生成产物、兼容与合入顺序 | 所有开发都要等上游 merged |
| 性能要求/性能敏感路径 | 同环境基线、明确负载、指标和阈值 | 无来源的“必须快 20%” |
| UI/交互变化 | 实际动作、状态、指定尺寸/平台、视觉参照 | 无设计依据的主观美丑标准 |
| agent 的模型行为变化 | 固定样本、已知错例、独立评分、按约定重复评估 | 单次顺利输出就宣称概率可靠性 |

性能阈值、时间上限、权限和恢复语义来自需求、已确认决定或现有明确契约。无法确定的材料问题记录为待决，不让 agent 发明标准。

纯文档任务按用户规则：必要文档检查、提交/push、MR 创建或更新后交付，不新增应用运行或主动查询/等待 CI。检查该规则适用性本身也是范围判定的一部分。

## 2. 如何从需求生成对应验证

### 步骤 A：读取完整输入，固定来源

输入包括：当前需求、用户后续修订、已定决定、设计/接口资料、实施计划、当前仓库规则、已有测试与运行命令。记录版本或内容哈希，以及它们覆盖的范围。

原始需求和用户决定确定目标；实施计划用于补充执行和影响范围，不能用计划里的遗漏缩小原需求。代码说明“目前怎样做”，不能自行替代“应该怎样做”。冲突先按已明确的指令优先级解决；只有会改变产品结果且无法推定的冲突才请求决定。

### 步骤 B：把需求拆成可判断的行为

每个要求记录：来源、前置条件、动作、应该出现的结果、不应发生的结果、适用条件。给要求稳定 ID，不以测试文件名作为需求身份。

例如“支持修改设置”太粗。若需求明确包括保存和重启后生效，就拆成“保存成功”和“重启后仍使用保存值”；若还明确取消不保存，则单独保留。不能自动添加需求未要求的其它语义。

核查覆盖时逐条回看原文的默认值、否定条件、例外、阶段顺序，不只检查标题是否出现。一条需求关联十条测试也可能漏掉一个例外。

### 步骤 C：按行为和改动选择检查方式

先定位已有测试、CLI、浏览器驱动、日志和数据观察入口。优先使用成本低且能够证明结论的检查；用户入口、默认装配和跨模块路径需要真实组合场景。

- 确定的输入/输出关系使用可执行断言。
- 状态流转观察状态、事件和外部副作用，不只检查函数被调用。
- UI 场景检查动作前后及结果；最终截图不足以证明某个动作触发了变化。
- mock 可以覆盖故障分支，但只证明 mock 边界内的行为；不能替代明确要求的真实 provider、真实设备或实际入口。
- 外部事件的故障注入使用项目已有可控边界/适配器；绕过产品入口直接设置内部状态，不能被标成真实入口验收。
- 风格、视觉、开放式模型输出可用独立 agent 判断，但需明确参照和评分标准；判断不确定就保留未验结论。确定性属性仍用代码断言。

### 步骤 D：为每个场景补齐执行条件

一项可自动执行的场景至少要包含：

1. 对应要求和当前验收定义版本。
2. 精确的准备/运行方式：项目内现有命令、脚本或工具操作步骤。
3. 目标代码版本、环境、数据和所需工具。
4. 可重复的前置数据及隔离方式。
5. 明确的断言和判定依据；等待异步结果的边界/超时来源。
6. 日志、截图、响应、状态差异等证据的保存方式。
7. 清理自己创建的资源；证据不被清理。
8. 依赖与共享资源；能否并行、何时要串行。

未知命令、空阈值、未找到的工具或占位路径存在时，场景仍是草案，不能交给自动执行器并宣称 ready。凭据只记录名字/引用，不放进方案和证据正文。

### 步骤 E：独立检查验收定义是否漏项、是否会误判

使用一个没有参与本次实现判断的验收 agent，读取原需求和计划，检查每条要求的实际判定方法。它可以阅读代码定位入口，但不能照抄实现者的完成结论。

重点检查：

- 需求有没有对应场景，场景有没有真正断言预期结果。
- 错误实现会不会照样通过，正确的替代实现会不会被误拒。
- 是否只测内部方法而漏掉默认装配和用户入口。
- 运行工具是否已验证可用；测试是否空跑/被跳过/误匹配到零用例。

对关键行为，利用已知 bug、修改前可复现失败或隔离副本中的小范围错误来检查断言能否检出；不要求每次跑全量 mutation 测试。新功能没有旧失败时，不伪造红测记录。隔离的错误副本不进入交付分支。

独立 agent 也可能漏项。这里提升发现概率，不把多模型一致或“覆盖率 100%”作为绝对证明。先把必需场景和标准形成明确版本，再运行候选代码。

### 步骤 F：执行、修复、重验

执行前核对候选版本和准备状态；执行时记录命令/动作、退出码、实际断言、测试数量和原始输出。发现代码问题，交回实现 owner；owner 修复后形成新候选版本，再验证受影响场景和组合路径。

实现者可以修复代码和提出验收定义的问题，但不能为了变绿删掉要求、减弱断言或把必需场景改为不适用。验收工具本身出错时，验收 agent 根据原需求修正执行器，记录新版本和理由，重跑相关检查；实际改变需求含义才需要新的产品决定。

预先记录可用时间/费用/修复轮次，复用 Agent Lord 的有界重试。环境准备失败、实现失败、验证工具失败和需求不明确分别处理；重复没有新进展的循环应输出具体阻塞，而非无限重试或假通过。

## 3. 最终交付物是什么

交付物分“代码完成前可准备的输入”与“执行后产生的证明”。四部分在机器上能直接关联；人读的摘要由它们生成，避免维护两套清单。

### A. 一份验收定义

建议称 `verification-plan.json`，包含需求来源/版本、要求与场景的对应关系、预期结果、执行引用、适用条件、资源和证据要求。

这是概念名称和建议结构，当前 Agent Lord 尚未原生支持此文件。可先复用已有 plan 的 acceptance/verification 并链接这个产物；不能直接向 `implementation-plan-v1` 增加未知字段，其 schema 禁止额外字段。

### B. 可执行检查

尽量引用项目已有测试文件、命令与真实驱动工具；确有缺口才增加测试、fixture 或薄脚本。能长期复用的检查放业务仓库，任务的一次性材料放现有 run 产物目录。

单纯生成一份“请测试某功能”的文档不算可执行检查。可复用 skill 也可以作为入口，但必须有真实命令/工具步骤并完成试运行；本方案不要求另建通用 runner 框架。

### C. 机器可读的实际结果

建议称 `verification-result.json`，包含候选身份、验收定义哈希、逐场景结果、逐需求结论、失败分类、证据索引和最终判定。没有执行的检查明确为 NOT_RUN，不预填 PASS。

### D. 原始证据与简短报告

`evidence/` 留日志、测试结果、必要的截图/录像或状态差异；文件有大小/哈希及产生它的运行 ID。清理运行环境后仍能读取。报告回答：验证了哪个版本、哪些要求通过、哪些失败/未验、复现方法、下一步。

报告中的覆盖表从 A/C 自动生成；不再手工维护另一份 coverage ledger，也不要求把全部内部检查表和大日志加入 MR。MR 可放简短结论和必要引用，原始材料留现有任务产物位置。

示意目录：

```text
业务仓库
  现有 tests / e2e / scripts 中新增或复用的检查

现有任务产物目录 / verification
  verification-plan.json
  attempts/<attempt-id>/verification-result.json
  attempts/<attempt-id>/evidence/
  report.md                     # 从结果生成
```

## 4. 结果怎样决定是否自动交付

### 场景与运行状态

| 场景结果 | 含义 | 可否当通过 |
|---|---|---|
| PASS | 对应版本实际运行，断言满足，证据有效 | 可以 |
| FAIL | 执行后发现结果不符合要求 | 不可以，进入修复 |
| BLOCKED | 环境、权限、工具或关键语义缺失，无法判断 | 不可以，尝试解决可恢复问题 |
| NOT_RUN | 尚未执行 | 不可以 |
| STALE | 代码/需求/验证/环境变化，证据需要重新判定 | 不可以 |

是否“适用”在定义中单独记录，不是失败后的通过出口。不适用项必须附范围依据；未满足的有效要求不能靠此移出分母。没有适用的必需场景或所有测试被跳过，不能自动判定成功。

聚合规则：

- 任一适用必需断言 FAIL，则总体 FAIL。
- 没有 FAIL，但存在 BLOCKED/NOT_RUN/STALE、无场景的要求或不确定的必要判断，则总体 BLOCKED。
- 所有范围内有效要求都有完整必需场景，且场景有效 PASS，才输出 PASS。
- 已有明确授权接受的缺陷单列为“有例外交付”，记录授权来源，不能改写成所有需求通过；没有授权不创建例外。
- 自选的探索性发现先判断是否违反有效要求或仓库既有强制规则；属于新建议的不自动扩大本任务范围。

报告分别显示“已映射要求数/有效要求数”和“已验证要求数/有效要求数”，同时列未覆盖项。映射完整不代表测试有效；上述比率也不代表全部未知问题已被穷尽。

### 版本与环境必须一致

绑定：原始需求/决定版本、验收定义与执行器哈希、每个仓库 base/head、构建产物、依赖/配置、数据集、平台、实际服务实例。运行时确认访问的是本次实例和构建，避免本地 checkout 新而端口上跑的是旧进程。

验证期间候选源代码保持固定；测试可写隔离临时数据，不能悄悄修改交付代码。结束时核对代码和构建身份。跨仓需求记录完整版本组合，不能仅凭一个仓库 SHA 判定整体验收。

修复或 rebase 产生新 head 后：重新判断影响范围，重跑受影响场景及需要的组合检查。只有能够证明代码/依赖/环境与判定相关部分未变的检查才复用；明确记录旧证据和复用依据，不能把旧日志伪装成新执行。同版本已通过的有效检查不重复跑。最终报告对应本次实际交付候选。

## 5. 怎样接进 Agent Lord

### 5.1 推荐位置

```text
需求/方案确定
  → 生成并核查验收定义
  → 模块实现及局部检查（独立模块可并行）
  → 整合出候选代码
  → 独立需求验收
      ├─ 代码失败 → 原 owner 修复 → 新候选 → 重验
      ├─ 工具/环境失败 → 有界恢复 → 重验
      ├─ 未解决的必要决定 → 明确阻塞
      └─ 全部有效通过 → 发布/核对 MR → 最终报告
```

“发布/核对 MR”沿当前授权范围；验证通过不授予合并或部署权限。CI 在实际需要远端触发时可先 push/更新 MR，验收与 CI 均满足前不报告完成；本图是逻辑门槛，不强行规定所有远端动作只能最后发生。

正式最终验收放在整合候选上。模块实现过程中复用同一份定义做可执行的局部检查；首次完整行为出现时即可做组合预检，不必等最终阶段才发现接线问题。

### 5.2 当前能力与需改的边界

本次本机源码 HEAD 为 **cf06465299b43bc2390719d9d28d51380407d320**（#43），工作区干净。较上轮增加了 worktree 依赖安装；复用 workspace setup、隔离 worktree、任务产物、checkpoint/recovery 和写入保护。

| 当前源码事实 | 新环节需要补齐 |
|---|---|
| PlanModule.acceptance 和 verification 是字符串数组 | 将有效要求关联到实际场景和验证定义产物 |
| worker delivered 验证实际提交/operation 成功 | 保留代码交付事实，再判断模块已执行的场景；不能把提交成功当功能通过 |
| VerificationReceipt 只有 head_sha、checks(name/status/evidence/reason) | 接入机器结果；验证产物是否存在、身份/哈希和状态是否支持结论 |
| runtime 检查 evidence 非空、check 名称、SHA；不执行测试、不判 waiver 授权 | 执行者采集事实，控制器按状态/完整性生成 receipt，保留授权来源；不把任意非空路径当证据有效 |
| receipt 仅 passed / accepted_failure | FAIL/BLOCKED/NOT_RUN/STALE 保留在运行结果，不投影为成功 receipt；必要时扩展原有结果契约 |
| required checks 当前硬编码 ci | 需按任务政策处理是否需要 CI；不得为 docs-only 伪造 passed 或无授权 accepted_failure |
| closed run 拒绝新执行 | 验收与修复必须发生在 plan-report 关闭前；关闭后的新变更按原规则新 task/run |

不要在已关闭 run 后追加一个无法修复的检查，也不要只在最后报告里增加一句“已验收”。

### 5.3 最小接入方式

先保留现有 planner、workers、integrator；在 run 关闭前增加一个独立验收执行任务。验收任务使用独立隔离工作区、同一个已冻结候选版本，复用当前 writable endpoint 的依赖 setup；用任务写入边界约束它不改产品源码。不要使用 `--read-only` 后又假定依赖 setup 会运行，当前实现会跳过 read_only 的 setup。

integrator 在代码就绪时交出实际候选提交。验收任务返回机器结果和证据；代码失败由 caller 通过原 integrator 的合法续跑继续修复，再对新候选启动/接续验证。验收任务不得在 integrator 工作区中修代码，不形成第二个写入者。具体操作序列需在实施时结合当前 delivery 契约验证，不在本设计中虚构新的 CLI 命令。

成功时把已完成验证的具名检查关联到现有 verification receipt，同时保留详细结果引用；最终关闭前再次核对候选身份和所有必需状态。只检查 JSON 结构不能证明工具确实运行，应优先用 harness 捕获的日志/测试机器报告，独立 agent 负责无法机械判断的部分。

docs-only 可继续现有短路径，不进入要求 CI 的 plan-to-implement gate；若要统一接入，需先修改现有 CI 适用性政策。新设计不能声称当前 runtime 已支持自动 N/A。

## 6. 怎样最大程度减少人的介入

自动完成：读取既有决定、生成场景、准备环境、执行、收集结果、定位失败、交回修复、重验、输出报告。可重试的环境问题走已有恢复，已有授权不重复请求。

只把无法自行消除的问题交回：有效需求互相矛盾、缺少无法从项目推断的产品取舍、所需环境/权限不可用、已到修复预算且仍无法达标。此时列明具体要求、现有证据、已尝试方案和最小待决事项，其它独立工作可继续。

如果目前没有可靠自动判据，先补判据和运行工具；不通过“让另一个模型说可以”消除不确定性。无人介入是由可验证目标和可恢复环境支撑的执行结果，不是要求 agent 永远输出 PASS。

## 7. 第一版该做到哪里

1. 选择一个真实行为需求和一条曾发生的遗漏场景。
2. 生成一个验收定义，复用已有测试与真实入口，补最少必要工具。
3. 验证正确版本可通过、已知错误版本会失败、环境缺失会阻塞、空跑/旧版本证据会被拒绝。
4. 用同一任务实际走一次“实现 → 独立验收 → 修复 → 新版本重验 → 完成”。
5. 确认所有结论都能追到要求和原始结果，再决定 schema 与 pipeline 的最小正式改动。

这些是实施验收条件，本轮没有声称已经执行。示例文件见 examples/，全部标为草案/未运行，不能直接导入当前 Agent Lord schema。
