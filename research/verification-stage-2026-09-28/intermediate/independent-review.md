# 新验证环节：独立设计审查

日期：2026-09-28，Asia/Shanghai。状态：独立建议，未实现、未运行需求验证。

依据：本仓库已有研究与讨论；只读核查本机 Agent Lord `cf06465299b43bc2390719d9d28d51380407d320`，工作区干净。该版本比此前流程分析所用 `7fd6b38` 更新，新增 worktree 依赖准备；下述 receipt 结论来自本次源码读取。

## 1. 最小设计判断

建议新增的是一份可执行验收定义，以及实现后根据定义执行、失败后接续修复的环节。Agent Lord 继续负责派发、身份核验、状态保存和恢复；业务仓库负责启动项目、构造数据、操作产品和观测结果。

不需要另建任务数据库或第二份完成状态。需求和验收定义应进入现有 Plan / acceptance；结果最终汇入现有 receipt。中间每次执行的原始结果可作为 receipt 的证据附件。

**一条验收至少回答六件事：**

1. 对应哪条用户要求或已确认决定？
2. 在什么前提下做什么动作？
3. 预期观察到什么，哪些事情不能发生？
4. 用什么入口执行，观察什么外部结果？
5. 什么结果算通过，失败或无法执行如何区分？
6. 对应哪组代码、构建、环境和原始证据？

实现前形成验收定义；实现后运行定义。若只在代码写完后让同一个 agent 根据 diff 猜需求，再编测试，会把原始遗漏保留下来。

## 2. 验证应覆盖哪些部分

按需求风险选择，不要求每个任务运行全套。

| 部分 | 要回答的问题 | 最小合适证据 |
|---|---|---|
| 需求覆盖 | 原始要求是否都有对应场景，关键反例是否考虑？ | 要求 ID → 场景 ID；不能仅报测试数量或代码覆盖率 |
| 局部规则 | 状态、计算、转换及输入边界是否正确？ | 受影响单测、明确断言 |
| 接线与契约 | 调用、参数、依赖和跨仓生成产物是否一致？ | 集成／契约检查、实际出站参数或状态记录 |
| 用户完整行为 | 从默认入口启动，用户最终能完成要求吗？ | CLI/API/UI 操作以及结果、持久状态、副作用 |
| 回归与异常 | 变更是否破坏相关旧行为？重试、恢复、竞争等适用风险是否成立？ | 按影响面选择的回归与必要异常场景 |
| 版本与交付身份 | 验证的东西是否就是准备交付的东西？ | repo/base/head、构建标识、依赖版本、MR 身份 |

性能、权限、迁移、幂等、并发、恢复等按需求触发；没有相关风险时，不为统一模板强加昂贵流程。真实浏览器截图本身不证明持久化或后台副作用，需要对应观测；静态 review 不能替代运行结果。

## 3. 如何从需求生成验证

1. **汇总输入。** 原始需求、后续修正、已确认决定、现有接口与项目运行方法。明确哪份输入最新；已有资料可回答的问题由 agent 自行查证。
2. **拆成可观察要求。** 从“支持更新 Goal”得到“后台运行时更新，后台结束后只继续一次，并使用更新后的内容”等具体行为。示例只说明方法，不替用户决定未知产品语义。
3. **选择风险维度。** 正常路径、关键边界、失败恢复、旧行为、跨层接线。避免为每个需求机械相乘出全部组合；针对状态交互和历史漏检选关键组合。
4. **选择最便宜但足够的证明。** 规则用单测，接线用集成，关键用户行为通过实际入口。能共用一个场景证明几条相关要求时明确映射。
5. **绑定现成运行入口。** 优先复用业务仓库脚本、fixture、日志和浏览器控制。缺能力时先补最小入口，不把一份自然语言“应通过”当作可执行验证。
6. **独立核对覆盖。** 验收 reviewer 以需求为起点检查遗漏、错误假设、不可观察断言、假通过可能。实现 agent 不得靠删除场景或降低断言通过。
7. **检查验收本身是否有效。** 对 bug 保留基线复现再验证修复；对新增功能，按适用性用旧版失败、已知反例或受控错例确认场景能识别未实现。不能要求所有性能／非回归检查在基线失败。
8. **执行与修复。** 结果失败交还 owner；环境故障与产品缺陷分开；修复后重跑失败项及受影响关联项，保留旧尝试。

独立检查不保证完全独立判断，换一个模型也不是正确性的证明。最有价值的独立性是“预期来自需求、结果来自实际执行、判定可复查”；角色数量按风险选择。

## 4. 最容易遗漏的实现边界

### 4.1 当前 receipt 还不能表达完整执行过程

Agent Lord `core/src/plan.ts:137-145` 的 `VerificationReceipt` 目前只有：最终 `head_sha`；checks 的 `name`、`status`、`evidence`、可选 `reason`。状态只有 `passed` 和 `accepted_failure`。

`core/src/plan.ts:1413-1463` 核查 final SHA、名称覆盖、evidence 非空及 exception reason；它没有运行测试，没有读取日志验证断言，也没有检查 exception 的授权。`references/pipelines/plan-to-implement.md:115` 同样明确这个边界。

因此 MVP 可用每项 check 的 evidence 引用一个运行结果附件；它记录场景、动作、命令、退出码、断言、时间、原始文件哈希、观察到的行为与运行身份。**不要宣称现有 runtime 已经机械保证需求覆盖或证据真实性。** 如需要机器强制 gate，则需小范围扩展 schema 与校验；不得只把 prompt 要求当作运行时保障。

完整执行记录需要表达 `passed / failed / blocked / not_run`，并独立记录基于明确政策的 `not_applicable`。最终 receipt 是通过后的交付凭证，不宜把所有中间失败强塞成 `accepted_failure`。机器判定只能校验可计算部分；语义充分性仍由证据及独立复查降低误判。

### 4.2 docs-only 与当前 CI 硬要求冲突

`core/src/plan.ts:1428-1448` 固定要求 `ci` 加所有模块 verification。用户最新 AGENTS 明确 docs-only 必要文档检查、提交/push、MR 创建更新后结束，不主动查询/等待/修复 CI。

方案应声明兼容策略：复用既有 docs 短流程，或增加按实际 diff 识别的政策型 `not_applicable` 并修改对应 runtime gate。后者属于未来代码变更。**不能伪造 `ci: passed`，不能把不适用一律算作用户接受失败，更不能新增等 CI 要求。**

### 4.3 HEAD 正确仍可能运行错产物

最终候选 HEAD 固定后，仍可能连到旧服务、缓存旧构建或别人的端口。记录并核对运行程序/构建来源、启动命令、实际连接地址、必要配置与相关依赖标识。跨仓验收绑定整组 SHA；源码 SHA 正确不能替代运行身份。

不必收集机器所有环境变量或敏感信息。只记录解释结果所需字段，对凭据脱敏。

### 4.4 版本变化必须有失效规则

修复改了某段代码或基线／依赖／环境，重跑受影响场景，不能把旧 PASS 改个 SHA 继续使用。不受影响的同版本检查不重复执行。若拟复用不同 HEAD 的结果，必须明确影响判断依据；最终真实组合验收仍针对实际候选产物。

### 4.5 验证也可能破坏共享环境

验证计划需要最少运行前提、数据隔离、端口／数据库占用、清理方式。独立环境可并行，共享不可隔离资源串行。避免多个验证 agent 同时改同一数据后互相污染，或清理掉他人资源。

### 4.6 修复环不能无限运行，也不能悄悄降标

在任务预算内允许自动修复、重试和继续。相同失败无进展、所需权限/环境不可用、需求矛盾或产品取舍缺失时，结果为明确 blocker，并说明已做什么及需要哪个最小决定。预算可配置，不建议把固定重试次数宣布成经验最优。

复用现有 owner、claim、recovery；恢复时先确认旧写入者停止。验收失败可以派给原 owner 或安全接管者，不要求永远同一个 session。

### 4.7 功能验证通过不扩张交付授权

“可以开 MR”“可合并”“已合并”“已上线”分开。现有 integrator 不合并 MR。新增验证环节不能据此自动合入或部署；终点由本次需求已授权范围决定。

## 5. 最终交付物应是什么

一个随需求与版本保存的**验证包**即可，包含三个逻辑部分；不要求三个重复状态系统：

1. **验收定义**：要求、场景、运行前提、操作、断言、必要性和映射；对应原始需求版本。
2. **可执行入口**：复用或新增的测试／脚本／操作步骤，机器能找到并执行；业务仓库维护可复用部分。
3. **验收结果与证据**：逐条结果、执行身份、原始日志／trace／必要截图、缺项、最后判断；进入现有 receipt/report。

结论必须能回答：“覆盖哪些已确认要求；哪些实际通过；哪一组候选版本；哪里没验；是否到达本次授权交付终点。” 未运行不得算通过；不適用需说明依据且不混进已验证比例。

最小自动 gate：所有有效要求都有必要场景映射；必要场景全部实际通过；证据身份匹配候选；无未处理阻塞；不适用依据符合政策。该规则只能保证声明的范围，不能证明现实世界不存在未知缺陷。

## 6. 建议先验证流程自身

选一个真实需求做小试验，不立即建设通用验证平台：

- 用历史错例证明会漏接线的版本能被验收检出。
- 用正常版本证明能从启动到结果自动执行。
- 人为换成旧构建、遗漏场景、留下必需项未运行，检查能否阻止误报通过。
- 失败后交还 owner 修复，重跑受影响项，保留前后证据。
- 中途换一次 session，验证后继者能依据记录继续，不需要用户搬运报错。
- docs-only 走短路径，不产生额外 CI 等待。

这些是未来验收设计的试验要求，本轮没有执行或证明其收益。

- 最终结果绑定要求、定义、执行器、候选代码及实际运行环境；原始结果可追溯。

实施时还需证明的三点（文中已经保留为实施边界，不要求本轮再扩框架）：

1. **验收 endpoint 的不修改候选约束。** 当前 writable endpoint 才会执行依赖 setup，不能仅靠提示保证未改产品/测试；需复用或补足执行前后身份核验，确认候选代码、验收执行器和必要数据没有未经记录的改变。当前 `core/src/workspace.ts:78` 确认 read_only 会跳过 setup。
