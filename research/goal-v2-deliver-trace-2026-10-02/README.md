## 4. 深层问题：为什么跑得多，仍会晚发现

### 4.1 验收器把现有事实写成了错误契约

这不是一个孤立的 S04 问题，而是一组观测和断言错误：

| 案例 | 错在什么地方 | 正确处理边界 |
|---|---|---|
| S04/S05 | 产品计入本次已发出后被取消的请求，而该请求没有进入 Inspector，两者不是同一集合 | 明确请求身份、取消与失败的计数来源；检查同类条目，避免逐个发现逐个问 |
| S09 | 把“该 Goal 没有新请求”写成“整个系统没模型请求” | 标题生成等辅助请求应按身份排除 |
| S24 快捷键 | spec 说沿用用户偏好，却把非默认键写成默认键 | 查当前代码/设置；不为错误文档改产品行为 |
| S24 色值 | `blue/#0000ff` 字符串判法拒绝其他蓝色色值 | 按被冻结的可见意图判断；规范化表示，不扩大颜色要求 |
| S01 第二轮 | 把“至多 1 次收尾”变成“必须 1 次” | 允许 0，但对应未触发的分支要保留未验证状态 |
| S22 | 分析器读错 status 路径得到 null，仍 PASS | 必须证明必要字段真的存在；M5 检查已发现，旧运行原始值恰好正确不说明判定器可靠 |
| S02 第二轮 | 重置时间早于运行时间，合法自动恢复被判升级保持失败 | 开始前核实 fixture 到期时间；过期就重新构造 |
| X1 | 停止/恢复跑通，但目标 `user-stop + continuation` 状态四次未出现 | 分开“运行有效”“路径命中”“结果通过”，不能用末尾成功覆盖前提缺失 |

因此最划算的优化不是更多口头查漏，而是给**已有判定器**补少量能拒绝缺字段、过期前提、错误表示的真实反例。先修高复发项，不为每个字段建立新框架。三家依据见 T1/T2/T11，原始失败与本轮核对见 [末端状态](final-state.md)和 [M5 检查](../../requirements/goal-v2-and-feedback-fixes/evidence/milestone-M5-r1.md)。

### 4.2 验证前提过分依赖模型临场行为

S09 多次要求模型第一次就选择特定工具，实际先 glob/bash，导致前提不成立；S10 也有类似重复尝试。X1 用 sleep 与插话时序形成目标队列状态，四次未打中真正待测的暂停路径。这里即使模型完全按产品规则行动，也可能没覆盖目标代码。

可控状态转移用故障注入、事件屏障和集成测试固定；需要证明用户入口/真实模型表现的部分仍走真实入口。前提构造与结果判定分开记录，失败次数上限和盲区沿用已授权 verify。不要删掉真实模型验证，也不要无限重跑直到出现一个绿样本。

S25 是反例：两次失败揭示历史 Goal 指令还在影响普通对话，不能简单归为模型随机。owner 经 q4 加状态提醒后，三次有效运行不再执行旧任务；这是有代码变化、请求证据和结果对照的修复。保留这条因果链，不能只留下最后三次 PASS。

### 4.3 组合状态检查来得晚

M5 才核实“恢复事实—绑定 conversation—问卷恢复—Goal 接管”的派发关系，发现可能卡死 ready；M6 才发现用户停止/离开/普通失败造成的 queue pause 会挡住 Goal continuation。现有里程碑按功能拆分，但故障跨 Goal、queue、questionnaire、普通 Turn 的边界。

优化应把 **恢复 × 队列暂停 × 问卷/普通 Turn** 这几个高风险组合在迁移接通时就做最小集成探针，并在最后实际入口验证。不是把所有场景都提前，也不是要求 M1 就重跑 M6 全集。检查器之间应关注不同风险：代码检查找生命周期/派发关系，场景检查找真实入口和用户可见结果，二者都无法独立替代另一方。

### 4.4 并行真正被共享资源限制

早期已有多个实现子任务，继续增加 agent 数量不能解决：Electron 共享认证刷新、全机键盘焦点、基线数据目录、检出/构建产物被不同任务改动。

V1 有实际改善：20.8 分钟五实例运行，以及最终五条 lane，鉴权计数为 0。第一轮五 lane 的子任务跨度约 29–72 分钟，按最长 lane 决定整体时长；这些集合不同，不能拿它与 M4 的串行耗时做严格倍速实验。M5 又发现 TUI 刷新未完全纳入规则，随后补修，说明“某轮没有401”不等于覆盖了所有刷新边界。

18:37 用户键盘进入测试窗口，是新的共享资源缺口；发送前比对输入框是局部止损，不能证明以后多窗口并行不会被抢焦点。S15/S39 的越界事件进一步说明独立 workspace 不代表执行能力被限制在 workspace。应优先改现有测试入口，选择可靠后台驱动或真正独立的测试桌面/执行环境，再用污染实验确认隔离。具体方式待设计，本轮未更改机器环境。

### 4.5 质量检查清单没有和实际 CI 对齐

早期已有敏感词、knip、迁移测试、旧 dist 引用漏项；最后 CI 再出现新导出/类型与 TUI lint。大量相关测试通过，仍不代表生产 dead-code 或另一包 lint 已覆盖。

可证的问题是实际执行的本地检查与 CI 触发的检查集合不一致。最小做法是在现有 plan 中引用仓库已有命令组，按本次触达包补齐，最终读合并结果 CI。不要复制另一套 CI，也不要以“功能不受影响”忽略明确的交付失败。[当前失败证据](ci-evidence.md)

### 4.6 “外层服务中断”没有形成完整交接

末尾错误不是自然结束，模型已经无法继续生成；不能指望它在报 403 后再写完收尾总结。已有 plan 和 evidence 避免了全部丢失，但 plan 停在四条 lane 开始附近，第二轮结果分散在主/子 trace，最后文档提交未推，MR 描述还是早期状态。

应利用现有 plan 在每条 lane 返回时留下结果/剩余项/对应 head，不等整轮全绿再汇总。外层失败必须区别于产品 FAIL，恢复时先核对资源状态和已完成工件，不从头全部重验。只在执行器已有能力里留持久状态；本轮不提新的 Stop hook、收费自动扩容或常驻调度系统。理论依据 T4/T5/T9。

### 4.7 记录本身会漂移

发现三类漂移：plan 的 00:35/00:50 与实际 Git 00:03/00:15 不一致；全量 trace 含 UUID 重放；子任务 usage 首片段被当总量。另有坏字符在后半程仍出现：主会话 L11799 明说钩子把第③项猜成②，01:08 与 01:20 又手动修 U+FFFD。

这些不证明产品代码有坏字符，却足以否定“装好钩子后所有材料都可靠”的概括。保持原文可追溯；涉及语义的自动补字应有 diff 读回，数字时间来自命令/事件，不用估计值补齐。主 plan 保持短，只链接证据；完整历史留归档按需读。

## 7. 对“能优化多少”的回答

可以确定消除的是具体失败模式：同一事实反复询问、已过期 fixture 重跑、错误判据拒绝有效结果、不同实例互相失效、失败后重新从零定位状态。**不能据此给出“能节省 X 小时/百分之 Y”的承诺。** 夜间主链中断、用户不在线、子任务仍运行、不同场景集合等因素让简单相减失真。

已有足够正证据保留三件事：迁移前后对照；里程碑代码检查与场景实跑的互补；新规则下的跨家咨询和并行实例。它们分别发现了真实回归、缩小了不必要等待、提高了运行吞吐。本次还缺最终独立验证与交付收口，应该先让这条链完成，再评价整套流程。
