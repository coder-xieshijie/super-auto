## 4. 对本次新增断点的具体适用方式

以下是根据主分析提供的最新 trace 位置作出的工程推导；它们是修复设计的输入，尚未实施或验证。

**执行器 403 与产品 Goal 预算分层。** 末条 `Failed to authenticate ... 403 预算不足` 描述的是承载本次工作流的 Claude 调用失败。需要保留原始错误、最后成功事件、当前工作树/提交、活跃子任务、已验证/未验证清单。恢复先核对资源状态和工作树，再接未完项；不能期待已经无法调用模型的 owner 在失败之后自行写完摘要。因此恢复所需的状态要在运行中增量留下。预算提升、账号切换与新的费用承诺均不在理论的“自动恢复”授权里。依据 T4；此处不提出 Stop hook 的新增实施，用户已经把它排除在当前 PR 外。

**有效场景至少有三件独立事实：前提、观察、结果。** S02 的 `--reset-in 3600` 是会随真实时间失效的 fixture；之后运行若未复核时钟前提，失败不能直接归因产品。X1 f4 中目标前提未成立而恢复读数 PASS，只能证明实际发生的那条路径，不足以覆盖目标场景。重跑应保留旧失败及原因，并证明新运行构造了目标前提；不能只是“再试到绿”。S24 的 CSS 色值表示差异则属于观察器：先确认 spec 要求的是颜色语义还是字面 token，再选规范化色值、计算样式或可见效果断言。原文不提供这些具体算法；它们是 T2 的工程应用。

**隔离应覆盖共享对象，而不仅是工作目录。** Electron 多个 profile 可以仍共享 refresh token，多个窗口也可以仍共享一个键盘焦点。认证租约的有效期、令牌刷新者和失效响应，应由测试能力明确管理；前提有时效时，要在场景开始前重新构造或检查。焦点污染需要有具体复现实验后再选驱动方式；仅加一句“发出前看输入框”有帮助，但不能证明并发安全。T6 给的是隔离原则，不是默认要求多个账号、虚拟机或全面去沙箱。

**异常行为与覆盖状态需要保留，不因分类方便抹掉。** X1 f3 的 `questionnaire_watch` 指出等待原因缺失的线索，在 owner 对照预期和状态事件判定前应继续列为待判定。外层服务中断、无效 fixture、有效观察下的产品错误、越界 incident 应分别记录。功能 PASS、场景覆盖完成、无未处置 incident、CI 通过是不同事实。当前死代码/no-lone-blocks 若仍失败，意味着结果要求仍未满足；“只查结果”没有免除 CI。

**重跑与恢复只要求说明为什么，不要求新账本。** 现有 plan 的进度、证据路径、决定清单和结果检查已经能承载这些区别。优先在已有输出里增加能判因的字段或错误说明：例如 fixture 到期时间、观测到的真实状态和任务停止原因。是否新增结构、脚本或硬门禁应由真实复发成本决定，不把分析分类全部变成流程代码。

## 6. 人工介入的判断口径

对每次人工介入分别回答四个问题，比只统计“问了多少次”更有用：

1. 它提供了 agent 无法自行获得的新事实，还是补发了已经存在的授权/决定？
2. 没有这次输入，工作是客观无法继续，还是旧规则要求它等待？
