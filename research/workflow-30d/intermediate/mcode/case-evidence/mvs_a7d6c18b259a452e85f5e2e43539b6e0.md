## 现在重新解释决策 1 和 2

### 决策 1：`rm build/*` 这类命令怎么办？

沙箱开启时，这类命令无法走笼子外的可恢复路径（原因见上，展开 = 越狱）。三个选项：

- **甲：让它在笼子里正常 `rm`** —— 真删除，不进废纸篓。沙箱本身会保证它删不出工作区，所以**安全性没问题**，只是这一次删除不可恢复。需要明确告诉用户。
- **乙：投入成本做"安全展开"** —— 在授权层自己实现 glob 匹配（不调用 shell，只做纯路径匹配），把展开结果纳入授权判断后交给笼子外执行。能保住可恢复，但工作量明显更大，且 `$f`、`$(...)` 这类仍然做不到。
- **丙：拒绝执行，让模型改写成单条 rm** —— 这是 MR 现在 step 8 的做法（`bash-permission.ts:1489-1498`）。

> 我倾向**甲**。理由：沙箱已经保证了删除范围安全，"可恢复"是锦上添花而不是安全底线；为了它把常见命令堵死或投入大量工程量，性价比不对。乙可以后续排期。

### 决策 2：mavis-trash 脚本本身坏了怎么办？

程序每次用脚本前会检查"这文件还是我认识的那个吗"——**逐字节比对**（`ensure-trash-script.ts:90`）。对不上的现实场景：装了两个版本的 app 共用同一个 `~/.minimax` 目录、用户手动改过脚本、磁盘只读。

现在的代码选择是：**拒绝执行任何含 `rm` 的命令，而且用户点"同意"也没用**（`facade.ts:1239` 的 `safety-immune`），并且**沙箱开不开都一样**。

决策 2 就是问这种时候应该：

- **保守**：继续拒绝——保住"删除一定可恢复"的承诺，代价是这台机器上所有 `rm` 全部瘫痪且用户无法自救
- **降级**：直接删除 + 明确告知用户"本次删除不可恢复"——能用，但破坏承诺

> 我倾向**降级**。一个执行层的辅助能力坏掉，不应该有权瘫痪用户的基本操作，更不应该连"我知道风险，继续"都不给。

---

两个决策的共同点是：**"可恢复"到底是产品承诺（必须保证，宁可不可用）还是尽力而为（能做就做，做不到降级告知）**。你定这一条，1 和 2 就都定了。

## 1. shim 是什么，为什么要用它

### 先搞清楚：你敲 `rm a.txt` 时到底发生了什么

`rm` 不是什么魔法关键字，它就是一个**程序文件**，躺在硬盘上，通常在 `/bin/rm`。

你敲下 `rm a.txt` 之后，bash 要去把这个程序找出来。怎么找？它有一份**目录清单**，按顺序一个个翻，用**第一个**找到的。这份清单就叫 `PATH`：

```
PATH = /usr/local/bin : /usr/bin : /bin
```

bash 先看 `/usr/local/bin` 里有没有叫 `rm` 的，没有就看 `/usr/bin`，再没有才看 `/bin`。找到就用，不再往下找。

**关键推论：谁控制了这份清单的最前面，谁就决定了 `rm` 到底运行的是哪个程序。**

### shim 就是插在最前面的那个替身

我们在清单最前面加一个自己的目录，里面放一个也叫 `rm` 的文件（内容是 mavis-trash）：

```
PATH = /Users/x/.minimax/shims : /usr/local/bin : /usr/bin : /bin
        └── 这里放一个叫 rm 的文件
```

从此 bash 找 `rm` 时第一站就撞上我们的，`/bin/rm` 根本轮不到。**命令文本一个字都不用改**，`rm a.txt` 还是 `rm a.txt`，但实际跑的是回收站版本。

"shim" 中文一般叫垫片——就是塞在中间的一层薄片，把原本要碰上的两个东西隔开。

### 为什么这比现在的做法好

现在的做法是**改写命令文本**：程序在执行前先读一遍命令字符串，把 `rm a.txt` 编辑成 `mavis-trash -- a.txt`，再交给 bash。

像一个校对员，在你的信寄出前找出"删除"两个字改掉。

问题是：**要改对，就得先看懂这封信。**而 shell 命令可以复杂到看不懂：

| 命令 | 校对员的困境 |
|---|---|
| `echo ok && rm a.txt` | 得先看懂这是两条命令，找出第二条里的 rm |
| `xargs rm` | rm 在这，但要删什么完全没写 |
| `find . -exec rm {} \;` | rm 是别的程序的参数，不是命令本身 |
| `bash cleanup.sh` | **文本里根本没有 rm**，它藏在脚本文件里 |

这个活儿**永远干不完**，每冒出一种新写法就是一个新窟窿。

shim 不看信。它不关心 `rm` 是被谁、用什么方式叫起来的——用户直接敲的、`xargs` 叫的、`find` 叫的、还是某个脚本里面叫的，**只要有任何东西试图运行一个叫 `rm` 的程序，跑起来的就是我们的**。

问题被挪到了更底下一层解决，上面那一整套"看懂命令"的复杂度就全没了。

打个比方：公司里大家打分机 8888 找清洁工小王扔东西。
- **改写方案** = 挨个去改每个人通讯录里的号码。总有人从别处抄到老号码（脚本、xargs、find）。
- **shim 方案** = 直接把 8888 这个分机转接到小李。不管谁、从哪拿到的号码，拨 8888 接的就是小李。

### 两个要注意的地方

**唯一的漏洞**：有人不拨分机，直接拨外线——也就是 `/bin/rm a.txt` 这种写死绝对路径的写法，它跳过了 PATH 查找。不过我查过了，permission 层**已经有专门的检测**（`bash-permission.ts:243`），精确认得 `/bin/rm`、`\rm`、`busybox rm` 这些绕过写法，是现成的，不用新写。

**一个坑**：这个 shim 目录**绝对不能**放在 `~/.minimax/bin/`。因为程序启动时会把那个目录写进你的 `~/.zshrc`（`ensure-path-integration.ts:53`）——那是**你自己终端**的 PATH。往里放个 `rm`，你自己敲 `rm` 也会被换掉。必须用一个独立目录，只给 agent 的 bash 用。

## 2. unlinkAllowOnly 是做什么的

### 先说名字

`unlink` 是 Unix 里"删除文件"这个动作的正式名称。为什么叫"解除链接"？因为在 Unix 里，文件名只是指向真实数据的一个**链接**；把最后一个链接解除掉，数据才真正消失。所以 `unlink` = 删文件。

`unlinkAllowOnly` = **"删除操作只允许发生在这些目录里"**。

### 为什么删除要单独管

沙箱是给命令套的笼子，笼子的规则是按**动作种类**分开写的：

| 规则 | 管什么 |
|---|---|
| `allowRead` | 能读哪些地方 |
| `allowWrite` | 能写哪些地方 |
| `unlinkAllowOnly` | **能删哪些地方** |

为什么不把"删"并进"写"？因为两者的风险完全不同：

- **写错文件** → 一般还能救（git 能还原、有备份、文件还在）
- **删掉文件** → 可能就真没了

正因为分开管，才能配出一个很有用的档位：**可以写全盘，但只能删工作区**。agent 可以改你 home 目录下的配置文件，但绝对删不掉你的 `~/Documents`。这就是 `delete_guard` 档。

产品现在有四档（`effective-policy.ts:44-53`）：

| 档位 | 能写 | 能删 |
|---|---|---|
| `read_only` | 只有临时目录 | 只有临时目录 |
| `workspace_write` | 工作区 | 工作区 |
| `delete_guard` | **全盘** | **只有工作区** |
| `full_access` | 全盘 | 全盘 |

### 最关键的一点：这是操作系统在拦，不是程序在拦

`unlinkAllowOnly` 不是代码里写个 `if (路径不对) return false`。它是交给 macOS 内核的规则（seatbelt 机制）。

区别很大：程序里的 if 判断，只在程序想起来检查的时候才生效，写漏一处就是个洞；内核拦截是在**真正执行删除的那一瞬间**由操作系统挡下来，**程序骗不过它，也绕不过它**。

### 这跟回收站的争论是同一件事

现在你能看出前面那些讨论为什么绕着这个词转了：

**如果 mavis-trash 在笼子里跑**（我推荐的方案）：
`delete_guard` 档下 agent 执行 `rm ~/Documents/x`，脚本尝试把它挪走 → 内核发现这个删除不在工作区 → **直接拒绝**。正确、自动、不需要任何手写检查。

**如果 mavis-trash 在笼子外跑**（当前 MR 的做法，或者走 Finder）：
删除动作压根没经过内核 → **`unlinkAllowOnly` 在这条路上完全失效** → 只能靠人手写一段检查来补 → 那就是 `host-trash-executor.ts:191-225` 那 35 行，而且它写得比内核规则**更窄**（内核允许删 git 目录，它不允许），沙箱关闭时更是**一点都不检查**。

一句话：**把执行搬出笼子，就等于把沙箱最核心的那条规则关掉，然后再手写一个残缺版本顶上。**

### 我说"地基待验证"是什么意思

把文件挪进废纸篓，脚本用的是 `mv` 命令。

而 `mv` 在同一个磁盘上，底层执行的其实不是"删除"（unlink），而是"**改名/搬家**"（rename）——文件数据没动，只是换了个位置登记。

所以问题来了：**沙箱的删除规则，盯的只是"删除"这个动作，还是连"把文件搬走"也一起盯？**

- 如果连搬家也管 → 我的方案成立，`rm ~/Documents/x` 会被内核挡下
- 如果只管删除不管搬家 → `mv ~/Documents/x ~/.Trash/` 就溜过去了，**`delete_guard` 形同虚设**，整个方案塌掉

这个答案藏在 `@minimax/mcode-sandbox-runtime` 这个包里，而它在任何一个 worktree 里都没安装，我只能从字段名推断、验证不了。所以我一直说这条**必须让实现者确认，或者装上包实测一次**——它是整个方案的地基。

# 1. 配置热生效

## 是什么

你在设置面板把沙箱从「只读」改成「可写工作区」。此刻可能有 5 条 bash 正在跑。**新设置从什么时候开始算数？** 这就是热生效要回答的问题。

- **连正在跑的命令一起改** —— 物理上做不到。命令已经被 `sandbox-exec` 按旧规则包好交给内核了，内核不接受中途换规则。

- **重开 App 才生效** —— 最笨但最省事。

# 3. Put Back 能力缺失

## 是什么

macOS 上你在访达里删文件，它进废纸篓。右键有个「放回原处」(Put Back)，一键回到原目录。**这个「原来在哪」的信息不在文件里，是访达单独记的一笔账。**

`mavis-trash` 有两条路进废纸篓（`trash-script.ts:320-345`）：

1. **叫访达干** —— `osascript -e 'tell application "Finder" to delete ...'`。访达记账，**有 Put Back**。
2. **自己 mv** —— `mv "$file" "$HOME/.Trash/xxx"`。文件确实在废纸篓里、看得见拖得出来，但**没人记账，Put Back 是灰的**。

## 不是 mavis-trash 缺能力，是我主动禁了第一条

两条路它一直都有。是我这次改动在沙箱内**强制走第 2 条**：`trash-script.ts:326` 判断 `MAVIS_TRASH_FORCE_MV`，`srt-macos.ts:127` 注入这个变量。

**为什么必须禁**：访达是一个**在笼子外面**跑的独立进程。你让它删文件，真正执行 unlink 的是访达自己，内核检查的是访达的权限，不是被关起来那个 bash 的权限。结果就是——沙箱设了 `unlinkAllowOnly`（只准删工作区内的），但绕道访达任何路径都能删，`delete_guard` 形同虚设。Linux 上 `gio trash` 是一模一样的问题（交给桌面服务进程）。

## 取舍与影响面

**沙箱开着**：牺牲 Put Back，换 `delete_guard` 真的生效。
**沙箱关着**：`MAVIS_TRASH_FORCE_MV` 不存在，走访达，Put Back 照旧。

`trash-script.ts` 在 6284 里是 **0 行改动**（纯复用），这个降级是我这次 MR 6510 引入的。影响面仅限「沙箱开启 + macOS/Linux」。文件不会丢，只是恢复时要手动拖回去。

# 4. 硬解析 / 破坏性 / 删除漏网

## 4.1 还有多少硬解析

有，不少，但**位置和性质都变了**。

改之前：POSIX 上「删除能否恢复」依赖解析——permission 层认出 `rm` 才改写成 `mavis-trash`，认不出就漏。
改之后：POSIX 上靠 PATH shim（`ensure-rm-shim.ts:47-64`），**不依赖任何解析**。不管是 `rm`、`xargs rm`、`find -exec rm`，还是 agent 现写的脚本里的 `rm`，shell 都要走 PATH，必撞 shim。

**仍存在的硬解析**（全在 permission 层，管的是「要不要问用户」，不是「能不能恢复」）：

| 位置 | 认什么 | 认错的后果 |
|---|---|---|
| `bash-permission.ts:228-243` | `rm` + 绕过形状（`\rm` `/bin/rm` `busybox rm` `command rm` `env rm`） | 少问一次；**不影响可恢复性** |
| `dangerous-patterns.ts:1128-1169` | `unlink` / `find -delete` / `xargs rm` / `parallel rm` / `fd -x rm` | 少问一次 |
| `dangerous-patterns.ts:531-568` | `del` / `erase` / `rd /s` / `Remove-Item` | Windows 上**真删且不可恢复**（Windows 没 shim） |
| `bash-wrapper-unwrap.ts` | 拆 `bash -c` / `cmd /c` 嵌套 | 内层命令躲过安全扫描 |

**关键：解析不准的代价，从「数据没了」降级成「少弹一次确认框」**（POSIX 上）。这正是分层要达到的效果。

## 4.2 对已有功能的破坏性影响

**① `rm` 语义变了，且是全局的，agent 每一条 bash 都受影响**

- `rm` 现在拒绝删当前目录、home、及它们的父目录（`trash-script.ts:119-153`）。`cd /tmp/build && rm -rf .` 会直接失败，退出码 64。原生 `rm` 没这限制。
- **大量删除会塞满废纸篓**。`rm -rf node_modules` 变成把几万个文件 mv 进 `~/.Trash`，**不释放磁盘**。跑几轮清理磁盘就满了。MR 里**没有任何配额或自动清理**——我认为这是最可能被真实用户投诉的一条。
- 跨文件系统时 `mv` 退化成拷贝+删除。工作区若挂在与 `~/.Trash` 不同的卷（外置盘、Docker volume、tmpfs），删 10G 目录变成拷 10G，慢到像卡死。
- 错误信息前缀从 `rm:` 变 `mavis-trash:`，任何 grep 输出的脚本会失配。

**② 覆盖不完整——有 bash 生成点没拿到 shim**

我实测三处：

- `local-runtime/src/api/local-native-tools.ts:192` → 前台 bash，**有**
- `local-runtime-v2/src/runtime.ts:105` → 后台 bash，**有**
- `agent-core/src/pi-turn-runner/tools.ts:54` → `resolveBashEnvPolicy()` 裸调用，**没有**

同理 `agent-tools/src/desktop/local-pi-tools.ts:349` 和 `background-bash/executor.ts:53` 都是 `envPolicy ?? resolveBashEnvPolicy()`——传了才有。desktop 主链路都传了，但**靠调用方自觉，类型上不强制**。新增 bash 入口忘了传 = 静默的删除黑洞，没有测试会红。

**这是本次改动自身引入的最大结构性风险。** 修法：把 `prependPath` 变成 `BashEnvPolicy` 的必填，或让 `resolveBashEnvPolicy` 默认就带上。

**③ `read_only` 模式不给 trash 写权限**（`effective-policy.ts:56-58`）

有意为之——只读就不该删。但后果是 read_only 沙箱里跑 `rm`，mavis-trash 的 `mv` 被内核拒，报 `failed to trash`，而不是「只读模式不允许删除」。体验问题，非安全问题。

## 4.3 删除防护会失败吗？哪些场景漏了

会。按「能不能找回来」分三类：

**A. shim 接不住，但 permission 拦得住（拦住就不执行，安全）**

- `/bin/rm -rf x` —— 绝对路径不查 PATH，但 `RM_BYPASS_SOURCE_PATTERN`（`:243`）认出来了 → ask/deny
- `env -i rm` / `busybox rm` / `command rm` —— 同上
- `find . -delete` / `xargs rm` / `fd -x rm` —— `:1145-1168` 覆盖
- `git clean -fdx` / `git reset --hard` —— `:1301-1305` 覆盖。git 直接调 unlink，shim 完全接不住，只能靠 permission

**B. shim 接不住，permission 也接不住 —— 真漏**

- `/usr/local/opt/coreutils/libexec/gnubin/rm` —— `RM_BYPASS_SOURCE_PATTERN` 只列了 6 个目录（`bin`/`sbin`/`usr/bin`/`usr/sbin`/`usr/local/bin`/`usr/local/sbin`），Homebrew coreutils 路径不在内
- `perl -e 'unlink glob "*"'` —— `\bunlink\s`（`:1143`）要求 unlink 后跟空格，`unlink(` 不匹配
- 任何编译好的二进制自己调 unlink
- `python3 -c "shutil.rmtree(...)"` / `node -e "fs.rmSync(...)"` —— 命中 `interpreter-inline`（`:876-883`），但那是 SOFT，**只弹确认框、不阻断，也不会让删除变可恢复**

**沙箱没开时，B 类全部是真删除、不可恢复。** 沙箱开着时，B 类中超出 `unlinkAllowOnly` 范围的会被内核拦下；范围内的仍是真删除——内核只管「准不准删」，不管「删了进不进废纸篓」。

**C. 沙箱自身的绕过**

`localAccess: 'open'` 是默认值（`sandbox-config.ts:40`），它同时打开 `allowAppleEvents`（`srt-macos.ts:177`）。Apple Events 开着 = 笼内进程可以指挥笼外 App 干活，包括让访达删文件。`MAVIS_TRASH_FORCE_MV` 只管住了 mavis-trash 自己，管不住 agent 直接写 `osascript -e 'tell application "Finder" to delete ...'`。**这是一条真实的 delete_guard 绕过路径，本次 MR 没修，是 6284 自带的。**

## 4.4 一句话结论

分层是对的，POSIX 侧从「靠猜命令文本」换成「靠 PATH」是质变。但**「保证所有删除都走可恢复」这个目标，当前实现的真实覆盖是：经 shell 按名字调用 `rm` 的删除 100% 可恢复；其它删除路径不可恢复，只有部分被 permission 拦住。** 比改动前强很多（改前连 `xargs rm` 都漏），但不是「所有」。

# 直接回答

因为「把 mavis-trash 从 permission 迁到 execution」**搬的是职责，不是代码**。原来的代码没法照搬——permission 层的机制是「改写命令文本」，而 execution 层根本见不到命令文本的语义，它手里唯一的工具是 spawn 时的进程环境。所以这不是搬家，是**换机制**：从「文本改写」换成「PATH shim」。机制一换，覆盖模型和工程成本都跟着换，你看到的「改动多」和「遗漏」几乎全部由此而来，下面逐条拆。

---

## 为什么代码不能照搬

打个比方：文本改写像**寄信前把信里的地址涂改掉**——只能改看得懂的信（`rm -rf x` 能认出来，`xargs rm` 认不出来）。PATH shim 像**改邮局的投递规则**——不管信怎么写，凡是投给「rm」这个名字的都送进废纸篓。

如果真的把改写代码原样搬进 executor，会得到三个坏结果：executor 要重新解析 permission 已经解析过的命令（两份解析器，必然漂移）；`xargs rm`/脚本内 rm 照样漏（解析的固有盲区跟着搬过去了）；executor 还得依赖 permission 的 tokenizer——**这是制造新耦合，不是解耦**。所以 execution 层表达「删除可恢复」的正确形式只有一种：让操作系统解析到的那个 `rm` 本身就是可恢复的，即 PATH。

## 机制换了 → 成本结构换了，这就是「改动多」的来源

关键区别一句话：**文本跟着命令走，环境跟着 spawn 链走。**

- 旧机制：改写发生在 permission 管道里一个点，改完的文本自己流到任何执行处。一处改，处处生效。
- 新机制：环境必须在**每一条 spawn 链**上注入。这个仓库有两条独立链（前台 V1：`local-native-tools.ts` → agent-tools；后台 V2：`runtime.ts` → `deferred-port.ts` → `initialize.ts` → `executor.ts`），所以出现了 6 个文件的穿线，每处 3-8 行。

这 6 个文件的管线**不是迁移做糙了，是环境类机制的固有价格**。作为对照：它买回来的是文本机制永远买不到的东西——`xargs rm`、`find -exec rm`、agent 现写脚本里的 `rm`，全部收编。

## 「遗漏」的账：三栏对比

| 场景 | 迁移前（文本改写） | 迁移后（shim + 保留改写） |
|---|---|---|
| 解析得出的 `rm` | ✅ 可恢复 | ✅ 可恢复（双保险） |
| `xargs rm` / `find -exec rm` / 脚本内 `rm` | ❌ 漏 | ✅ **迁移消灭的** |
| `/bin/rm`、homebrew rm、`git clean`、`python -c` 删除、二进制直调 unlink | ❌ 漏（只有 permission 弹框） | ❌ 照旧漏（只有 permission 弹框）——**迁移前就有，不是迁移产生的** |
| 未穿线的 spawn 点（如 `pi-turn-runner/tools.ts:54`） | 走 permission 就有文本改写 | 同样有文本改写，只是**没升级到 shim** |

**结论：迁移让遗漏集合严格变小了，没有任何场景变差。剩下的第三栏不是迁移的锅——那是物理极限**：删除最终是一次 unlink 系统调用，文本层看不见它，PATH 层只接得住「按名字找 rm」的，系统调用层只有沙箱内核够得着，而内核只能「拦」不能「改写成可恢复」。所以设计就是三层各兜各的：shim 转换接得住的，permission 对接不住的形状弹确认，sandbox 拦范围外的 unlink。想把第三栏清零，得上 FUSE 覆盖文件系统这类 OS 级手段，那是另一个量级的工程。

**问题在哪**：「往 PATH 前面塞」这件事不是自动发生的。代码里每一个「启动 shell」的地方，都要自己记得把改过的 PATH 递进去。这个仓库启动 shell 的地方不止一处——前台命令一个入口、后台任务一个入口、内置兜底工具又一个入口。而「递 PATH」在类型上是**可选参数**（`prependPath?`），还有 `envPolicy ?? resolveBashEnvPolicy()` 这种「没给就用素的」兜底写法。

**打个比方**：公司规定所有包裹必须过安检机。但大楼有好几个门，安检机要各个门自己装，而且制度上写的是「建议安装」。现在已知的门都装了；可是明年新开一个侧门的同事，完全可能不知道有这条规定——制度不会拦他，也没有任何巡检会发现。

**事故剧本**：半年后有人加了一个新的「定时任务执行 bash」功能，没传 envPolicy。恰好那之前旧的文本改写保险（R7 里讲）已经被清理掉了。于是这个入口跑的 `rm -rf`，全部是静默真删。没有报错、没有测试变红、没人知道，直到某个用户的文件找不回来。

**怎么修**：把可选变必填——类型上规定「不带 PATH 政策的 shell 入口编译不过」；再加一条单测盯住所有 spawn 站点。让「忘了装」从「静默通过」变成「造不出来」。

## R2 Apple Events 绕过——牢房里有部能叫外援的电话

**背景知识**：沙箱是个笼子。笼内程序删文件时，操作系统内核会检查「这个文件允许你删吗」（`unlinkAllowOnly` 规则）。这是删除守卫（delete_guard）的全部依仗：**检查的是笼内那个进程的动作**。

**问题在哪**：macOS 有个古老机制叫 Apple Events，相当于程序之间的对讲机——A 程序可以呼叫 B 程序「帮我干个活」。沙箱配置里 `localAccess` 默认是 `open`，这个开关顺带把对讲机也打开了（`allowAppleEvents: true`）。于是笼内程序可以呼叫**笼子外面的访达（Finder）**：「帮我把某某文件删了」。真正动手删的是访达，访达没被关在笼子里，内核检查的是访达的权限——畅通无阻。删除守卫从头到尾没被触发。

**打个比方**：囚犯确实出不了牢房，但牢房里有部电话，打给外面的朋友什么事都能办。

**事故剧本**：用户开了 delete_guard，以为工作区外的文件删不掉了。一段被注入的恶意提示让 agent 执行 `osascript -e 'tell application "Finder" to delete POSIX file "/Users/me/税务资料"'`——一行命令，守卫形同虚设。（我们已经管住了 mavis-trash 自己不走这条路，但管不住 agent 直接写这行命令。）

**怎么修（需拍板）**：要么开启删除守卫时强制把对讲机关掉（`localAccess` 收成 restricted），要么把 `allowAppleEvents` 从 `localAccess` 里拆出来单独控制。不修的话，delete_guard 的承诺书面上就要打折注明。

## R3 废纸篓无配额——只进不出的仓库必然爆仓

**背景知识**：「删除可恢复」的实现就是不真删，把文件**搬**进 `~/.Trash`。搬家不释放磁盘空间。

**问题在哪**：以前只有能被解析出来的 `rm` 走废纸篓，这次 shim 把覆盖面扩到了所有 `rm`。开发场景里最大宗的删除是什么？`rm -rf node_modules`——几万个文件、好几个 GB，一天可能清好几次。现在这些全部进废纸篓，而废纸篓**没有大小上限、没有过期清理、没有提醒**，任何机制都没有。

**打个比方**：公司规定所有丢弃的文件必须搬进档案室「以备恢复」，但档案室永不清理。第一周没事,第一个月过道就堆满了。

**事故剧本**：不需要剧本，这是确定性事件——正常使用一到两周，磁盘告急，用户查了半天发现 `~/.Trash` 里躺着 40 GB 的 node_modules 尸体，对产品的信任直接扣分。

**怎么修（需拍板）**：三选一或组合——① 设大小上限，超了自动清最老的；② 按天数过期；③ 超过阈值时提醒用户手动清。选哪个是产品决策。

## R4 契约复印件早于原件定稿——合同还在审批，复印件已经开工

**背景知识**：前端和运行时之间的通信接口，定义写在另一个仓库（weaver/idl）里，这是「合同原件」。我们仓库里那几万行 `generated/` 代码是用代码生成器从原件「复印」出来的，复印完手工提交进仓库。

**问题在哪**：合同原件的审批（IDL MR 13194）**还没走完**——我查了，状态是 `opened`，没合入。但 6284 已经把复印件提交并用起来了。审批过程中原件哪怕改一个字段名、一个编号，复印件就和原件对不上了。而且**没有任何自动比对**会发现——复印件是文件，不是每次 CI 现场生成的。

**打个比方**：房子还在改图纸，施工队已经按上周的图纸把承重墙砌好了。图纸最终版把门挪了 30 公分,没人会通知施工队。

**事故剧本**：IDL 评审人要求把某个枚举值 6/7 删掉（正好就是我们发现的那两个死状态）。IDL 改了、合了。6284 里的复印件还带着 6/7,前端按旧复印件解析、后端按新合同发数——错位 bug,而且查起来极痛苦，因为「生成代码」是所有人默认不会错的地方。

**怎么修**：流程卡死顺序——13194 先合入 → 在 6284 分支重跑 `pnpm gen:thrift` → 确认 diff 为空 → 才允许 6284 合入。最好再给 CI 加一步「现场重新生成，和提交的复印件比对必须一致」。

## R5 delete_guard 防「文件消失」，不防「内容消失」

**背景知识**：delete_guard 模式的规则是：笼内程序**到处都能写**（allowWrite = 整个磁盘），但**删除**（unlink——让文件从目录里除名）只允许在工作区内。

**问题在哪**：「让数据没了」有两种手法，守卫只防了一种。
① 把文件除名（unlink）——**被拦**。
② 把文件内容清空或覆写——比如 `echo > 论文.txt`，文件还在、名字还在，10 万字变 0 字节。在内核眼里这是「写入」，不是「删除」，而 delete_guard 模式写入全放行。
还有个组合技：先 `rm` 一个文件（进废纸篓，账面上「可恢复」），再覆写废纸篓里那份副本——恢复出来的是垃圾数据。

**打个比方**：保安规定「不许把书搬出图书馆」，但没规定不许把书里每一页涂黑。书还在架子上，内容没了。

**为什么只是 P1**：这是 6284 设计的模式语义本身（不是这次改出来的），而且「防覆写」在内核层很难表达（seatbelt 没有「只许新建不许覆写」这种规则）。真要防内容,该用 workspace_write 模式（写入也只限工作区）。

**怎么修**：至少把文档和 UI 文案写诚实：「delete_guard 防的是文件移除,不防内容覆写」。别让用户以为开了它数据就毁不掉。

## R6 shim 播种失败是 fail-open——门锁很牢，但装门失败时洞是敞着的

**背景知识**：两个术语。**fail-closed**：出故障时宁可停摆也不放行（银行金库门卡住 = 锁死）。**fail-open**：出故障时放行（商场安检机坏了 = 大家直接走）。你之前给「mavis-trash 脚本损坏」拍板的是 fail-closed。

**问题在哪**：假 `rm`（shim）是每次启动时「播种」写到磁盘上的。如果播种失败（磁盘满、目录权限坏），现在的代码只在日志里记一行（`host.ts:500-505`），一切照常。后果：PATH 指向的 shims 目录是空的，shell 找不到假 rm，**顺着 PATH 找到真的 `/bin/rm`**——所有本该进废纸篓的删除静默变真删。讽刺的是 shim 自己内部倒是 fail-closed 的：它找不到 mavis-trash 会拒绝执行并报错（`ensure-rm-shim.ts:58-62`）。锁本身很牢，装锁那步失败时却没人管。

**事故剧本**：某用户磁盘快满（恰好也是 R3 造成的！），启动时播种失败，日志里一行 `trash_seed_failed` 没人看见。之后一整个会话的删除全是真删。用户以为有保险，其实保险从启动那刻就没生效。

**怎么修**：把「shim 是否完好」并进 mavis-trash 已有的那套完整性检查门（byte-check，坏了就拒绝删除类命令并给修复指引）；或至少播种失败时升级成用户可见的告警，而不是一行日志。

## R7 双轨并存——新锁装好了，旧锁还挂着

**背景知识**：现在有两套机制同时在保护删除。旧的：permission 层认出 `rm -rf x` 就把命令文本改写成 `mavis-trash -rf x`（文本改写）。新的：PATH 上的假 rm（shim）。两条路殊途同归，最后都调 mavis-trash。保留旧的是刻意的——双保险，且符合「少改动」原则。

**问题在哪**：两条路必须**永远**对 mavis-trash 的调用方式保持兼容。将来有人给 mavis-trash 改参数（比如加个新 flag、改 `--` 的处理），改了 shim 这条路、忘了文本改写那条路（或反过来），就会出现「同一条 rm 命令，有时进废纸篓、有时报参数错误」的间歇性怪 bug——这类 bug 最难查。
另外它锁死了清理顺序：**删旧锁（rmRewrite）之前必须先做 R1（必填化）**。顺序反了，那些没穿线的门就连旧保险都没了，R1 的风险立刻从「将来时」变「现在时」。

**怎么修**：不用急修，记录两条纪律——① mavis-trash 参数面变更时两条路同测；② 清理 rmRewrite 的 MR 必须以 R1 落地为前置。

## R8 read_only 模式下的报错不说人话

**背景知识**：沙箱调成只读模式时，设计上连废纸篓都不给写权限（`effective-policy.ts:56-58`）——只读就不该删任何东西，这个设计本身是对的。

**问题在哪**：用户在只读沙箱里跑 `rm x`，实际发生的链条是：shim 接住 → 调 mavis-trash → mavis-trash 试着把文件 `mv` 进废纸篓 → **内核拒绝** → mavis-trash 只知道 mv 挂了，报 `mavis-trash: failed to trash 'x'`。用户读到的是「废纸篓坏了？」，而真相是「只读模式禁止删除」。

**打个比方**：你在图书馆想撕书，保安拦住你——但他不说「图书馆禁止撕书」，只说「你的手今天不好使」。

**为什么只是 P1**：安全上没有任何问题（该拦的拦住了），纯粹是报错归因错误，会引发用户困惑和无效排查（去检查废纸篓、重装、发工单）。

**怎么修**：让 mavis-trash 失败时能识别「被沙箱拒绝」这种情况（比如检测 `MAVIS_TRASH_FORCE_MV` 存在 + mv 被 EPERM 拒），改报「当前沙箱为只读模式，不允许删除」。

## 为什么不能"只对删除 close、其他 fail-open"

要"只对删除关门",前提是能回答**"这条命令会不会删东西"**——而这恰恰是整个 shim 设计要逃离的那件事。回顾一下我们为什么用 shim 而不是文本改写:`xargs rm`、`find -exec rm`、agent 自己写的脚本里的 `rm`、`perl unlink`……"删除"可以藏在任何看起来无害的命令里,解析器认得的形状永远是不完整的集合。

所以"非删除命令放行"在实现上只有一条路:解析命令文本,判断它不含删除,然后放它过去。而漏判的那批——藏在脚本和管道里的删除——**恰恰是最危险、最会漏的形状**。fail-open 放行"看起来不是删除"的命令,等于把洞精确地开在了防线最薄的地方:shim 不在了,这些命令里的 `rm` 会直接解析到 `/bin/rm`,静默地变成不可恢复的硬删。

## 其实有一半已经是"删除粒度"的 fail-closed

这套防线有两层,粒度不同:

- **shim 文件在、但 mavis-trash 坏了** → 只有 `rm` 失败。shim 脚本自己会检查 `mavis-trash` 是否可执行,不行就报错 `exit 1`("refusing to fall back to an unrecoverable delete"),其他命令完全正常。这层本来就是你说的"只对删除 close"。
- **shim 文件本身没了** → 这时 PATH 里已经没有任何东西能拦住 `rm` 了,bash 会直接查到 `/bin/rm`。管线里不存在一个"只拦删除"的位置——除非回去解析文本。`requiredExecutables` 管的就是这种情况,它是唯一剩下的闸门,所以只能整体关。

## 这个代价实际上很小

触发条件是异常态:shim 在**每次运行时启动**都会重新播种(幂等,还会修执行位),spawn 时的检查只在"启动播种就失败了"或"运行中有人删了/chmod 了 dataDir 里的 shim"时才会响。真触发时,报错信息带着具体路径和"重启重新播种"的指引,重启即愈;Windows 和无 dataDir 场景根本不装这个门。换来的是:环境已经损坏时,产品得到一个**响亮、可修复的可用性故障**,而不是一个**无声、不可逆的正确性故障**(bash 一切正常,但每次删除都是真删)。

## 如果想进一步缩小不可用窗口,有一个不破坏语义的折中

spawn 时发现 shim 缺失,**先尝试原地重新播种**(播种本来就是幂等的),重播成功就放行,失败才拒启。这样不可用窗口从"shim 丢了"缩小到"shim 丢了且 dataDir 不可写"——后者基本等于磁盘/权限已经坏了,bash 里的任何写操作也都会失败。实现上有一点层次成本(enforcement 在 agent-core,它刻意不知道 shim 里是什么,需要让 policy 带一个 repair 回调,或把自愈放在 local-runtime 侧的 spawn hook),但不大。
