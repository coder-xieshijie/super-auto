# Codex 近 30 天工作流分析

## 主要判断

你已经具备 Lauren 所强调的两项能力：用真实产物做反馈，以及把失败教训写进工具、代码和测试。欠缺更多发生在这些能力的衔接处：一个 agent 的完成报告、一个 UI 的显示值、一份被交叉审过的摘要，仍可能被当成下一步可用的完整事实。结果是你本人又接手检查运行结果、有效决策和最后产物。优化重点应是让执行者更早得到可复验的结果，同时降低协调层擅自添加目标、重复总结和增加流程节点的机会。

此判断来自下列三种不同强度的证据，不能混在一起：

1. **用户直接反馈。** 例如“dev 还是存在这个问题”“设置 xhigh 但平台仍是 Medium”“怎么 plan 删了这么多”。这是确实发生过的验收失败或预期不符。
2. **当时 assistant 的诊断与交付报告。** 例如漏传 effort、epoch 不一致、plan 有效细节丢失。报告在本次作为当时的可见结论保留；本次没有重新运行当时产品，也没有将它当成今日代码状态。
3. **本次推论。** 从多个样本归纳未来应强化哪类反馈和验证；不据此推算整体成功率、个人生产率或收益百分比。

`messages.jsonl` 保存可见 user/assistant/tool 记录及源行号；`replay_of` 标记同消息 ID 或同根、同时间、同角色、同文本的可证回放。短句没有跨全局去重。`session_meta.id` 用于区分 agent/fork，`session_meta.session_id` 在部分子 agent 文件中仍指向根任务。子 agent、已匹配 Agent Lord endpoint、system wrapper 分别标记；`human_candidate` 只是启发式候选，不能读作已确认是真人逐次输入。Imported/fork sources 即使保留同一个 session ID，也按源路径区分后再去重。

代表性深读覆盖 15 个根任务标识，合并成 [12 条主要任务链](deep-read.md)，完整短证据卡见 [case-cards.json](case-cards.json)。选取标准是跨阶段、用户明确纠正、可见后续结果，以及包含成功反馈环路；属于目的性选样，不是随机抽样。不能据此推算“多少百分比的会话失败”。旧会话复盘和研究会话里的转引话语不用于主题频率；复盘任务本人的直接指令仍可用于对应案例判断。

## 已经做得好的部分

**你会把抽象争论改成看实际产物。** 网页设计案例先做 Demo，用户指出跟随视野、空白生长、动画流畅度等具体行为，再比较 A/B，最后批准上线（C11）。这类对话轮数增加带来了可观察的决定，不能归类为无效往返。对后端功能也可以采用同样结构：先让 agent 跑一个完整用户路径，提供结果，用户只裁决真正有取舍的部分。

**你在持续减少无用流程。** Handoff 从双 Skill 设想收敛为单入口 reference，后来按当前需求移除；clarification 在用户判断效果差后当天要求删除（C01、C02）。所以“再加一套统一调度框架”与证据不符。更适合的是在已有 Agent Lord 的 operation、任务、恢复与产物记录里补必要的验证证据。

**你在主动区分要求、实现与交付。** Goal v2 澄清里由你决定旧预算迁移、grace 复用与模块边界；方案里仍有未决项时，末回答明确未视为你已同意（C06）。纯文档任务也多次明确不等于功能实现，不跟踪 CI。这些边界应继续保持。

**你能把实际教训沉淀为持久规则。** 语音任务把长音频切分、推测标注和阅读格式写回 Skill；Goal 队列回归通过移除 UI 的原始计数接口及补组合测试减少再次误用（C05、C12）。比起一律增长提示词，更值得保留的是这些绑定具体失败模式的改动。

## 优先优化的四个地方

### 1. 把真实路径验收移到第一次“完成”之前

C04 中配置与状态栏都是 xhigh，但真实新 Session 没有持久化 effort；C05 中组件/运行时测试已经很多，用户实际运行仍发现等待期间修改 Goal 的组合场景。两者都说明局部正确和实际路径正确存在距离。

每类能力先选一个最关键、能自动复验的垂直场景。Effort 可检查“启动→新建 Session→持久化→Provider 请求”；Goal 可检查“后台任务→创建→修改→后台结束→恢复”。如果真实 Windows/Provider 环境不可用，交付必须把这一步标为未验证，并保留可以直接运行的命令和证据入口。增加同类文本 review 轮次无法代替缺失的运行环境。

这与 Lauren 的产品验证思路直接相接，但你的场景包含 Runtime、IDL、跨平台和外部 Provider，截图或浏览器操作不足以独立完成验收；必须读取正确边界上的持久化和请求证据。

### 2. 限制协调者自行改写目标，验收实际终稿

C08 的用户要求是交叉 plan，协调者却额外加入精简导向，随后用精简稿替换整份方案。用户看见 875→279 行后才发现接口、装配和验收细节被压掉。要约束的不是“任何文档都要很长”，而是“协调者不能把自己临时增加的编辑偏好当成交付目标”。

保留一个权威 spec 和当前 plan；派发引用具体版本，携带本轮变化、职责和验收点。终稿检查比较仍有效的行为边界与实施细节是否保留，对象是最后实际提交的文件。不要把“审查员同意修订意见”当成“作者已经正确应用意见”。

C07 已给出用户自己的写作标准：开头 3–5 个重点，正文展开完整决定。它同时降低阅读成本和保留实施信息，适合继续复用。

### 3. 让恢复和交付状态减少人工接力

C03 中恢复能力缺失被解释成重新授权，用户重复指出已有权限；后来同任务续做成功并补了恢复策略。C10 中用户明确停掉未完成实现，后续审计也将优化列为待办。启动 operation、CLI 终态、代码可合入和功能完成必须继续分开。

进度面向用户只需回答：正在改变什么、现在阻塞哪项已定义条件、需要谁做什么、当前可检查的产物是什么。故障先区分可继续的同会话失败、需要外部环境、需要用户裁决；复用现有恢复状态，减少让人回到主会话说“继续”。对不可恢复/环境不足的状态，及时给出明确边界，避免把轮次增长当进展。

### 4. 把已确认的决定随着交付同步回权威资料

C09 中多个文档同时持有修复状态和发布步骤，旧指令与新要求冲突；C11 中正式设计已经上线，设计仓库仍写旧推荐/未决状态；C12 中用户还要问产物在哪。这里需要的通常是少量稳定入口，而非再增加一份汇总台账。

每一类事实指定一个当前维护位置：行为要求、实现计划、活跃问题、发布证据、设计决定。交付直接回写这个位置，其余索引只链接。原始讨论和历史验证可保留，但标明历史状态，不继续当成当前指令。文件链接、运行命令、基线 SHA 和验证边界应随最终产物一起交付。

## 不建议直接得出的结论

- 不建议“少用 AI/少用多 agent”：用户明确授权的交叉 review、实现与澄清有不同目的；应按反馈质量和独立性取舍。
- 不建议“所有任务都加端到端全套测试”：低影响文档或格式任务，必要的静态检查和回读即可；真实验收应集中在会改变用户行为的边界。
- 不建议“降低 effort 就会提速”：本次没有相同任务、模型、约束的对照实验；更不能从会话总跨度推断模型耗时。
- 不建议再次删除已移除 pipeline、再次修已修 bug：本报告总结失败模式和验收策略，当前实现是否仍缺失需要另行源码/运行验证。
