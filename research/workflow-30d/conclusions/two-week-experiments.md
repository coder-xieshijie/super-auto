# 两周小规模试验：复用现有能力，验证收益

这是供选择的改进方案，没有修改 Agent Lord、Agent Archon、Skill 或客户端配置。先做前两项，第三项在已有恢复机制确有缺口时做。每项绑定真实任务；样本不足就报告不足，不推算固定节省比例。

## 试验一：一个 owner 交付一条真实用户路径

**适合场景：**下一项类似 Goal 更新/恢复、模型 effort 传递或 sandbox 模式的行为变更。选择已有控制入口、可在隔离环境复现的任务。

1. owner 先固定仓库、目标分支、基线 SHA、相关用户决策；沿现有 CLI/RPC/UI 找到真实入口。使用现有任务/receipt 字段，不另造任务系统。
2. 保存一条能暴露旧行为的复现路径：输入、触发动作、持久状态、实际执行/输出、期望结果。需要异步等待或重启的，就实际走一次。若缺控制入口，先补最小入口。
3. owner 连续实现并保留上下文，按可审查、可回退的变化分 commit。第一次小切片就跑相关类型/布局/行为检查；不默认给每个 commit 启动一个 CLI。
4. 独立 reviewer 只承担本次主要风险，例如结算不重复、模式边界、跨进程字段传播；用最新固定 SHA 验证。未影响的检查不反复重跑。
5. 交付附真实运行证据和远端状态。区分本地检查、CI、remote head、MR opened/merged；不以一张通过截图覆盖其他失败。docs-only 遵循既有文档检查策略。

**观察：**首次可复现结果时间、首次有效修改时间、用户补充重复事实次数、运行验收后发现的问题、review 有效缺陷、集成返工、可得的模型用量。时间是任务墙钟跨度，人工审查分钟只有实际记录才填写。

**通过条件：**agent 能从同一入口独立复现和复验；验收能抓住至少一个已知回归，或能证明本任务前后行为差异；交付不会再要求用户重做同一验收。没有现成故障时不伪造“抓住缺陷”。

## 试验二：把一条已确认决策完整传过三个阶段

**适合场景：**设计 → 实现 → review，或跨 Codex/MCode/Claude 接续。

只将以下信息放进已有任务正文或引用文件，不让每一阶段复制长篇历史：

```text
用户结果：从哪个入口做什么，应看到什么。
代码身份：repo / requested target / base SHA / worktree / 当前 head。
已确认决定：最多 3–5 条，链接用户决定或当前 spec；更改需新证据。
允许的推进范围：本次已授权到哪一步；仍需决定的事项。
验证入口：实际命令或操作路径、预期观察、适用环境。
当前状态：完成的证据、剩余问题、下一步；关联 task/operation/endpoint。
```

机器可从现有字段读到的内容自动取，不要求用户重复填表。开始写入和创建 MR 前核对目标分支。跨仓 IDL 同时写清开发基线与合入顺序，不混为一个门槛。下游依赖上游实现时，使用可追溯的上游交付 SHA；独立 worktree 保持隔离。

**观察：**是否重新追问已定边界、是否重开已否决方案、是否用了旧 target/旧配置、交接后重复探索了多少同一事实、最终 MR 与指定对象是否一致。

**通过条件：**三阶段对同一决定的解释一致；review 的新增问题有明确新证据；错误分支在修改/发 MR 前被发现。发现冲突仍保留人工判断，不强行压成“零提问”。

## 试验三：恢复一个既有任务，而非再派一份副本

**前提：**先验证当前 Agent Lord/宿主已有哪些唤醒、锁、claim、恢复和幂等能力。历史中出现 provider 错误不证明今天缺少恢复实现。

在可回退任务中分别验证：明确可重试的临时 provider 错误；子 agent 完成后 owner 继续；已授权范围内的阶段转换。沿原 task、endpoint、worktree、head 接续，回读 operation 和交付结果。记录重试上限和最终停止原因；用户取消、凭证失效、需要新产品决策等走各自状态，不混成重试。

**通过条件：**不靠用户发送“继续”完成已授权动作，没有重复副作用，没有把 cancelled 改写成 provider 故障，没有仅因 operation succeeded 就宣称已交付。任何一项失败都先修对应窄路径，再扩大自动化范围。

## 两周如何安排

| 时间 | 动作 | 留下的证据 |
| --- | --- | --- |
| 前 2 天 | 从新任务挑 1 条真实路径、核对现有能力与验收入口 | 任务短说明、基线 SHA、复现记录 |
| 第 3–6 天 | 连续 owner + 细 commit + 一次针对性 review，执行试验一 | 相关检查、运行证据、返工原因 |
| 第 7–10 天 | 相近任务保留原流程作参照，同时试验决策继承 | 工作量/风险差异、交接遗漏、用量 |
| 第 11–14 天 | 有需要才做恢复试验；比较结果并删掉无收益环节 | 通过与失败案例、保留/撤销决定 |

任务没有可比性时，不做前后百分比。让同一方案在两三种实际任务上表现稳定，再决定推广。无需新增一个“优化所有流程”的长期项目。

## 建议每项任务只补记这些数据

| 数据 | 口径 |
| --- | --- |
| logical task | 明确用户结果；关联多端 session、operation、PR，不按它们各算一项 |
| 时间 | 开始、首次复现、首次有效修改、达到约定交付状态；另列等待外部依赖 |
| 人工参与 | 产品决定、学习理解、审查判断、重复事实、修补错误、催继续分开 |
| 返工 | 需求改变、错误基线、漏运行路径、结构检查、集成错配、provider 中断分开 |
| 质量 | 真实验收、独立 review 的有效发现、交付后回归/回滚；缺失写 unknown |
| 成本 | 可获取的 token/账单/人工审查记录；不同 provider 口径不硬合并 |

这些字段用于小样本试验。当前历史语料没有一致的人工审查计时、token 账单和生产缺陷回流，无法可靠计算本月整体 ROI。
