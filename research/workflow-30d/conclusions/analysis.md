# 你的近 30 天 Agent 工作流，与 Lauren 方法论的对照

分析窗口：**2026-08-25 17:33 至 2026-09-24 17:33，北京时间**。依据本机 Codex、MCode、Claude Code 的原始会话、Agent Lord 操作记录，以及此前保存的 Lauren 两段视频、原帖和外部分析。当前代码、MR 和生产状态没有在本次历史研究中重新验证。

## 最值得先做的五件事

1. **把真实产品验收前移到实现开始。** Goal 等待/更新、effort 首轮传递、默认生产装配、TUI 附件、视频布局，多次都是用户实际使用或后期整合才揭示遗漏。先让一个 agent 能沿真实入口复现、修改、复验，再扩大并行。这是与你最相关的 Lauren 经验。
2. **把你已确认的决定变成跨阶段稳定输入。** 你最有价值的工作是确定产品语义、删多余设计、判断体验；重复解释四档权限、IDL 开发顺序、目标分支，则可以通过现有任务字段、简短行为矩阵和机器核对减少。
3. **按可独立验证的行为切任务，让整合者提前工作。** 细 commit 有利于 review；独立 CLI 要有足够独立的上下文与交付边界。下游应能消费上游真实交付代码，默认生产链路应贯穿迁移过程。
4. **少加通用流程，优先收紧已发生错误的代码路径和检查入口。** 你已经删除效果差的 clarification/handoff，并把 schema 漂移等问题变为门禁。继续这条路线；每次增加规则前，先检查能否复用现有能力、消除重复状态、修正执行入口。
5. **用完整交付、返工和人工负担衡量收益。** PR、session、operation 和 tool-call 都不足以代表产出。先用两周小样本记录真实验收、重复协调、有效 review 发现与成本，再决定 worker 数、TDD 范围、模型 effort 和自动化程度。

我的总体判断是：**你已具备复杂任务的组织、裁决和审查能力；下一阶段的收益更可能来自让 agent 自己看到并验证最终结果，以及让任务交接继承正确事实。** 这是跨多条任务链得到的判断，不是全体任务的效率统计或因果实验结论。

## 优先级三：分工依据依赖与可验收性

M03 同时有三种用户反馈：“tickets 需要这么多吗”“这都读一小时了”“只要不依赖，不能都派出去吗”。它们指向任务分解的质量：独立工作应该并行；强耦合的小任务拆开会重复读上下文，把接口问题推给整合阶段。

M09 给出了具体机制：assembly worker 在旧冻结基线上实现，又因 `owned_paths` 与架构验收文件不一致返工；移除旧 stub 后，检查再次受到旧基线接口影响。此前的 [Goal v2 单次审计](../../lauren/workflow/evidence-notes.md)也指出 ready set 没有固定并发上限，而依赖链、下游基线和串行模型往返更突出。后者是特定运行样本，不能外推整月。

建议在下一项中等任务做对照：一个 owner 保持上下文，按可审查变化分 commit；可独立验证的模块和需要独立判断的 review 并行。复杂跨仓任务仍可多 worker，但满足：

- 每个 worker 的输出能被独立核验，职责包含实现所必需的契约测试。
- 下游启动时拿到可追溯的上游交付 SHA，协调者负责保持分支与整合边界。
- 整合者提前维护最薄的真实生产链路，逐步接入模块。
- 只对新 head 和受影响范围重验；不要把旧 head 的 PASS 转移到新 head。

现有记录无法给出“最佳 agent 数”或三种模型的能力排名：任务风险、提示、effort、上下文、宿主和序列化方式都不同。用同类任务的小规模对照，判断重复输入、有效发现、返工和完成时间。

## 优先级五：把流程改进做成小实验，及时删掉无收益部分

本月你已这样做过：

- D01：明确授权 clarification 后，直接评价效果差并要求删除 pipeline；最后报告创建了删除 PR。授权并不能证明该流程有效，删除是合理反馈。
- D02：先把 handoff 从复杂多 Skill 设计缩为按需 reference，后又因不需要而要求移除；末报告仍明确未跑真实多 CLI 流程。
- M13：把 schema round-trip、文档链接和 Skill 体积问题转入检查，报告保留了未全绿边界。
- D11：用 A/B Demo 选择真实动效，之后发现设计库仍保留旧状态，再补归档。实际可见原型有助于做决定，最终选择应及时回流当前事实入口。

后续改进按 Lauren 的层次尝试：先消除重复状态与错误接口，随后用确定性检查，最后才用规则/Skill 处理需要判断的部分。例如 Goal 用户可见队列与计数统一派生，可能比再增加一条“记得过滤内部消息”的提示更可靠。具体能否简化代码，仍需对当前源码和测试验证，不能仅凭历史报告就动手删。

任务类型也应决定流程：事实查询和纯文档沿最短路径；局部修复采用连续 owner 和受影响验证；跨模块行为变更采用稳定契约与独立复核；探索/审美先用原型形成反馈。C06 的学习提问、C15 的图形对照、D11 的设计选择，都是有意投入，不能为追求低“干预率”而消除。
