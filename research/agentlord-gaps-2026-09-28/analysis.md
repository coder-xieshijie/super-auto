## 当前已经有的能力

plan-to-implement 的主要过程：已有方案 → planner 拆模块 → 就绪模块并行实现 → 所有模块交付 → 单独 integrator 整合/检查/创建 MR → 核对证据后结束。

已有依赖判断、独立 worktree、持久状态、进程与写入保护、恢复、真实提交核对、MR 身份和最终 SHA 核验。不能把这些说成需要从零新增。readySet 没有固定 worker 数上限。

## 先补三项

### 1. 下游开工时取得真正的上游代码

当前 `plan.ts:432` 中模块执行使用 repository 的原始 head；`readySet` 根据依赖 delivered 解锁，没有在这一步组成含上游提交的新基线。依赖完成状态不等于下游工作区已包含它。

例：A 写接口，B 使用接口。B 应拿到 A 的实际提交，再实现调用；仅给接口文字、仍从旧代码启动，会把不一致延后。

建议复用现有 worktree 和提交核验，形成可追溯的下游起点。具体 merge/cherry-pick 与路径规则需另做设计，不在本次直接决定实现。开发可使用已验证 feature SHA，不必等上游合入；保留 Archon/IDL 现有跨仓顺序。

### 2. 在最后整合前，持续检查能否组合运行

当前 `plan.ts:959` 明确要求所有模块交付后才开始 final integration。可先保留该最终交付角色，补充早期组合验证：第一个可运行场景出现后，检查默认装配、实际依赖和用户入口；以后接入一部分就核对受影响路径。

例：界面、保存、后台执行分别通过，不证明用户点击后一定能开始执行。应尽早跑通这条完整路径。

不要直接取消单写保护或再加万能协调 agent；先用现有任务和隔离工作区证明这种检查能提早检出历史问题。

### 3. 给 agent 一套可以自己执行的产品验收

当前有 verification 字符串和绑定 SHA 的 receipt；runtime 核对结构，不负责执行测试或判断场景是否足够。这是明确的职责边界。

需要各业务仓库补齐启动、实际操作、观察结果、清理的现成入口。优先复用已有 CLI、测试和日志，选少量高频用户行为。

例如：新建 session 后核对实际请求 effort；后台工作期间更新 Goal 后核对续跑；跨模块变更检查默认生产装配。历史问题不是当前仍有 bug 的声明。

Agent Lord 的作用是派发验收、保留版本和真实证据、缺项时明确未验；具体行为脚本由业务项目维护。

## 随后补两项

### 4. 让交付后的反馈回到同一项需求

当前计划流程负责到已核验的 opened MR，integrator 明确不合并；closed run 不能继续执行，后续用新 task/run。这不应被误称为没有恢复能力。

对于用户要求继续到可合并/合入的任务，可以复用现有新任务/恢复能力，将 review、CI 和基线变化关联回原需求和 MR，继续处理到授权终点。连续的是责任和产物，允许更换 session；接续前保证旧写入者不能继续写。

如果用户只要求开 MR，就在那里结束；不默认扩大到合并或发布。所有 docs-only MR 继续执行用户的短路径，不主动查/等 CI。

### 5. 按任务大小选择流程，测清楚再调并发

当前计划流程即使只有一个模块，也要求独立 integrator；这对有整合需求的任务有价值，小范围任务可考虑通过已经存在的普通 task 路径完成，保持必要独立验证。用户点名某 pipeline 时仍按约定执行，不能自行省略角色。

先记录每项需求的实际工作、等待上游、验证、人工审查、返工时间。已有并发无固定上限，暂不把增加 worker 或加入统一限额作为首要改造。只有出现环境/CI/审查拥堵证据后，再调整对应资源的放行。

**先让下游拿到上游代码 → 提早组合运行 → agent 自己完成真实验收 → 接续交付反馈 → 按数据删减流程与调整并发。**
