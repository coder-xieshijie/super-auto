# 两周试验与最小改造顺序

这是研究后建议，尚未实施；不要求新建平台、不预设更换模型。本方案扩展 [9 月 24 日试验建议](../../workflow-30d/conclusions/two-week-experiments.md)，加入 owner 连续性、队列与交付核销。

## 先明确完成边界

每个需求用现有 issue/task/receipt 表达：

1. 用户可观察的目标、明确不做的范围、验收样例和关键反例。
2. repo / target / 当前 base / owner / 实际工作区；真依赖及上游产物位置。
3. 可执行的真实验收入口；缺失环境如何标记，不能用 mock PASS 代替。
4. 当前任务授权的终点：研究、实现、本地验收、PR、合入或发布；继承已有授权，避免重复确认。
5. 结果证据位置和候选 head；可自动继续的失败、需人决定的事项和停止条件。

字段已存在就复用；不要再加第二份 coverage/ledger。如果已有 receipt 只能表达局部完成，先用最小补充说明试验，不立即设计新 schema。

## 阶段一：确认现有能力（约 1–2 天）

挑一个局部行为需求，一个有真实依赖的跨模块需求。运行前先查现有 CLI/测试/运行入口，不凭旧档案宣称能力缺失。

| 能力 | 最小验证 | 通过标准 |
|---|---|---|
| 可运行环境 | owner 启动、驱动、观察一个真实入口 | 不依赖人临时补手工操作；证据留存 |
| 基线继承 | 下游读上游真实交付 SHA；用可控错误基线验证检测 | 旧 checkout 不会被误判为依赖已满足 |
| 连续 owner | PR 修改意见和检查失败返回同一任务 | 保留决定、代码身份与有效检查；无重复 PR |
| 恢复 | 一次可控临时进程/provider 故障后接续 | 原目标和产物不丢失；可用现有 recovery 完成 |
| 停止 | 明确停止后检查待执行操作 | 停止生效；晚到回报不会触发新写入 |
| 交付核对 | 对照真实 PR 状态和任务报告 | PR opened、merge-ready、merged、发布状态不混用 |

不要向生产制造故障；使用已有测试或隔离环境。发现当前已有能力满足就记为通过，不新增重复组件。

## 阶段二：试连续交付组合（约 3–7 天）

从日常真实任务取小样本，按任务类型/风险/规模分层；在资源允许时分配可比任务到现有流程与试验流程，不强行重复实现同一业务变更。

试验流程仅改变三件事：

- 同一 owner 跟到已授权终点，独立 reviewer 负责不同视角；明确 reviewer 的有效发现由谁修正。
- 写代码前落实至少一条真实验收路径；不能运行时先解决环境或准确报告边界。
- 已授权的 CI/review/retry 反馈自动接续，减少“继续”和人工搬运。

两组保留相同最终质量门槛，保持模型、effort、预算尽量一致；试验改变验证的时点与接续方式。这阶段只评价三项变化的组合效果，不能单独归因于 owner、验收或接续；之后再逐项消融。owner 连续性不要求同一进程永久运行，换 session 时先核对旧执行停止或失去写权限，再接续同一需求和产物。小样本只形成方向性判断，不做统计显著或固定提速承诺。

## 阶段三：调并发，不改其它变量（约 8–12 天）

只对可独立完成的需求提高在途数量；例如从 2 项试到 3–4 项只是试验水位，不是推荐最优值。需要真实上游代码的任务不能为了占满槽位在旧基线上实现；已验证的 feature SHA 可以满足开发依赖，无需等到 merged。Archon/IDL 继续遵守“开发用配套 feature、Archon 合入前 IDL 先合入再生成”的现有顺序。

记录三类队列：实现前等待、可审后等待、验收/CI/合入等待。若增加并发后完成数没有上升，而最老在途任务、人工 review 等待或返工上升，回到前一个水位，把配额用于完成现有任务。

同一需求内部并行另开对照：单 owner vs owner 加独立调查/验证，固定总预算和相似范围。不要用跨需求并发的改善证明所有任务都需要更多协作角色。

## 阶段四：删减一个流程组件（约 13–14 天）

借鉴 pstack #419：选一个怀疑重复的检查/角色/提示，在已有代表任务及历史已知 bug 上做保留/移除对照。一次只删一个；真实发现减少或关键缺陷漏检就恢复。保留已证明有效的契约测试、真实入口和法定/项目必要验证。

所有 docs-only MR 走用户既定短路径，完成必要文档检查、commit/push 与 MR 创建或更新即交付，不主动查询或等待 CI；不作为“复杂需求降风险验证”的实验样本。

## 最小测量表

| 字段 | 记录方式 |
|---|---|
| task / 类型 / 风险 / 范围 | 逻辑需求为单位，多 session/PR 关联同一 task |
| ready、开始、首个真实验证、可审、merge、发布 | 时间戳；未到阶段留空并说明 |
| 等待原因 | 上游、环境、agent、CI、人工决策、审查、发布 |
| 人工分钟 | 决策、协调、审查、修补、学习分开；并发 wall time 不相加工时 |
| 结果 | 达标、部分、取消、接管、失败；纳入全部样本 |
| 质量与成本 | 真实验收、漏检、返工、回滚、费用/可得 token；未知保留未知 |
| 版本证据 | base/head、命令或动作、环境、结果、证据路径 |

自动提取能取得的字段，人工只补无法观察的时间/判断；不要让测量本身变成日常行政负担。预算、暂停阈值和扩容观察窗口在开始前按真实容量记下，不预设一个通用金额或次数。样本很少时先展示逐项时间和样本量，p90 不作稳定估计。

## 继续扩大投入的条件

相近任务中，完整需求交付数或周期改善，且人工分钟、返工/回归、每需求成本没有不可接受的恶化；未完成和取消样本也被计入。若只是 PR 变多、提交变碎、review 排队变长，应撤销对应扩容或角色配置。

线上回归和维护需要后续观察；两周只能看到短期反馈。最终决定应写明样本数、差异与未观测部分，再选择下一项最小改造。
