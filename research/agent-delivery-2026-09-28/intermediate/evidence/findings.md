# Agent 交付研究：效果、并发与人工瓶颈的证据边界

检索日：2026-09-28。范围：原始实验、研究机构发布、论文全文；不研究 Lauren 本人，不重新测量用户的工作流。

## 对交付方案最有用的五个判断

1. **按需求完成与人工投入评价自动化。** PR 数、代码量、token、评论量都是活动指标，无法单独说明需求已完成。至少同时看验收通过的需求数、端到端时间、人工操作分钟、后续返工和总成本。
2. **先区分两种并发。** 多个独立需求各由一个 agent 执行，与多个 agent 共同解决同一个需求，是不同实验。多 agent 协调论文主要测后者，不能据此否定前者，也不能把金融任务的多 agent 增益当代码交付增益。
3. **把需求变成可执行的验收依据，才有长时自治的支点。** MirrorCode 展示了大任务能力，但它有明确参照程序、可见样例、隐藏端到端测试。这类清晰任务可以持续自动纠错；模糊产品意图仍要先消除歧义。
4. **自动化审查要衡量有效发现与返工，不应把评论数量当质量。** agent 指挥、CI 通知、审查意见混在同一 PR 里，直接数 review 容易失真。
5. **按整合、验证和审查的消化能力放行工作。** 让已开始的需求完成、缩短反馈路径，再增加并发；对已有等待和冲突建立背压。此项是工程推导，需要在用户仓库试验，不是本次测得的最优并发数。

## 1. METR：2025 的慢 19% 不能直接描述今天

[2025 RCT 原文](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)：16 位熟悉其大型开源仓库的开发者，246 个真实任务，逐任务随机允许/禁止 AI；2025 年 2–6 月数据，主要使用 Cursor 与 Claude 3.5/3.7。AI 条件完成时间增加 19%；该设置下有因果解释，但样本、经验、工具、任务类型限制外推。

[2026-02-24 更新](https://metr.org/blog/2026-02-24-uplift-update/)：57 人、143 仓库、800 多任务；原参与者子集时间变化估计为 −18%（区间 −38% 至 +9%），新参与者 −4%（−15% 至 +9%）。研究者明确认为信号不可靠：拒绝无 AI 工作的人/任务被排除，报酬下降，并发 agent 令工时计量失真。不能把这些估计写成“当前提速已证实”。

**迁移到本用户：** 把“同一时段开了几条 session”与“人工花了多少分钟”分开。比较按任务难度分层的完整交付结果，保留未完成、退出、人工接管任务，避免只统计成功样本。主观感觉与客观交付都记录，不让任一替代另一个。

原始资料：[2025](../../raw/evidence/metr-2025.txt)、[2026](../../raw/evidence/metr-2026.txt)。

## 2. DORA：代码生成的收益取决于整个交付系统

[2025 报告入口](https://dora.dev/research/2025/dora-report/)及[2026 官方解释](https://dora.dev/insights/balancing-ai-tensions/)指出，2025 的 AI 采用与更高吞吐、同时更高不稳定性相关。不要混用 2024 的负吞吐结果。它是调查/观察关联，不能推出给某团队安装 AI 就会带来相同比例变化。

[能力模型原始问卷](https://dora.dev/ai/capabilities-model/questions/)列出：明确 AI 使用立场、健康数据体系、AI 可访问内部信息、版本控制、小批次、用户导向、优质内部平台。AI 采用由依赖、信任、习惯使用等自报变量构成，并非 agent 数量或 token。问卷还表明部分质量/效果变量是主观测量。

**迁移：** agent 应能自己找到项目资料、启动环境、构建、验收、定位失败、产出可回滚变更。细分需求仍需保持一个可理解的完成边界。[小批次](https://dora.dev/capabilities/working-in-small-batches/)和[WIP](https://dora.dev/capabilities/wip-limits/)提供方法依据；本次仅读取报告入口、官方解释和问卷，未把受表单限制的完整能力报告标为已精读。

原始资料：[官方解释](../../raw/evidence/dora-2026.txt)、[问卷](../../raw/evidence/dora-questions.txt)、[小批次](../../raw/evidence/dora-small-batches.txt)、[WIP](../../raw/evidence/dora-wip.txt)。

## 3. 多 agent 的收益取决于任务结构；新版比旧博客更谨慎

[Towards a Science of Scaling Agent Systems v3](https://arxiv.org/html/2512.08296v3)，2026-04-08：260 个配置、6 个 benchmark、5 种架构、3 个模型家族，固定工具/提示/计算预算比较。旧 Google 博客是 180 配置、4 个 benchmark，不能混引。

v3 新增的 SWE-bench Verified 子集上，各多 agent 架构平均相对单 agent 约下降 2%–15%；但仅抽样 20 题，单格区间约 ±20 个百分点，不能据此宣称所有代码多 agent 都更差。金融任务的 +80.8% 与顺序规划的 −70% 是不同任务的相对变化。

回归交叉验证 R² 为 0.373（任务能力指标版本 0.413）。87% 是域内保留配置的最佳架构选择率，不是“87% 新工业任务可准确预测”。17.2×/4.4× 是 trace 级错误引起的额外计算放大，不能称缺陷率放大；论文另区分任务级失败比例。部分工具/协调特征经聚类稳健推断不再显著。

**迁移：** 同一任务保持一个代码责任人；有条件并行独立调查、独立模块和验证。存在真依赖的下游等待真实上游产物。增加 worker 前对同类任务对比 wall time、token、整合返工，而非设通用人数公式。

原文：[HTML](../../raw/evidence/scaling-v3.html)，[解析全文](scaling-v3-fulltext.txt)，重点 §4、§5、附录 F。Jina 错抓为 SVG 的返回也保留但不作证据。

## 4. MirrorCode：明确行为参照使长任务成为可持续纠错过程

[MirrorCode v2](https://arxiv.org/html/2606.30182v2)，2026-07-17：25 个程序，读取文档、调用原程序、查看样例，但不能读源码；以隐藏测试验证行为复刻。最高模型总体得分 56%，不是“56% 工业需求能自治”。gotree 示例约 16,000 行，14 小时、251 美元、2,000/2,001 测试通过。作者估计人工 2–17 周，不是同条件完整人类对照。

有单次运行达 19 天/2,600 美元，不能把最佳案例成本推广到全部任务。目标程序经过可测量性筛选；这些结果支持“精确定义任务能做得很长”，尚不证明发现产品需求、部署运维和长期维护也自治。

**迁移：** 需求准备优先产出接口样例、原行为、可重复故障与反例；让独立验收检查最终行为。对于模糊需求，先用原型换取反馈。不能只给 agent 更多运行时间而不提供进度判据。

原始资料：[v1](../../raw/evidence/mirrorcode.txt)、[v2 HTML](../../raw/evidence/mirrorcode-v2.html)、[v2 解析全文](mirrorcode-v2-fulltext.txt)。

## 5. SWE-Bench Pro 系列：验收本身也需要验证

[原始 Pro v2](https://arxiv.org/html/2509.16941v2)：1,865 题、41 仓库，包含公开、保留、商业集合。它改善传统短任务覆盖，但单题测试通过与生产交付之间仍有距离。

[OpenAI 2026-07-08 审计](https://openai.com/index/separating-signal-from-noise-coding-evaluations/)：在 731 题公开集，先筛出 286 个疑似问题，再做 agent 深审与每题 5 位工程师检查。两条路径标出 200/249 个有问题任务；约 30% 是研究方估计，筛查设计并非全量独立人工穷尽审计。问题包括过窄测试、漏写需求、覆盖不足、描述误导；已撤回早期推荐。

[2026-09-16 Pro Verified v2](https://arxiv.org/html/2609.08149v2)：保持 731 题、修正 102 题，并阻止从历史提交/隐藏文件/网络取得答案。阻止本次观察到的绕过，不代表证明不存在所有绕过。

**迁移：** 验收从用户行为要求出发，检查“正确的其它实现是否被误拒”和“只通过现有测试的错误实现能否蒙混过关”。 agent 写的测试不能单独证明自身实现；保留独立验收与真实场景。基准隔离隐藏答案的约束不应原样用于实际开发：真实开发依然应该访问合法的项目历史和文档。

原始资料：[Pro](../../raw/evidence/swe-pro-v2.txt)、[审计](../../raw/evidence/swe-audit.txt)、[Verified](../../raw/evidence/swe-verified.html)。

## 6. 真实 PR：审查协作有数据，长期维护净成本仍缺证据

[When AI Teammates Meet Code Review](https://arxiv.org/html/2602.19441v1)，MSR 2026：AIDev v3（2025-11 访问），33,596 个 agent PR、2,807 个热门仓库。合并与 reviewer 参与正相关，与改动大、force push 负相关；模型按仓库聚类，仍是观察研究。不能据此说增加评论会使合并成功，也不能把不同 agent 合并率当模型优劣排名。数据不区分纯自治与人工触发。

有 PR 创建至合并/关闭的日历耗时；**这不是人工 review 分钟，也不是纯排队时间**。关闭未合并也进入“decision”。revert 被作者明确视为不完整质量代理，未作为主要结果。

[These Aren't the Reviews You're Looking For](https://arxiv.org/html/2605.02273v1)，EASE 2026：在同仓对比中，可观察人类参与比例接近（约 30%）；区别主要在纯人工审查、混合互动和指挥 agent 的结构。人工评论里存在大量“修复/运行/更新”的调度命令；无评论也不能说明无人审阅。该研究不评估代码质量、审查有效性，未控制大小/难度等混淆因素。全文一处 mixed-review 百分比与分母不一致，本报告不使用该数。

[Early Adoption of Agentic Coding Tools](https://arxiv.org/html/2607.14037v1)：虽发布于 2026-07，实际窗口为 **2025-05 至 2025-07**，25,264 PR/2,361 仓库；不少流程由同一人审查与修改。它描述早期采用，不能据此断言今日普遍孤立协作或工业自治成熟度。

**证据缺口：** 本轮未找到能普遍量化“每个 agent PR 增加多少审查工时/长期维护成本”的可靠因果研究，也没有本用户的该项实测。应跟踪首轮可审查率、人工修补分钟、无效审查发现率、合并后返工；不要把网络里的倍数当预算常数。

## 建议给整体研究的试验设计（推导，未实施）

### 先把时间拆开

每项需求记录：ready → 开始 → 首次验收通过 → 首次可审查 → 合并 → 发布/真实使用验证。阻塞分别标记等待上游、环境、agent、人工决策、审查、CI/发布。人工投入单独记录，多个并发任务的 wall time 不求和冒充工时。记录任务类型、复杂度、风险和外部依赖，以免自动化组只分到简单任务。

### 两种并发分别试验

- **跨需求并发：** 在独立低风险需求上比较少量不同 WIP 水位，保留 review/集成队列等待数据。评价每周验收通过且被接受的需求数和 p50/p90 交付时间。
- **需求内协作：** 固定模型和预算，比较单责任 agent 与责任 agent 加独立调查/验证。仅在总成本或交付质量改善时保留额外角色。
- **人类瓶颈：** 区分产品决定、安全授权、专业判断与“继续/搬运/解释已定规则”。只自动化最后一类以及已充分验证的例行判定。审查材料自动收集到版本/测试/场景证据，避免人重复还原过程。

### 背压与完成定义

从队列视角，若审查/集成吞吐不变而在途需求持续增加，等待会累积；这是理论推导，未测得用户最优 WIP。不要以让每个 agent 都忙为目标。处理能力不足时把新执行配额转给已有变更的复现、验收、冲突消解，优先结束老任务。

建议主指标：验收且被接受的需求数 / 人工小时；同时报告需求类型，避免把它变成个人绩效排名。配套护栏：缺陷逃逸/回滚/返工率、p90 交付时间、每项总成本、人工接管率。PR 数作为分解后的产物计数，不能替代需求数。
