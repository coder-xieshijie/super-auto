## 最重要的新增判断

**这段教程补充了如何把角色、交接产物和流程入口配置成可复用组件。它没有补齐工业交付的状态核对、真实验收与合入闭环。** 对用户现有 Agent Lord 工作流，最值得借鉴的是交接文件更明确、角色配置按项目覆写、阻塞状态集中可见；没有证据支持再加一套执行平台或预设更多 agent 角色。

与 [既有综合报告](../../conclusions/report.md) 相比，下列 4 点更具体：

1. **工作流入口可以很薄。** 教程描述的 TS 入口主要是读取 SKILL.md、合并用户输入、注册 slash command；后续修改流程通常只改 skill。它说明流程无需专门建一个庞大 DSL，但也意味着流程主要由模型遵循文本执行，不能据此声称拥有确定性的状态机保证。[13:37–14:18](https://www.youtube.com/watch?v=y1TXjYlRjBU&t=817s)，L343–366。
2. **中间产物是明确的接力点。** 每步的输入、输出和字段写在 contracts 文档，放入任务目录交给下一角色。这比口头“上一步完成了”更便于复用和检查；但视频没有证明 schema 验证、原子写入、版本身份或不完整产物拒收。[11:28–11:42](https://www.youtube.com/watch?v=y1TXjYlRjBU&t=688s)，L291–295；[14:45–15:12](https://www.youtube.com/watch?v=y1TXjYlRjBU&t=885s)，L376–389。
3. **短任务 worker 可以结束，需求责任不能随之消失。** 视频把 auto-exit 用于无需继续等待输入或审核的角色。可迁移为让一次性研究 worker 完成后退出、保留主任务的持续 owner；不能把所有编码 worker 都在首次产出后退出设为默认。[12:30–12:48](https://www.youtube.com/watch?v=y1TXjYlRjBU&t=750s)，L315–324。
4. **UI 重连和故障恢复是两件事。** 作者明确把保持运行状态的条件限定为 herdr 后台服务不重启。关闭窗口再回来证明的最多是界面脱离不终止现有执行，不是崩溃、机器重启、模型中断后的 durable recovery。[19:01–19:50](https://www.youtube.com/watch?v=y1TXjYlRjBU&t=1141s)，L489–508。

## 哪些话不能直接当作已证实结论

- **“契约让沟通不会遗漏数据”**：L643–648（25:21–25:39）是作者的意图。字段文档与样例不能代替校验器；下游仍要检查必填信息、实际路径和版本。
- **“质量可控”“比单 agent 更专业”**：L110–119、L554–561 是作者评价，没有相同需求、相同预算、同评分标准的对照，不足以推导多智能体净收益。
- **“完整覆盖开发迭代”**：L631–638 的范围是本地 demo；字幕没有 Git PR 创建/更新、当前 SHA CI 证据、merge queue、生产风险控制或发布后验证。
- **“关闭窗口仍运行”**：L500–508 明确依赖后台服务存活，不是持久化恢复测试。
- **“全部功能完整”**：作者在 [30:08–30:31](https://www.youtube.com/watch?v=y1TXjYlRjBU&t=1808s)，L758–766，自己指出车模型不完整、视觉较差、规则未详细定义。这个例子恰好表明多个角色和多轮设计评审后仍会留下产品质量缺口。
- **“不要把 agent 定义放 GitHub”**：L166–170 是教程的一般提醒，不宜上升为禁用版本管理。可复用且无秘密的角色/流程定义需要可审计版本；敏感信息另按实际内容处理。本轮不改用户配置或发布文件。

## 与用户历史工作流的具体关系

这里沿用既有 [30 天报告](../../../workflow-30d/conclusions/analysis.md) 和本轮综合报告中的案例归纳；未重新审查现有实现，以下是试验方向。

| 既有历史证据 | 教程提供的具体补充 | 应保留的工业要求 |
|---|---|---|
| M09 下游 assembly 基于冻结旧版本；已有 fixed SHA/receipt 习惯 | 交接产物明确输入、输出与任务目录 | receipt 关联真实上游 SHA、repo/target、验证命令；下游先核实产物身份再使用。不能只收到摘要就开工 |
| D03/M05 恢复与 C13 跨端接续 | 所有 worker 的阻塞/权限状态集中展示，UI 可脱离 | 区分活着、等待输入、实际推进和可恢复；复用 Agent Lord 已有 operation/claim/fence/recovery。前端重连不代替故障演练 |
| M03 任务过细、重复读取 | 精炼角色定义；并行只读研究先产出结构化材料 | 耦合实现维持完整 owner，避免每个小步骤都新开外部 agent；研究并发成功不代表实现也适合相同拆法 |
| D01/D02 不必要 clarification/handoff | 一个轻入口执行现有流程；定义可逐步迭代 | 不新增重复派发和问卷；继承用户授权与已定决策。为新增角色设可测保留条件 |
| D05 Goal 组合路径、D04 effort 首轮请求、M10 默认装配 | 教程本地 URL 强调交付可运行作品 | 进一步要求 agent 走真实 UI/CLI/API 路径并检查副作用；仅设计 critic 或局部 tests 仍不充分 |

## 推荐增量：优先接入已有能力

1. **只补缺失的交接字段。** 先查看现有 receipt 是否已有任务、repo、base/head、产物和验证结果；有就复用。确有历史失败才增加字段及可执行校验，不再创建平行账本。
2. **让状态面板暴露行动信息。** 每个任务至少能区分运行、等待、阻塞和完成；被卡住时显示阻塞原因与谁能处理。若已有等价能力，就用它减少人工检查，不再造 UI。
3. **按项目给角色少量差异。** 从已有默认角色出发，覆写真实必要的验证命令/工具/模型；不用为一个新项目复制完整角色库。
4. **先测一条小闭环。** 用一项带真实验收的小需求比较当前流程与加入结构化交接后的结果，检查实际人工分钟、等待、返工和成本。演示中的 5 或 7 个角色不作为目标。

不建议由本片推出：安装 pi-herdr-agents、替换 Agent Lord、增加固定七角色团队、让无上限 review 循环负责质量，或把配置文件存在当成流程被强制执行。真正的新价值是**轻入口、明确交接、集中可见状态和角色复用的配置方式**。
