# 两段视频补充：哪些值得借鉴，哪些不宜照搬

分析日：2026-09-28。结合此前 [工业交付报告](../conclusions/report.md) 与截至 9 月 24 日的用户工作流档案。完整读取两片字幕；另外抽看 Factory 数据图和 Pi 游戏成品画面，未逐帧观看或人工听校全片。视频下载失败记录、字幕、元信息、作者示例源码和中间分析均保留。

## 结论：Factory 对你的增量更大，Pi 教程适合借鉴轻量配置

最值得吸收的五点：

1. **高耦合需求可以串行实现，同时并行研究与审查。** “更多 agent”与“更多同时写代码的 agent”应分开。跨独立需求继续并发，同一迁移/功能内则比较串行写入是否减少返工。
2. **实现前定义验收依据。** 不只是列测试命令，还要写出用户可见行为、反例、真实入口，并让每个实现切片对应这些要求。
3. **交接是可核对的事实包。** 完成了什么、没完成什么、实际命令和退出码、已发现问题，连同真实 base/head 交给下一阶段。问题没有处理或明确处置，就不能凭一句“完成”继续。
4. **策略可以放在 Skill，执行保障要靠可靠操作。** 灵活拆分任务与选择修复策略可以交给模型；身份核对、未解决问题门禁、状态恢复不能只依赖提示。
5. **为真正的验证与修复预留容量。** 快速生成代码后仍需要运行应用、检查结果和处理反馈。验收失败应进入同一需求的修复循环，减少人手动发“再改一下”。

以上是结合两片与已有证据的建议，不是两套系统在你项目里已得到验证的收益。

## 视频一：Pi Agent / pi-herdr-agents 实战

[畅的科技工坊，2026-09-19，约 31:18](https://www.youtube.com/watch?v=y1TXjYlRjBU)。中文字幕来源标为 authored or unspecified，不能确认已由作者校订。[完整字幕](raw/y1TXjYlRjBU/transcript/browser-export.txt) / [逐段分析](intermediate/pi-video-notes.md)。

### 可借鉴的三处

**薄入口与可复用角色。** 教程把角色定义、流程 Skill 和命令入口分开。入口只加载流程与用户输入；通用角色复用，项目只补差异。对你已有的 Agent Lord，值得借鉴的是减少重复定义和流程入口的额外逻辑，未必需要另加一套 Pi 平台。[08:19](https://www.youtube.com/watch?v=y1TXjYlRjBU&t=499s)、[25:45](https://www.youtube.com/watch?v=y1TXjYlRjBU&t=1545s)

**明确中间产物。** 用任务目录和 contracts 规定上一步输出、下一步输入，比跨对话转述更容易追踪。你的增量应是核对现有 receipt 缺什么，补足实际路径、版本和证据；不要重新引入被你取消的 coverage 账本。[14:45](https://www.youtube.com/watch?v=y1TXjYlRjBU&t=885s)

**集中看阻塞原因。** 多个 agent 的等待、输入请求与产物能在一个工作区看见，可减少逐窗口巡查。但作者明确要求后台服务仍活着，关闭 UI 再打开不等于崩溃/重启恢复。[19:01–19:50](https://www.youtube.com/watch?v=y1TXjYlRjBU&t=1141s)

### 源码核查比演示更有价值

已固定作者示例仓库到 `8ebf2fc6c3ed53268f77b9b2427a288b52af10c8`，保存对应目录的 19 个文件。它主要是角色定义、两个工作流 Skill 和命令注入器；**不是完整运行引擎**。流程引用的 `check_build.py`、`qa_playtest.py`、`serve_game.py` 没有随该示例提供，查过仓库树也未找到这些脚本，不能把它当作已可复现的完整交付流水线。[固定源码](https://github.com/melodylife/changworkshop_project_sharing/tree/8ebf2fc6c3ed53268f77b9b2427a288b52af10c8/pi_agent_subagent_workflow)、[核查明细](intermediate/pi-source-check.md)

这不证明作者本机没有脚本；它说明公开配置写了某个验证步骤，不等于你下载后就拥有该验证能力。工业改造时先跑通命令，再讨论角色数量。

游戏配置另有 **core/player/input/ui 四模块并行写入**，预先规定接口和各自文件，再集中集成。这比旅行只读并发更接近代码协作；但本轮未运行验证，共享目录的写入边界靠提示约束，不能证明机械隔离或任意耦合需求都适合这种拆法。

源码还提供了有界返工的思路：设计审查最多两轮后对未收敛的严重问题升级。但 QA 对“只剩 P1 / UNVERIFIED”的终止规则存在歧义。适合借鉴的是明确修复预算、失败处置与终点，不把“两轮”当通用最佳值，也不把文本规则当运行时已强制执行。

### 不宜直接照搬

- 三个 researcher 的并行是只读调研；它没有验证共享仓库的并发写入。
- 七角色、多个 critic 并不自动带来完整成品。约 30:11 的抽样画面确实展示了赛车场景，字幕同时承认车模型和视觉不足；没有验证全部关卡、音乐和操作流程。[30:08](https://www.youtube.com/watch?v=y1TXjYlRjBU&t=1808s)
- 本地 URL 证明不了 PR、CI、合并与生产交付；contracts 文档也不等于 schema 被机器校验。
- 视频里全局 agents 路径前后不一致；不按字幕直接修改配置。本轮未安装插件或执行示例。

## 视频二：Factory 的 Missions 架构

[Luke Alvoeiro / AI Engineer，2026-05-06，约 18:30](https://www.youtube.com/watch?v=ow1we5PzK-o)。以下描述的是这场演讲的设计，不冒称为 9 月 Factory 产品当前实现。[完整英文自动字幕](raw/ow1we5PzK-o/transcript/browser-export.txt) / [逐段分析](intermediate/factory-video-notes.md) / [会议官方整理](https://ai.engineer/talks/ow1we5PzK-o-production-multi-agent-architecture)。

### 1. 最重要的反例：同 Mission 串行写入

讲者描述：一次只运行一个顶层 worker 或 validator，内部代码搜索、API 调研、review 可以并行。他们在并行实现时遇到冲突、重复工作和架构不一致，因此采用这个策略；进一步并行仍被列为开放问题。[09:17–10:25](https://www.youtube.com/watch?v=ow1we5PzK-o&t=557s)、[17:38](https://www.youtube.com/watch?v=ow1we5PzK-o&t=1058s)

对你最直接的意义：**不要把“能并行就并行”实现为所有 ready worker 同时改同一个紧耦合系统。** Goal/IDL/装配类任务可以先以一个连续 owner 管住需求，再顺序实现可验收切片，把研究和独立审查并行；独立需求、明确接口的独立模块仍可走并行方案。

这里只对真实共享写入与语义依赖排序。IDL feature 已提供可验证接口时即可支持 Archon 开发；Archon 合入前才要求 IDL 先合入、重新生成对齐，保留你既定的跨仓顺序。

这不是“软件开发只能串行”的证明。视频没有提供串行/并行的统一样本、耗时和缺陷对照；迁移到你这里仍要比较总周期与整合返工。

### 2. 验收契约先于实现，并分两种验证

Factory 先定义断言，再把断言分配到功能切片；在里程碑做代码/测试审查与真实用户流程验证。这样可以让判断依据来自需求，减少实现与自写测试共同遗漏同一要求。[06:34–08:06](https://www.youtube.com/watch?v=ow1we5PzK-o&t=394s)

例如你的 Goal 行为，可以在现有 Plan 的验收节直接写：

| 行为要求 | 验证入口 | 必须观察到的结果 |
|---|---|---|
| 后台任务期间更新 Goal，后台结束后继续处理更新后的目标 | 真实 UI/API 创建、更新并等待 | 持久状态、触发与用户可见结果一致 |
| 新 Session 的 effort 生效 | 创建 Session 并发出首轮请求 | 展示值、持久值和实际 outbound 字段一致 |
| 默认生产装配启用能力 | 正常启动路径，无测试注入 | 真实入口可用且走到预期模块 |

这是基于历史案例构造的建议，不代表当前代码仍有这些问题；不新增独立 coverage 文档。具体需要哪些场景和命令，以当前仓库为准。

讲者“实现后写测试只会确认决定”的表述过强。后写测试仍能找 bug；更稳妥的借鉴是**验收依据独立于实现，并覆盖真实行为**，不要求所有任务一律全套 TDD。

### 3. Fresh context 需要稳定事实支撑

worker 可以从新的上下文实现下一切片，但必须读到规格、当前代码和结构化交接。handoff 包含未完成项、命令/退出码与已发现问题；调度侧要处理问题，不能只保存它们。[05:13](https://www.youtube.com/watch?v=ow1we5PzK-o&t=313s)、[08:19–09:00](https://www.youtube.com/watch?v=ow1we5PzK-o&t=499s)

对你，这补充了“持续 owner”的实现边界：责任和任务身份连续，执行 session 可以替换。下一执行者需要此前已定的 sandbox、IDL、target 等约束；不能为了清空上下文把决定也清掉。

### 4. 薄确定性层与可调整策略并存

讲者把拆分和失败处理策略放在 prompts/skills，少量确定性逻辑负责记账、运行验证和阻断未处理的 handoff 问题。[14:48–15:47](https://www.youtube.com/watch?v=ow1we5PzK-o&t=888s)

这与前一轮 Stripe 的确定性编排可以互补：不要把所有语义选择硬编码，也不要把 claim、代码身份和推进门禁全交给自然语言。对 Agent Lord，更适合保留可靠控制能力，让具体计划/修复策略按任务调整；“700 行文本”不是应追求的规模指标。

### 5. 你给的 13:53：重点是成本、验证与修复

13:53 位于 Slack clone 单例的数据讲解末尾，正在讲 prompt caching。抽看 13:17 的原片图表：

| 图表项目 | 画面读数 | 可得到的结论 |
|---|---|---|
| 总运行时长 | 16.5 小时 | 长时任务实例；不是需求通用耗时 |
| 实现 / 验证 | 约 60.5% / 37.2% 时间 | 验证占可观容量，不能只优化模型写码速度 |
| 总 tokens / cache read | 778.5M / 744.9M | 总 token 含大量缓存读取；不能按普通输入价格估总成本 |
| 测试行占比 / 语句覆盖率 | 52.5% / 89.25% | 该例的测试规模；不能独立证明质量，也不是应追求配额 |

讲者称示例需验证后追加修复。应预留自动修复路径，不让每次失败都退回用户当调度员。[13:06–13:57](https://www.youtube.com/watch?v=ow1we5PzK-o&t=786s)

07:48 关于“多数时间等真实验证”的概括与这里单例 60.5% 实现，不宜合并成一个全体任务分布。16 天是讲者自报最长运行、30 天是预期；五人从十条工作流到三十条是设想，不能写成实证三倍提速。

## 和 Lauren 放在一起，怎样选

| 场景 | 建议组织方式 | 来源提供的启发 |
|---|---|---|
| 多个独立需求/PR | 每项持续 owner、隔离环境、滚动放行 | Lauren 的并发交付与合入准备 |
| 同一强耦合功能或迁移 | 先试顺序实现切片，研究/review 并行；每阶段验收实际组合 | Factory 的 feature 串行模式 |
| 可重复、明确输入输出的业务流程 | 薄入口、角色复用、明确产物契约 | Pi 教程的配置结构 |
| 当前验证入口缺失 | 先打通真实运行和观察，再扩角色或并发 | 三者共同强调验证，但保障程度不同 |

推荐下一轮只补三个地方：**现有 Plan 的行为验收、receipt 的未完成/问题处置、强耦合任务的串行写入对照**。保留已有跨模型 review、claim/recovery 和用户授权边界。docs-only MR 继续走必要文档检查、提交/push 与 MR 完成即交付的短路径。

本次不建议替换 Agent Lord、安装新插件，或增加固定七角色流水线。先验证这些具体机制能否减少你重复解释、催推进和亲自发现接线遗漏的时间。

Factory 官方整理页与自动字幕并存，页内部分摘要锚点与原片发言不齐，正文采用原片字幕时间。公开示例的当前固定源码晚于视频发布日期，是补充审计，不等于还原录制时环境。所有行业收益和产品能力均按相应时点与证据范围解释。
