# Goal 收口的最终回复与交付卡片：核心决策与约束

本文记录本次修复的核心决策与约束，作为方案设计、开发实现和代码审查的共同依据，也用于人工决策核对与对外说明。

具体实现可以调整，但必须满足这些约定；需要改变约定时，应先明确影响并重新确认。本文描述的是目标要求，不代表实现已完成或验证已通过。

**目的：** Goal 收口时，用户不用追问，就能在对话里读到本次任务做成了什么、交付文件在哪，并能直接打开模型声明的交付文件；续跑、最终校验和过程折叠不再吞掉这些内容。Goal 是否完成仍以 Host 结算为准。

对应缺陷 #7125906243，跟 10 月 2 日版本。术语（完成提案、Goal 完成、最终回复、完成摘要、交付标记、交付卡片、卡片提升、过程区）按仓库根目录 [CONTEXT.md](../../../../CONTEXT.md) 的“Goal 收口与交付”一节使用。

## 本次最核心的决定

1. **已接纳的完成提案不再立即结束本轮。** 模型在同一轮写一次最终回复，然后本轮结束，Host 照常结算和验证。最终回复写在验证之前，不宣称验证已通过。
2. **完成提案被接纳后，本轮的工具调用全部被拦下，包括 `update_goal`。** 这一轮只剩写最终回复一步；两次都没有回复时按正常结束结算，不因缺最终回复把 Goal 判为失败。
3. **Goal 完成时，Desktop 把这条 Goal 消息过程区里的交付卡片提到结果区，正文固定取最终回复。** 只移动卡片，不移动正文；同一文件只显示一张卡片。
4. **交付只认正文里的交付标记。** 不新增交付字段，不自动发现未声明的文件；产物面板、会话资产索引、IM 和 TUI 的代码都不改。
5. **严格控制影响范围。** 10 月 2 日封板的核心需求不是 Goal；改动只落在 Goal 自己的工具、提示词、工具执行前检查、complete 专用的空回复重试，以及 Desktop 的 Goal 消息展示，普通对话的行为不变。

## 完整决策与约束

### 1. 修复范围：A、B 两条路径

| 路径 | 现象 | 案例 |
| --- | --- | --- |
| A | 前一轮已经输出了报告或交付卡片，续跑校验后提交完成，报告和卡片被收进过程区，外露的只剩一句确认 | 6CPQVW0J |
| B | 模型先提交完成、打算之后再交付，本轮随即结束，最终回复没有生成，用户只看到过程句 | MG9FB8I4、MCT-202609-42YHZXRZ |

- B 包括 TUI 自动化模式（build-mode 状态栏加 `MCODE_TUI_RESULT_PATH`）和 headless（`requireAnswer`）把 Goal 完成的那一轮判成 `EMPTY_RESPONSE`、显示 `× Error Runtime completed without a final assistant response.`、状态栏 `state=fail`。
- 用户反馈文档第 8 项按 B 类场景验收，不要求证明它与 B 是同一条内部轨迹。
- 被接纳的 `blocked` 提案和 stale 拒绝保持现状：仍立即结束本轮。

### 2. 完成提案之后的这一轮：只写最终回复

**不结束本轮。** `update_goal(status=complete)` 被接纳后，本轮继续。工具返回和工具说明要求模型立即写最终回复：

- 写给用户，说明做成了什么、交付文件在哪、必要时怎么用；
- 为交付文件写交付标记，并写出文件路径；
- 不再调用任何工具；
- 不宣称验证已经通过。

**拦下后续工具调用。** 同一轮完成提案被接纳后，之后的每个工具调用都不执行，包括再次调用 `update_goal`（任何模式）；调用方收到的原因要求它不再调用工具、直接写最终回复。已接纳的提案保持不变，不会被随后的 `blocked` 或第二次 `complete` 覆盖。这项拦截放在 Goal 自己的工具执行前检查里，只在“本轮已接纳完成提案”时生效，不改通用工具循环。

**没有回复时的兜底。** 完成提案之后，模型的回复既没有文字、也没有工具调用时，重试一次。仍然没有回复，或者被拦下后直到本轮结束都没有写出文字，本轮按正常结束结算，完成提案照常进入验证；不走失败结算，不因此把 Goal 变成暂停、失败或其他状态。这种情况下用户看到的与现状相同：没有最终回复，TUI 自动化仍可能报 `EMPTY_RESPONSE`。这项重试只对“已接纳的 complete”生效，不在全局装配通用的空回复恢复。

**提示词。** 客户端实际使用的 Goal 提示词是 `@mavis/goal` 中的 TS 常量（`packages/agent-modules/goal/src/continuation.ts` 等），随客户端发布，远端 Prompt 已停用。与收口相关的指令改在这些常量里，与本节行为一致，不再要求“提交完成后直接停止”；`packages/local-runtime-v2/assets/agents/workflow/goal/` 下对应的 `.md` 同步成相同措辞。两者之间原有的其他差异不在本次对齐。

**被打断的这一轮。** `complete` 不再写“本轮有意结束”的标记（`terminates_turn`），`blocked` 与 stale 照旧写。完成提案之后、最终回复之前被打断的一轮，按其他被打断的 Goal 轮处理，例如可以显示“继续”。

### 3. Host 结算与验证保持现状

- Goal 的最终状态以 Host 结算为准。本轮结束后照常验证：`met` 为 `complete(verifier_met)`；`not_met` 保持 `active` 并续跑；验证模式为 `none` 时直接 `complete(worker_proposal)`。
- verifier 的判定口径不改，不新增“用户是否看到交付”之类的检查。
- `not_met` 续跑后，前一次最终回复与本条 Goal 消息的其他内容一起进入过程区，新一轮结束时再写新的最终回复。
- 写最终回复的阶段被中断或失败，或者结算时 Goal 已被暂停、修改、清除或预算用尽，都沿用现有结算规则，已接纳的完成提案不进入验证：

| 情况 | 结果 |
| --- | --- |
| 用户停止 | Goal 暂停为 `paused(user_requested)`；用户恢复后，模型重新检查并重新提交完成 |
| 应用重启或崩溃 | 提案丢失；Goal 仍为 `active`，启动恢复开一轮新的续跑 |
| 模型服务出错 | 按现有失败分类：限流或额度用完为 `usage_limited`，安全拒绝为 `blocked(safety_policy)`，其余为 `paused(infra_retryable)` |
| 结算时预算用尽（包括最终回复的消耗使其用尽） | 按现有预算规则：`budget_limited`，另排一轮预算总结 |

- 结算里的失败分类和预算规则不改。
- “立即发送”沿用现有规则，不做 Goal 特判。

### 4. Desktop：正文取最终回复，交付卡片提到结果区

以下规则只作用于 Goal 消息；普通消息的正文选择和折叠不变。

**正文选择。** Goal 消息里，成功的 `update_goal(status=complete)` 调用之后还有文字时，外露的正文固定取最后一段文字，也就是最终回复；不再与 complete 之前的文字比较长度。complete 之前的文字进入过程区。complete 之后没有文字的消息（例如旧历史）按原规则展示。

**卡片提升。**

- 触发：Goal 结算为 `complete` 时，也就是过程区折叠的时候。不以工具调用成功为条件；验证中、`not_met` 续跑、暂停等状态下不提升。
- 范围：这条 Goal 消息过程区里的全部交付卡片，包括更早各轮输出的。
- 去重：同一文件（规范化路径相同）只显示一张；正文里已有的不再重复。用户展开过程区时，已提升的卡片不在过程区里再显示一次。
- 只移动卡片，不移动正文。更早轮次的完整报告正文仍在过程区。
- 写在代码块和行内代码里的标记不算交付，不出卡片。
- 不采用“含交付标记的正文优先当正文”这类规则。

**其他展示面。**

- 完成标记“目标已完成 用时 …”和 Goal 横幅不变。
- 刷新、重启后从历史重建的对话，正文选择和卡片提升与实时展示一致。
- 右侧产物面板列出本次交付的文件，同一文件只列一次。现有读取已包含过程区里的标记，也按路径去重，不改面板代码。

### 5. TUI 与 headless

- 最终回复作为完成提案之后的助手回复显示；交付标记沿用现有的 `Created  file ↗` 行。
- 自动化模式和 headless 下，有最终回复的 Goal 完成轮不再是 `EMPTY_RESPONSE`、`× Error` 或 `state=fail`；完成后照常出现 `✓ Goal complete`。
- TUI 代码不改；上述结果由第 2 节的最终回复产生。

### 6. 交付声明：只认交付标记

- 声明交付文件的唯一方式是正文里的交付标记（`<deliver-assets>`、`<media/>`）。不新增 `deliverables` 或其他交付字段，不扫描工作区自动发现文件。
- 模型没写交付标记时不出卡片；最终回复仍要写出文件路径。
- 完成摘要（`update_goal` 的 `summary`）用途不变：交给 verifier，不展示给用户，不能代替最终回复。

### 7. 非目标

- `blocked` 提案与 stale 拒绝的行为。
- IM 出站、Fork、v1 local-runtime、Remote Control、Cloud 会话的展示与交付。
- 新增交付字段、自动发现未声明的文件。
- verifier 的判定口径；结算里的失败分类。
- 产物面板、会话资产索引、IM、TUI 的代码。
- 把更早轮次的完整报告正文默认展开。
- 对齐 Goal 提示词 `.md` 与 TS 常量之间原有的其他差异。
- 通用工具循环；全局装配通用的空回复恢复。
- 发布 Apollo Prompt。

### 8. 硬约束

- **影响范围：** 改动限于 Goal 工具（实现、说明、返回）、Goal 提示词常量及对应 `.md`、Goal 专用的工具执行前检查、只对已接纳 complete 生效的空回复重试、Desktop 中 Goal 消息的正文选择与卡片提升，以及随之更新的测试和文档。普通对话的行为不变。
- **平台：** 产品逻辑兼容 macOS 与 Windows。Windows 路径（盘符、反斜杠、含空格）的交付标记解析与去重用单测覆盖。
- **时间：** 10 月 2 日 12:00 前合入 `preview_train`。

### 9. 已接受的代价

- 更早轮次的长报告正文默认留在过程区，只有其中的交付卡片被提升。
- 模型没写交付标记时没有卡片。
- `not_met` 后，前一次最终回复进入过程区。
- 连续几轮 `not_met` 且最终回复逐字相同时，触发已有的重复回复暂停 `paused(no_progress_after_completion_claim)`。
- 写最终回复的阶段遇到用户停止、重启或模型服务出错时，完成提案作废，需要恢复后重新收尾。
- 最终回复消耗 token；接近预算上限的 Goal 可能因此在结算时进入 `budget_limited`，而不是进入验证。
- 完成提案之后模型两次都没有回复时，没有最终回复，与现状相同。
