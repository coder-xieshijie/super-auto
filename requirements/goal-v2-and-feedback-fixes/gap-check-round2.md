**当前仍需修正的问题**

**1. S07 的迟到回执场景存在执行顺序闭环**

类型：不可执行  
位置：verify S07 步骤 3–4、G1；连带 S32。  
问题：场景要求新 Goal 完成后才释放旧请求的结束帧，但旧请求未结束可能正是新 Goal 无法开始的原因。  
依据：S07 先要求“poll 新 Goal 到终态”，之后才“放行暂扣的响应”；指定分支的 Electron 说明明确，运行中清除 Goal 后“这一轮还在运行”。当前 `lifecycle.ts::deleteGoal` 也没有直接中止正在执行的模型请求。  
影响：保留在途请求的实现可能一直等不到步骤 3；如果迁移实现清理时取消连接，之后释放 HTTP 响应也不保证回执进入 runtime，因此正确实现仍可能没有所要求的丢弃记录。  
建议：把“新 Goal 已创建”和“新 Goal 已完成”分开，不以完成作为释放旧请求的前提。进一步区分 HTTP 响应延迟和 runtime 回执延迟：需要确定证明删除后回执处置时，用可控回执屏障或 B07 集成测试保证回执确实到达；Electron 场景验证删除、新建及用量隔离。

**2. S32 仍不能证明按活动时间选取证据，也不能证明完全只读**

类型：判别力不足  
位置：spec §3.6；verify S32、M14。  
问题：新增检查点没有构造能区分错误时间筛选的样本，业务状态比较也仍不完整。  
依据：S32 只说明回执“晚于旧 Goal 的创建与删除”，没有要求旧 Goal 创建时间落在窗口外；只比较“updated_at 与状态”。spec 要求“按请求与回执的活动时间选取近期证据”“不改变业务状态”。  
影响：按 Goal 创建时间筛选的实现，只要 S07 刚运行过，仍能通过；诊断修改 token、请求账本或其他不推进 epoch 的字段，也能通过。  
建议：增加固定时间样本：Goal 创建于窗口外、回执发生于窗口内，另有窗口外回执作为排除对照。生成前后比较完整业务持久数据，或用集成测试断言诊断路径没有业务写入；M14 保留用于检查常驻服务。

**3. 第 2 项的非默认 runtime 行为没有被明确纳入验收**

类型：缺少覆盖  
位置：spec §2、§5.4；verify R07、R97、RG2、B05。  
问题：仅要求第 2 项的三个真实场景通过，不能覆盖本次重新实现的工具拦截和空回复边界。  
依据：RG2 要求迁移时运行 S02、S03，最终运行“全部场景”；第 2 项实际只有 S01–S03，完成后连续调用 `update_goal`、空回复重试、两次空回复正常结算等在其 B2 中。本需求 B05 没有完整接入这些检查。  
影响：实现正常最终回复，但漏掉第二次 `update_goal` 的拦截、错误覆盖已接纳提案，或空回复重试漏计工作请求，仍可能通过现有场景。  
建议：明确纳入第 2 项 B2 中仍适用的检查及相关机械要求，并要求通过；预算相关预期按本 spec §5 覆盖。另补“最终回复为空、重试前恰好用尽次数”的固定请求序列，断言工作／收尾分类、次数和结算结果。

**4. 计量补测仍缺少完整投影与已知失败 attempt 的数值判别**

类型：缺少覆盖  
位置：spec §4.1、§4.6；verify S05、R35、B18。  
问题：现有补充仍允许部分消费面漏字段，以及失败 attempt 的已知 usage 漏记。  
依据：spec 点名 Desktop、TUI、CLI、API、事件、`get_goal` 的一致投影；R35 已漏列 CLI，S03 主要比较请求总数，B18 只覆盖 TUI。S05 的首次 attempt 返回 500，但未构造非零已知 usage。  
影响：CLI 或事件不投影预占／未知占用，`get_goal` 只返回总数，或者只计成功 attempt 的 token，都可能通过。  
建议：增加固定账本样本，逐一检查各消费面的适用字段，包括非零历史、工作、收尾、预占、未知占用和 `usageIncomplete`；明确预期值。为 retry 单独构造两次 attempt 均有已知用量的样本，断言逻辑请求数为 1、token 为两次用量之和。无法由 HTTP 替身可靠构造的部分列入集成测试。

**5. `/retry` 的额度受限路径和 Desktop 的失败反馈仍缺检查**

类型：缺少覆盖  
位置：spec §6、§7、§13；verify R93、S17、S20、S30、S35、S36。  
问题：`/retry` 只在 paused 状态验证；Desktop 恢复失败主要检查最终状态，没有明确检查本次失败向用户显示。  
依据：R93 要求“paused 或 usage_limited 时 `/retry` 等同 `/goal resume`”，S30 只构造 `paused(infra_retryable)`；S36 使用的仍是 `/goal resume`。spec §7 要求仍受限时“入口上显示失败”，S17／S20／S35 只要求回到受限状态和横幅提示。  
影响：只修复 paused 的 `/retry`，或 Desktop 点击后失败但只留下“额度恢复后自动继续”，都可能通过。  
建议：给 TUI 增加 `usage_limited → /retry` 的仍失败及恢复成功两条路径；Desktop 场景明确断言本次恢复失败的可见反馈，并与自动恢复安排仍保留分别检查。

**6. 定时恢复的错误排除矩阵没有覆盖完整**

类型：缺少覆盖  
位置：spec §7；verify R61、S21b、S30、G1。  
问题：明确排除的错误类型中，多项没有对应场景或替代测试。  
依据：spec 排除 HTTP 429、50111、50150、未知 BYOK 错误、50113 和上游 500；R61 没列 50111、50150、未知 BYOK，引用场景也没有持续上游 500。S05 的一次可重试 500 随后成功，不能证明终止后的恢复策略。  
影响：实现只排除 429／50113，对其他错误错误安排自动恢复，仍可能通过。  
建议：补参数化错误矩阵，分别断言失败分类、没有自动恢复安排、推进可控时钟后没有新 Goal Turn。429 样本明确携带 `Retry-After`，以检出把普通限流重试时间误当额度重置时间的实现。

**7. 通知场景没有覆盖“同一 Goal 会话里的普通 Turn”**

类型：缺少覆盖  
位置：spec §12；verify R88、S29、B12。  
问题：S29 的普通消息发在另一个会话，无法证明 Goal 会话内的非 Goal Turn 通知保持不变。  
依据：spec 特别包含“Goal 会话里补充消息的那一轮”；S29 步骤 3 则在首页新发普通消息。  
影响：按“Session 存在 Goal”整体屏蔽 Turn 通知的错误实现，可以同时满足会话 A 仅有完成通知、另一普通会话仍有通知。  
建议：在同一个有 Goal 的会话内执行可确认未绑定 Goal 的普通 Turn，离开会话后检查其通知仍产生，同时检查 Goal Turn 静默。补通知开关关闭、前台抑制的参数化检查，证明复用既有策略。

**9. S23 新增了横幅显示预算上限的要求**

类型：越出 spec

**10. 依赖任务的类型与归属交叉矩阵仍不完整**
