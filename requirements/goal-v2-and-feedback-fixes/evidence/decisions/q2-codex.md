选择：**D 选 1；E 选 2。** 已核对 spec、verify 和当前 HEAD `e71be11629` 的相关实现。

**D：额度到点自动恢复，也结束 `user-stop` 队列暂停。**

- spec §6 明确要求自动恢复真实落地；§7、R57 规定等待期间对 **Goal 本身** 的暂停、编辑、替换、删除或完成会取消旧目标的自动恢复。停止普通 Turn 没有暂停 `usage_limited` 的 Goal，因此自动恢复承诺仍然有效。
- 接受其明确代价：解除的是会话级暂停，排在 Goal 前面的用户消息也会按 FIFO 继续执行。这需要作为产品行为说明，不能描述为“只恢复 Goal”。
- 选 2 却不给等待原因，会直接违反 §6、R52；新增“队列已暂停”的等待状态虽然能消除无声卡住，但改变了到点自动继续的承诺，也超出了本期沿用现有等待文案、不新增暂停或受阻原因展示的范围，需要修改 spec，不能算现有要求已满足。

**E：用户显式恢复 Goal 时，也结束 `turn-final-failure` 队列暂停。**

- §6、R52/R53 对恢复落地的要求没有按队列暂停来源设置例外。用户已经明确要求继续，仍让 continuation 永久停在失败留下的暂停后面，与恢复按钮和 `/goal resume` 的含义不符。
- 解除队列暂停不代表认定原错误已解决，也不代表重放失败的 Turn；恢复后若仍然失败，应显示本次失败、保留真实状态和既有错误分类，不无限重试。积压消息继续按 FIFO 执行的代价同样需要接受。
- **选 1 并列为“已知限制”，就是放宽本次验收**：披露限制不能使违反 §6 的状态变成合格。选 3 需要新增可见等待原因及明确的解除入口，属于另一个需要调整 spec 的产品方案，本次不推荐。

落实这两个选择时，应保留 pause token 和 Goal epoch 的并发保护，以及权限、问卷、依赖门禁；解除暂停失败必须如实报告。E 的选择仅针对**显式恢复**，不据此扩大到自动清除失败暂停。
