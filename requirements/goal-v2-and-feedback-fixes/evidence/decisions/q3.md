## 决定 F：前台 Turn 最终失败后，active 的 Goal 停在队列暂停之后
集成测试（`packages/local-runtime-v2/test/integration/goal/goal-resume-after-user-stop.integration.test.ts`，final-failure 用例）观察到的情况：Goal Turn 运行中，用户按默认方式发了补充消息，消息排进队列。Goal Turn 结束后，它的 continuation 排在这条消息后面。补充消息那一轮最终失败（例如 provider 报错），这时：
- 队列以 turn-final-failure 原因暂停（这是 turn-system 的既有规则：有待处理项时，最终失败会暂停队列）；
- Goal 仍为 active，continuation 留在队列里，没有 Goal Turn，也没有等待原因；
- Desktop 上 active 的 Goal 按 §11 不显示继续按钮。会话里能看到那一轮的失败；用户再发一条消息时，会经“发送到已暂停队列”的既有路径解除暂停，之后 Goal 继续。TUI 的 `/goal resume`、`/retry` 和 HTTP PATCH active 都会经新实现解除暂停。

spec §6：“不允许出现：Goal 为 active，没有 Goal Turn，没有等待原因，也不会自动开始”，这句写在“恢复必须落地”一节。§11 规定 active 时不显示继续按钮。§10 规定补充消息默认排队。

可选做法：
1. 不改。把它当作普通对话失败的既有行为：用户看得到失败，再发消息或用 TUI 恢复即可继续。作为已知行为写进决定清单。
2. 普通 Turn 最终失败、而队列里只剩 Goal 的 continuation（或者 Goal 的 continuation 在队列中）时，不暂停队列，或者在失败之后自动解除暂停，让 Goal 继续。
3. 失败暂停期间给 Goal 一个可见的等待原因（新文案），或者让继续按钮可用（违背 §11 的 active 规则）。

请给出选择和理由。如果某个做法放宽了 spec 的验收或违背了 spec 的意图，请明确指出。
