# Goal v2 迁移、请求计量与反馈修复：核心决策与约束

本文记录本次改造的核心决策与约束，作为方案设计、开发实现和代码审查的共同依据，也用于人工决策核对与对外说明。

具体实现可以调整，但必须满足这些约定；需要改变约定时，应先明确影响并重新确认。本文描述的是目标要求，不代表实现已完成或验证已通过。

**目的：** Goal 的状态、计量和执行由 local-runtime-v2 唯一持有。用户看到的用量随实际发出的模型请求实时增长，预算用尽时在当前轮内收尾。恢复一个停下的 Goal 后，它要么真的开始执行，要么显示在等待，要么显示失败；Goal 运行中发出的普通消息只补充方向，不再替换目标；继续按钮和通知与 Goal 的真实状态一致。

**范围与来源：** 飞书《Goal 需求澄清与验收文档｜12 项｜2026-09-30》（revision 30）的第 1、3–12 项；第 2 项另行交付，衔接见 §2。第 6、11、12 项的核心约束来自 Goal v2 spec（`matrix/agent-archon` commit `5da626fd765767192edf1625f20f0a12e50ffb9f` 的 `.harness/docs/specs/goal/spec.md`，sha256 `b7bc6cfeee95b2754148e73beca6facfcb2fdf0a3ebf51da070e8711d1c5c7ca`，下称“v2 spec”），本文采用其 4 个核心决定与 10 条约束并在 §3–§5 展开。第 5 项的交互依据产品 PRD《goal模式下支持用户steer》。术语按仓库根目录 [CONTEXT.md](../../../../CONTEXT.md) 的“Goal 执行、恢复与计量”一节使用；现有 Goal 行为见 [Goal 当前行为规格](../../goal/spec.md)（下称 GOAL-xx）。

## 本次最核心的决定

1. **Goal 业务完整迁入 local-runtime-v2，删除 v1 专属实现；迁移本身不改变行为。** 状态、持久化、准入、预算、续跑、验证、问卷中的 Goal 策略和全部入口由唯一的 v2 Goal owner 持有，不保留 v1 owner、fallback 或双写；问卷、权限、附件、任务等共享能力继续复用。
2. **计量和次数预算从 Turn 改为 Goal 请求，预算用尽在当前 Goal Turn 内收尾。** 用量在 Turn 内逐请求持久记录并实时可见；旧上限和已用数原数延续；次数上限只拦下一次工作请求，最后一次请求的结果照常处理；收尾复用 `graceSteps`，取消独立的总结 Turn。
3. **恢复必须落地。** 任何一次恢复（用户操作或到点的自动额度恢复）的结果只能是：开始一个 Goal Turn；显示现有等待文案、条件满足后自动开始；显示失败。不允许停在 `active`、没有 Goal Turn、也没有等待原因。
4. **Goal 进行中的普通发送是补充消息，不再替换目标。** 输入框不再默认锁定目标模式，移除目标标签不暂停 Goal；替换目标只能再次输入 `/goal`、发送并确认。
5. **按钮和通知表达 Goal 的真实状态。** 有未完成 Goal 时，输入框的继续按钮由 Goal 状态决定，点击即恢复 Goal；Goal 的执行轮不再逐轮通知，只在完成和需要用户处理时各通知一次。

## 完整决策与约束

- Goal 状态、单个 Turn 的状态、后台任务状态和输入模式是不同概念：`active` 不代表已有 Goal Turn 在执行，Turn 结束不代表 Goal 完成。

### 3. Goal 完整迁入 v2（第 11 项）

#### 3.1 归属、删除与复用

- 状态、持久化、CRUD、准入、预算、自动续跑、验证、问卷中的 Goal 策略，以及工具、HTTP、CLI/TUI、Desktop、队列、执行与结算的全部入口，由同一个 v2 Goal owner 持有。
- v1 Goal owner、fallback，以及散落在问卷、Host、compat 中或藏在共享接口后的 Goal 专属业务随迁移删除。不保留静默 fallback，不只接测试消费者。
- 通用执行、队列、调度、数据库、权限、附件、任务和问卷实现继续复用，共享实现可以暂留 v1。不整体迁移无关模块，不删除整个 local-runtime 包，不新增第二套调度框架。
- 接口契约、生成代码与 schema migration 沿用仓库规范：[desktop-service-idl-first](../../../skills/desktop-service-idl-first/SKILL.md)、[local-runtime-v2 规则](../../../../packages/local-runtime-v2/AGENTS.md)。

#### 3.2 迁移不改变行为

- 完成、验证、续跑和 breaker 保留既有 Turn 边界；不借迁移重定义验证超时、重试和失败分类。普通问卷、Plan、权限、附件及任务行为保持。
- 迁移保持的行为基线是：当前 `preview_train` 的 Goal 行为，加上 !7181 的额度恢复（迁移前并入，§7），加上第 2 项的 runtime 行为（§2）。
- 迁移完成、行为改动开始之前，Goal 功能地图（`.harness/docs/goal/feature-map/`）已实跑的场景在各自入口上的结果与迁移前一致；第 2 项 spec 改变的结果以该 spec 为准。

#### 3.3 数据与执行连续性

- 保留已有 Goal 的状态、历史用量、问卷答案、期限与执行归属。删除旧实现不等于删除历史数据或升级路径；迁移失败按仓库事务规则回退，不丢原数据。
- 只保留一份权威状态，不双写、不双调度。升级前处于 `active`、`paused`、`blocked`、`budget_limited`、`usage_limited`、`complete` 的 Goal 按状态和已有接纳事实接管，不因新账本为空而丢弃合法的在途工作。
- 重复启动、恢复或唤醒只产生一个有效续跑；旧 epoch 的队列项不启动、不阻塞新队列。
- 旧的预算总结队列项退役：不执行、不复活总结、不堵队列。
- Goal 或 Session 删除时清理其关联工作。暂停、删除、替换或完成之后到达的迟到任务、verdict、回执不复活旧执行，不污染新目标。

#### 3.4 问卷中的 Goal 策略

- Goal 问卷策略归 v2 Goal owner，共享问卷能力保留。
- Goal 问卷的创建、替换和自动回答涉及的跨表写入保持原子；人工回答与自动回答并发时只接受一份答案。
- 自动回答要求 Goal 为 `active`；人工回答沿用原规则，不套用 `active` 限制。
- 保存答案不等于可以续跑。答案已保存、但注入未完成时，只补注入，不重新作答，不重复开启 Turn。
- 等待回答和本地自动选项不计 Goal 请求。

#### 3.5 装配与生命周期

- 所有入口接入同一个 owner。启动时先让恢复所需的事实就绪，处理旧总结项、问卷恢复和活跃 Goal 接管之后，再唤醒队列。
- 关闭时停止新准入，有界处理在途工作；正常关闭之后不再有新准入。

#### 3.6 诊断

- 诊断保持经用户同意、按需只读、有数量与时间上限、脱敏。增加请求与回执的已知、未知、已应用状态和丢弃原因摘要。
- 不导出 objective、完整 transcript、prompt 或原始回执，不新增常驻写文件的服务。
- 按请求与回执的活动时间选取近期证据；诊断读取不推进 epoch，不改变业务状态。

### 4. 请求级计量、预算与展示（第 6 项）

#### 4.1 什么算一次 Goal 请求

Goal Turn 继续承载完成、验证、续跑和 breaker 的边界。一次 Goal 请求是 Goal 主执行实际发出的一次逻辑 LLM 请求，一个 Goal Turn 可以有多次。

| 情况 | 计量 |
| --- | --- |
| 同一逻辑请求内部的 transport 重试 | 不增加请求数；每次 attempt 已知的 usage 如实累计 |
| after-hook 引发新的真实模型调用 | 另计一次逻辑请求，并单独准入 |
| 请求发出后失败或被取消 | 计一次 |
| 请求发送前被拦截 | 不计 |
| 工具执行、本地自动选项、等待、未发出的合成回复 | 不计 |
| 崩溃时请求已进入发送边界，无法确认是否送达 | 保留一次未知占用，标记为未知，不冒充已确认发送 |
| 可靠证明请求没有发出 | 释放预占，不计 |

- 普通用户 Turn 不因同一 Session 有 Goal 就计入 Goal；Goal 问卷续跑按实际执行归属计量。
- 验证不占主执行的请求数。subagent verifier 的 token 计入 Goal；evaluator 只上报，不计入。
- 普通子代理或 compaction 的归属，现有 owner 无法确定时，先补执行身份，不按 Session 粗算。

#### 4.2 次数预算

- 工作占用 = 历史占用 + 未作废的工作请求（含未知占用）。在下一次工作请求准入前检查次数上限。
- 配置键 `defaultMainTurns` 保留，单位改为工作请求，缺省仍然没有次数上限；配置文档同步说明单位变化。不新增单个 Goal 的请求上限的可写 UI 或 API。
- token、活跃时间上限的规则不变（GOAL-07）。

#### 4.3 旧额度原数延续

> 旧上限 10 Turn、已用 6 → 新上限 10 次工作请求、历史占用 6、剩余 4 次。

- 不重新发放额度；历史占用不伪造成已发出的请求。
- 暂停、恢复、编辑同一个 Goal 不清零；新的 goalId 从零开始。

#### 4.4 持续记录

- 请求账本在必经的执行路径上持久化，不依赖可能丢失的观测通知。每次请求的已知用量确认后即持久并投影：长的 Goal Turn 运行过程中，token 与请求数随之增长，不再等 Turn 结束才出现。
- 预算判断与展示使用同一份持久累计值。重连时重新读取权威状态，不靠累加事件重建账本。

#### 4.5 幂等、迟到与不完整用量

- 请求与 attempt 的回执、以及已应用水位防止重复入账：重复通知、乱序回执、结算重试、重启、重连和 Turn 结束都不重复累计、不回退。同一请求标识携带不同输入时按冲突处理。
- 用量更新不推进决定 epoch，不使当前执行绑定失效。
- 迟到的 usage 归不可变的原 goalId，不能改变当前 Goal 的状态。原 Goal 已删除时不写入、不转计到任何新 Goal，丢弃并记录有限的诊断原因。
- 缺少 usage 时标记为不完整，不当成零；真实消耗不截断到上限。已持久的 token 与尚未入账的增量只计一次。
- 发送情况未知的请求：保留一次占用；不估算 token、不自动退款、不重发原请求，不新增自动对账或扣步策略开关。已持久化的回执只幂等补应用。
- token 与请求账本不是账户的实际货币账单，不据此解释计费对错。

#### 4.6 跨端表达

- 本地 Desktop、TUI、CLI、API、事件与 `get_goal` 投影同一份持久状态。`accountingVersion=2` 标明新口径；请求数、工作请求与收尾请求、历史占用、预占与未知占用、`usageIncomplete` 分开表达。
- 旧的 `turnsUsed` wire 字段不删除：本地 Goal 上它承载冻结的历史值。云端 Goal 仍按原 Turn 口径，不能被标成请求；客户端不得用 `requestsUsed ?? turnsUsed` 一类的回退把两种口径合成“请求”。
- 新增字段对旧客户端可选，旧客户端忽略它们仍能读取 Goal。
- 真实 wire 字段经 IDL 生成链路进入各消费面（§16），不以 UI 本地扩展类型代替。

#### 4.7 Desktop 与 TUI 的展示

- 只显示已用量，不显示上限，与 token 的显示一致。
- Desktop 横幅原来的“N 轮”改为“N 次请求”。N 为本目标实际计入的请求：工作请求、收尾请求与未知占用之和，不含历史占用。
- 鼠标悬停在请求数上时说明构成，格式如“本目标请求 4（工作 3、收尾 1）· 升级前 6 轮 · 1 次发送状态未确认”；没有的部分不列。历史占用只在这里出现。
- 有请求缺少用量数据时，token 数后加“+”，悬停说明“部分请求缺少用量数据”。
- TUI 横幅、`/goal` 摘要和完成行里原来的 `N turns` 改为 `N requests`，N 的口径与 Desktop 相同；`/goal` 摘要另列出构成（工作、收尾、未知占用、升级前的轮数）。
- 云端 Goal 的展示保持现状。

### 5. 预算耗尽在当前 Goal Turn 内收尾（第 12 项）

#### 5.1 最后一次工作请求

- 次数上限拦截的是下一次工作请求，不截断最后一次合法请求返回的工具调用、结果与完成提案。
- token、活跃时间、权限、用户停止、绑定有效性和验证自身的限制仍然独立生效，不因此放宽。
- 最后一次工作请求带有合法的完成提案、且其他限制允许时，按既有策略验证：`met` 则 `complete`；明确 `not_met` 且次数已尽，保留结果并进入 `budget_limited`。验证超时、取消或失败保持原分类，不改判为预算耗尽。没有完成提案时不凭空验证。

#### 5.2 收尾请求

- 收尾复用 `graceSteps`（默认 1，范围 0–3），与工作请求分开限额。
- 收尾请求只根据已有结果生成纯文本总结：所有工具都禁用，包括 `get_goal`、`update_goal`；不继续普通工作，不提出新的完成提案。收尾请求中出现的工具意图不执行、不产生状态提案，也不无界地纠正重试。
- 收尾请求照常计入请求数与 token，所以总请求数可以超过工作请求上限。
- `graceSteps` 为 0 时不额外请求；已有有效的最终回复时不再总结；同一 Goal Turn 的恢复（重连、崩溃恢复、runner 重启）不重置已用或未知的收尾名额。

#### 5.3 不另起总结 Turn

- 取消独立的预算总结 Turn，取代 GOAL-07 的“达到预算后另排一个总结 Turn”和第 2 项 spec §3 的对应行。
- 当前 Goal Turn 已停止、失败、关闭，或根本没有获准时，不为总结重新启动，只保留已有结果与真实状态。
- “本轮已关闭普通工作”在同一产品 Turn 的 runner 重试、idle continuation 与安全重生成中持续生效，不被重置。
- 真正的 provider 失败或持久化失败不伪装成正常的预算结束。

#### 5.4 完成提案之后的最终回复与次数上限

- 第 2 项规定的“完成提案被接纳后在同一轮写最终回复”那次请求，以及只对已接纳 `complete` 生效的空回复重试，都是工作请求，未到上限时照常发出。
- 次数上限已经用尽时，最终回复改由一次收尾请求来写：它不带工具（与第 2 项“complete 之后拦下所有工具调用”一致），使用第 2 项最终回复的写作要求，不用通用的预算总结要求。
- `graceSteps` 为 0 时没有最终回复，按第 2 项“没有回复时的兜底”正常结算，完成提案照常进入验证，不因此判为失败。

#### 5.5 与用户输入的关系

- 关闭前后到达的用户 steer，不能因先被消费或确认、后被预算拦截而丢失。尚未执行的部分按既有身份和先后顺序交回普通输入路径，不重复正文，不再次执行已处理的输入。

### 6. 恢复落地（第 1、3、10 项共用）

- 适用于所有把停下的 Goal 带回执行的路径：Desktop 横幅的继续、输入框的继续按钮（§11）、TUI `/goal resume`、Goal 暂停时的 `/retry`（§13）、到点的自动额度恢复（§7）、依赖任务结束后的唤醒（§8）、编辑暂停中的 Goal 后保存、提高或清除 token 预算后重新打开 `budget_limited(token)` 的 Goal。
- 每次恢复的结果必须是以下三者之一：
  1. 开始一个绑定该 Goal 的 Goal Turn，用户能在入口上看到新的执行和输出；
  2. Goal 为 `active` 并记录等待原因，Desktop 与 TUI 横幅显示现有的等待文案，条件满足后自动开始 Goal Turn；
  3. 恢复失败，入口上显示失败，Goal 状态如实反映失败。
- 不允许出现：Goal 为 `active`，没有 Goal Turn，没有等待原因，也不会自动开始。
- 恢复沿用原 Goal 与 Session，不要求删除重建。重复点击，或自动计时与手动恢复同时触发，只开始一次；恢复与暂停、编辑、删除并发时不恢复旧 Goal。

### 7. 账户额度恢复后原 Goal 真实恢复（第 1 项）

- 以 !7181 的实现为基础，在迁移前 cherry-pick 它的提交：从 provider 的原始错误读取可信的额度重置时间，与停止写在同一次受保护的写入里；到点经原有续跑通道自动恢复原 Goal；应用重启或设备离线跨过恢复点后，启动时补偿。
- 自动恢复只针对停止时记录的 Goal 版本：等待期间 Goal 被暂停、编辑、替换、删除或完成，到点不恢复旧目标。自动恢复只开始一次，与手动恢复同时触发时不双启。恢复遵守 §6。
- 自动恢复已排定时，Desktop 横幅显示“额度恢复后自动继续”，TUI 横幅显示 `Goal will continue automatically after the quota resets.`，都不显示时间。
- 到点之前用户也可以手动恢复，恢复会真实尝试：按 §6 开始一个 Goal Turn。额度已经恢复（例如开启积分自动消耗、升级套餐）时照常执行；仍然受限时本次失败，Goal 回到 `usage_limited`，入口上显示失败，自动恢复的安排保留（新的错误带有可信重置时间时按新时间），提示仍为“额度恢复后自动继续”。
- 没有可信重置时间时不自动恢复：沿用现有提示“服务商额度恢复后可继续”，允许手动恢复；额度仍不足时照常失败、回到 `usage_limited`，入口上显示失败。
- 普通限流（HTTP 429、50111，以及 TPM 限流 50150）、未知的 BYOK 错误、50113 与上游 500 不适用定时恢复。Goal 自身预算耗尽（`budget_limited`）与账户额度（`usage_limited`）分开处理，提示不串用。
- 应用关闭时停止恢复调度。

### 8. Goal 只等待自己的依赖（第 3 项）

- Goal 依赖任务是由本 Goal 的 Goal Turn 启动的 `subagent` 或 `workflow` 类后台任务。Goal 的准入、续跑和完成结算只等待这些任务。
- 普通对话启动的任何后台任务，以及 Goal 自己启动的后台 shell 进程（例如 dev server），都不阻塞 Goal 的准入、续跑和完成结算。
- 依赖任务成功、失败或取消后重新评估并继续；后续 Goal Turn 看到任务的真实结果，失败不当成功。重复的终态事件不重复启动。
- 等待依赖时横幅显示现有文案“等待后台任务完成”（TUI 为 `Waiting for background tasks`），并且只在存在真实的 Goal 依赖任务时显示。
- Goal 等待期间，普通消息照常进入会话并执行；普通对话能执行不代表 Goal 已恢复。
- 停止 Goal 不删除对话历史，也不停止用户的常驻服务。
- 不能通过结束用户的常驻服务，或取消全部依赖检查来解决。

### 9. 更新冲突时刷新并保留输入（第 4 项）

- 本节适用于 Desktop 以及与 Desktop 共用操作层的手机端；TUI 的 Goal 命令不变。
- 修改目标、修改预算和恢复都带版本；暂停和清除不带版本，总是生效。乐观并发保护保留，不用旧快照覆盖新状态。
- 修改目标或预算遇到版本冲突时：重新读取最新 Goal 并刷新界面；保留用户的输入，输入框此时已有新内容则不覆盖；提示“目标已在后台更新，已刷新为最新状态，你的修改已保留，可重新提交”；用户可以直接再次提交保留的内容。不显示 “epoch changed” 一类的内部错误文本。
- 恢复遇到版本冲突时同样重新读取并刷新，提示“目标已在后台更新，已刷新为最新状态”。
- 不自动重试。等待用户重新提交期间，用户继续修改、切换或删除目标，旧请求的结果不污染当前输入。
- 超时、普通服务错误与版本冲突分别提示；重复点击不造成多次变更或重复启动。版本冲突不把仍在运行的 Goal 报成整个任务失败。

### 10. 补充消息、steer 与替换目标（第 5 项）

- 每个会话仍只有一个当前目标。
- Goal 创建并发出后，输入框回到普通模式；Goal 为 `active` 时不再强制锁定目标模式。
- 普通发送是补充消息：不修改 objective，消息在会话里可见并送达当前任务。送达时机沿用用户的发送偏好：默认排队，在下一个边界处理；“立即发送”时注入当前 Goal Turn。“立即发送”的快捷键沿用现有设置：发送键为回车（默认）时是 ⌘⏎，发送键改为 ⌘⏎ 后是 ⇧⌘⏎。
- Goal 不在 `active`（`paused`、`blocked`、`usage_limited`、`budget_limited`）时发送的补充消息按普通对话执行，不恢复 Goal，不修改其状态；横幅保持原来的状态标签和操作。
- 校验进行中发送补充消息：在途的校验作废，Goal 继续执行后重新提交完成（沿用运行时现状）。
- 移除输入框的目标标签只影响这一次输入，不暂停、不清除 Goal；暂停只通过显式的暂停操作。
- 替换目标：用户再次输入 `/goal`，输入框进入“目标”状态；发送时弹出确认框，标题“替换当前目标吗？”，说明“这会保留聊天，但会用你当前在输入框中的文本替换已保存的目标”；确认后替换，取消则不替换；替换发出后输入框回到普通模式。横幅的编辑按钮保留，经同一确认。Goal 已暂停时，确认替换即恢复（沿用现状）。
- 替换后，界面与之后的完成校验使用新目标，保留“目标已更新”记录，不产生第二个并行 Goal。Goal 已完成时，`/goal <目标>` 创建新 Goal（沿用现状）。
- 快速连续输入、附件、切换会话，以及与 §9 的版本冲突交错时，草稿、消息顺序和目标归属保持正确，不静默丢消息。
- TUI 不改：它没有常驻目标模式，普通消息本来就是补充消息，`/goal <文本>` 仍是显式修改目标。
- 手机端（Remote Control）与 Desktop 共用这一套输入意图规则。

### 11. 输入框的继续按钮（第 8 项）

| 会话中的 Goal | 输入框的三角继续按钮 |
| --- | --- |
| `active`（运行中、等待中、校验中） | 不显示；横幅显示当前状态或等待文案 |
| `paused`、`usage_limited`、`blocked` | 显示；点击即恢复该 Goal，按 §6 显示真实结果，不能只先变为 `active` 再无声失败 |
| `budget_limited` | 不显示；横幅保持“已达上限”及现有提示 |
| `complete`，或没有 Goal | 沿用现有的 Turn 续跑判定（含 !7178 的完成后规则） |

- 按钮随 Goal 事件刷新，不只在生成结束时刷新。历史重载、断线重连、乱序事件、切换会话和连续暂停、恢复时，按钮不被旧事件回滚。
- Goal 完成后释放该 Goal 的目标输入意图，仍可正常创建新 Goal；没有未完成 Goal 的会话，普通中断任务的继续功能不变。

### 12. 通知（第 9 项）

- Goal Turn 结束时不发通知。非 Goal 的 Turn（包括 Goal 会话里补充消息的那一轮）的通知保持不变。
- Goal 的通知沿用现有系统通知的格式：标题为会话标题（云端会话照旧加前缀），点开进入该会话。
- Goal 进入 `complete` 时通知一次，正文“目标已完成”。
- Goal 需要用户处理时通知一次，正文“目标需要你处理”。适用于：Goal Turn 中出现待答的问卷或权限请求；Goal 进入除用户主动暂停以外的 `paused`，以及 `blocked`、`usage_limited`、`budget_limited`。用户主动暂停不通知。通知不写原因。
- 同一 Goal 的同一状态只通知一次；持续受限、反复重试不重复打扰。断线积压、重连和应用重启后，同一终态不重复通知，已经过时的执行轮不集中补发。
- Remote Control 的断线缓冲：每个会话只保留最新一条待发的通知事件，丢弃 Goal Turn 的结束事件。在线时的事件转发不变；手机端如何弹出通知不在本仓库。
- 复用现有的通知开关、前台抑制与去重能力。阶段性交付不通知，不新增通知设置。不为减少通知而隐藏交付物或改变完成判定。

### 13. TUI 恢复与输出一致（第 10 项）

- `/goal resume` 按 §6 报告真实结果：开始了 Goal Turn 时打印 `Goal resumed.` 并在终端显示该轮后续的输出；在等待时打印现有等待文案；失败时打印错误。不再无条件打印 `Goal resumed.`。
- Goal 为 `paused` 或 `usage_limited` 时，`/retry` 等同 `/goal resume`，不再开始不绑定 Goal 的普通续跑。
- 恢复沿用原 Goal 与 Session，并核对当前有效的 Turn。终端重开、连接恢复、快速多次 resume，以及暂停、编辑、删除与迟到输出交错时，保持 Session 与 Turn 的归属和去重，旧任务的输出不串入新目标。
- 恢复后上游仍然失败：显示本次失败，Goal 回到相应状态，不产生重复轮或无限重试。保留可重试错误的分类，未知错误不启用无限自动恢复。

### 14. 校验中断后的恢复（第 7 项）

- 父 Goal 的恢复是恢复自主执行的唯一入口。
- 校验因异常中断而暂停的 Goal，恢复后开始一个工作 Goal Turn，并告诉模型上次校验因何中断、要求重新检查后再次提交完成；不直接重跑校验，不并行产生多个校验。
- Desktop 的 verifier 子会话里不再提供通用的“重试”，改为说明“校验由父目标管理”，并提供打开父目标会话的入口。
- 禁止在 verifier 子会话里创建或恢复普通 Goal 的保护继续有效。
- 父 Goal 被暂停、删除、完成或 objective 已更新后，迟到或重复的校验结果不会重新激活旧目标。校验的成功、未达标、异常、取消各自沿用现有的状态结果；重连与重复点击不造成双校验或结果串用。

### 16. 硬约束

### 17. 已接受的代价

- 次数上限数值不变、单位从 Turn 变为请求后，同一数值允许的工作量可能减少。
- 发送边界附近崩溃时，极少数实际没有发出的请求也可能占用一次；缺失的 token 用量保持未知，不估算补账。
- 部分预算停止没有新生成的模型总结。
- 收尾请求计入请求数，总请求数可以超过工作请求上限。
- Goal 自己启动的后台 shell 进程不再阻塞 Goal，由模型自行查看其状态。
- 校验进行中发送的补充消息会让这次校验作废，Goal 需要重新提交完成。
- 额度仍未恢复时的手动恢复会失败一次，这次失败的请求计入请求数。

### 18. 验证能力与功能地图（随本 MR 交付）

#### 18.1 测试账号额度

- verify-archon 提供查询、设置和恢复**当前登录测试账号**额度的命令，封装 Payment 测试台接口（`http://coverage.xaminim.com`，`/api/payment/token-plan/state`、`usage`、`weekly-usage`、`credits`），可以设置 5h 与 Weekly 使用率。
- 固定使用 `mode: "redis_simulation"`，命令不提供 `real`；只作用于 verify-archon 当前登录的账号，不接受任意账号。
- 设置前先查询；账号不在平台的测试环境中时报错退出，不做任何修改。
- 提供恢复：5h 使用率回到 20%。
- Skill 文档写明：Weekly 使用率保持在低位，否则界面优先显示周限额；构造耗尽前关闭 Credits 自动消耗（Desktop“设置 → 用量”），用完恢复；模拟只改窗口用量、不写扣费流水，要用一次真实请求确认命中了后端限额；上游 2056、2067 映射为 42212，普通限流为 50111。SKILL.md 的“边界”写明改动测试账号用量的这些规则。

#### 18.2 其他验证能力

verify 列出的其余验证工具缺口作为 verify-archon 的命令或启动选项加入并写进文档：故障注入 provider（按规则返回指定错误、去掉 usage、暂扣或挂起响应、记录请求与 attempt）、从已有数据目录启动、保留数据重启与强制结束、Electron 悬停读取、Electron 系统通知捕获、Electron 请求屏障（记录并暂扣指定请求）、Electron 配置注入并回读。
