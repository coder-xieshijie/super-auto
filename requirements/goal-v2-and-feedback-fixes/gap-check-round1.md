**1. Payment 测试台授权缺少原始决定依据**

类型：偏离原始约定  
位置：spec「交付与授权／测试账号额度」；verify S35、S36、G6、R99。  
问题：spec 新增了修改真实登录账号额度的授权，但给定原始约定没有对应授权，且明确采用另一种验证安排。  
依据：`original-decisions.md` 第二轮 Q13：“额度耗尽、429、50113 用故障注入的 provider 构造……真实 5h 额度不作要求，列为覆盖盲区”；spec 则写“可以用 Payment 测试台接口……修改……5h、Weekly 使用率”。  
影响：自动交付 agent 会依据未经原始决定支持的条款修改账号状态，并把新增场景作为交付要求。  
建议：按原决定保留故障注入与真实额度盲区，移除这段授权及强制场景；如确有后续授权，补入对应用户原话。否则需用户决定：维持原方案，还是授权指定账号的 Payment 模拟及恢复策略。

**2. 覆盖盲区的替代测试没有明确的通过门槛**

类型：判别力不足  
位置：verify「覆盖盲区」「完成条件」，尤其 B01–B10、B12–B14。  
问题：完成条件只要求附替代测试结果，没有明确要求这些测试通过。  
依据：“除覆盖盲区里的检查点外，全部场景……通过”；盲区只要求“标为 UNVERIFIED 并单列，附上替代判断的测试名称与结果”。  
影响：崩溃恢复、幂等记账、问卷原子性等替代测试即使失败，仍可能被解释为已满足文档的完成条件。  
建议：明确“所有指定替代测试必须通过；失败或未执行阻塞交付”。同时区分“真实入口未验证”和“替代测试已通过”，不要用同一个 UNVERIFIED 混合表达。

**3. S34 要求改变现有预算恢复契约**

类型：越出 spec  
位置：verify S34；spec §4.2、§6。  
问题：S34 要求两次独立命令“提高预算，再 resume”成功，但 spec 没有批准改变现有的同次更新要求。  
依据：S34 执行 `/goal budget=200K` 后再 `/goal resume`；spec 规定“token、活跃时间上限的规则不变（GOAL-07）”。现有 GOAL-07、功能地图及 `store-patch.ts` 均要求同一次 PATCH 携带预算变更与 `status: active`。  
影响：保持现有契约的正确实现会失败；为通过场景而放宽恢复契约的实现反而通过。  
建议：改用现有的同次 PATCH 重开路径验证 §6，并覆盖提高、清除预算两种情况。如果要新增 TUI 两步重开能力，应先作为新的产品决定写入 spec。

**4. TUI 场景把“启动后失败”误当成“从未恢复成功”**

类型：越出 spec  
位置：verify S18、S30、S36；spec §13。  
问题：场景一方面要求已启动新 Goal Turn，另一方面禁止出现启动成功提示。  
依据：spec：“开始了 Goal Turn 时打印 `Goal resumed.`”；S30 同时要求“这次恢复只产生一个新的 goal.turn_bound”和“没有打印 `Goal resumed.`”，S18、S36 同样如此。  
影响：实现真实启动后先打印 `Goal resumed.`，随后如实显示 provider 错误，会被误判失败；也可能迫使实现等待模型结果才报告启动。  
建议：分开验收准入失败、等待、启动后三种路径。已绑定并启动时允许启动提示，随后必须显示同轮失败及最终状态；没有启动时才禁止成功提示。

**5. S02 把迁移保留与恢复执行后的正常变化混为一谈**

类型：判别力不足  
位置：verify S02。  
问题：启动后允许 active Goal 自动执行，却要求其状态和累计用量仍与升级前完全相同。  
依据：检查点要求六个 Goal 的“status、……tokens_used、time_used_seconds……与升级前记录相同”，又要求 active 会话“继续执行到终态”；“不得出现”还包括“任一 Goal……状态改变”。  
影响：正确接管后立即产生请求、累计时间或完成目标的实现，会因正常变化而失败。  
建议：拆成迁移快照核对与恢复执行核对：在队列放行前验证数据保留；放行后按旧值加新增执行事实核对，允许合法状态迁移。所需启动屏障列入 G2。

**6. S03 没有保证调用 `get_goal`，且比较了不同时间的计数**

类型：判别力不足  
位置：verify S03 步骤 5及最终检查点。  
问题：场景没有构造 `get_goal` 调用，却要求读取其结果并与终态接口计数相同。  
依据：目标只要求创建五个文件；检查点要求“`get_goal` 的结果含请求数且与接口相同”。spec §4.6 要求的是各入口投影同一持久状态，并非历史工具结果随之后的请求更新。  
影响：模型不调用该工具时无法验收；即使调用，之后的模型请求仍会增加计数，正确的历史结果也可能被判错。  
建议：显式安排调用，并在相同账本水位比较工具、API、事件和界面读数；终态计数另按实际请求核对，不拿旧工具结果与终态值直接比较。

**7. S07 没有制造迟到 usage，却强制要求存在丢弃记录**

类型：判别力不足  
位置：verify S07、依赖它的 S32。  
问题：前台 shell 等待不保证删除 Goal 后还会到达模型 usage。  
依据：S07 在请求数达到 1 后清除 Goal，但强制要求“诊断摘要中有旧 goalId 的迟到用量被丢弃的记录”。spec §4.4 又要求已知用量及时持久化。  
影响：如果 usage 已在 shell 执行前入账，正确实现没有迟到回执可丢弃，S07 和 S32 都会失败。  
建议：用可控 provider 或回执屏障延迟一笔已知 usage，删除并新建 Goal 后再释放；验证丢弃原因与新 Goal 用量。普通 shell 场景只验证旧执行不续跑。

**8. S23 没有保证发生版本冲突**

类型：判别力不足  
位置：verify S23；S22 也需明确旧版本捕获点。  
问题：先由另一客户端更新、再点击 Desktop 按钮，不保证按钮发送旧版本。  
依据：S23 步骤 2 修改预算，步骤 3 才点击恢复，却要求必然显示冲突提示。仓库已有 `thread_goal.updated` 事件投影，Desktop 可以在点击前收到新版本。  
影响：及时刷新并成功恢复的正确实现会失败；暂停错误携带最新版本也可能通过步骤 4，无法证明暂停不带版本。  
建议：在 UI 请求捕获旧版本后阻塞该请求，另一路推进版本，再放行，断言真实冲突响应；暂停、清除则直接核对请求不携带版本。把请求屏障列为工具缺口或明确的 UI 测试能力。

**9. S09、S10 的固定请求序列不能由目标文本保证**

类型：判别力不足  
位置：verify S09、S10。  
问题：要求分别调用写文件工具，并不等于模型必须分三次请求调用，也不保证第三次请求恰好返回写文件调用。  
依据：目标要求“Write each file with a separate tool call”；检查点却固定“主执行请求共 4 次”“第 3 次请求返回的写文件工具调用已执行”。spec 明确工具调用与模型请求不是同一计量单位。  
影响：模型在一个响应中返回多个独立工具调用，是合法执行，却可能提前完成或走不同序列，导致正确实现失败。  
建议：把“第三次工作请求仍返回合法工具、随后还需继续工作”做成可核对的场景前提。精确序列用脚本 provider 固定；真实模型场景未命中前提应标为未覆盖，不能按产品失败处理或视为已证明该边界。

**10. 请求计量的数值正确性仍有关键漏测**

类型：缺少覆盖  
位置：spec §4.1–§4.7；verify R23、R28、R34、R35、R39、R41。  
问题：现有场景主要检查请求条数和非零 token，未覆盖以下明确要求的数值归属与投影。  
依据：

- spec：“subagent verifier 的 token 计入 Goal；evaluator 只上报，不计入”；S03 只检查 verifier 不增加请求数，通用前提还排除了 evaluator。
- R34 包含“真实消耗不截断到上限”，但唯一证明 S06 只检查缺 usage 标记。
- R28 包含“编辑同一个 Goal 不清零”，S04、S07 分别测试暂停恢复、删除新建，没有检查编辑后的累计值。
- R35、R39、R41 包含预占、未知占用及其跨端构成，S01/S03/S04/S10 没有构造非零未知占用；B01 也只判断 runtime 恢复。

影响：漏记 verifier token、错误计入 evaluator token、把超额用量截断、编辑时清零，或两端漏显未知占用，都可能通过。  
建议：补固定用量的归属矩阵和超额断言；增加编辑前后累计值核对；用非零历史、工作、收尾、预占、未知占用的固定样本验证各端投影。预期值由场景给出。

**11. 恢复与输入意图的状态矩阵没有实际覆盖完整**

类型：缺少覆盖  
位置：verify R52、R53、R70、R77、R83、R84、R92–R94。  
问题：要求表列出了多个状态和入口，但所引用场景只测试其中一部分。  
依据：

- R77 覆盖所有非 active 状态，S25 只测试 `paused`。
- R83 覆盖运行、等待、校验，S28 只在运行中检查继续按钮。
- R84 包含 `blocked`，S28/S17 只测试 `paused`、`usage_limited`。
- R92 要求等待时打印现有等待文案，S30 只有启动后失败与成功完成。
- R70 包含预算修改冲突，S22 只修改 objective，B09 未补预算冲突。
- spec §13 要求终端重开、连接恢复后的输出归属；S30、B08 没有构造终端断流与重新挂接。

影响：按状态或入口硬编码的局部修复可以通过，而遗漏用户已确认的路径。  
建议：逐项补参数化场景或明确替代测试，至少断言状态、按钮、输出归属和操作副作用；工具不能构造的路径应新增具体缺口，不能只保留要求表中的覆盖声明。

**12. 诊断的限制条件没有得到证明**

类型：缺少覆盖  
位置：spec §3.6；verify R17、S32。  
问题：S32 只检查部分输出内容和 `updated_at`，不足以验证完整诊断约束。  
依据：spec 要求“有数量与时间上限”“不导出……原始回执”“不新增常驻写文件的服务”“按请求与回执的活动时间选取近期证据”；S32 没有对应检查点，也没有覆盖盲区承接。  
影响：导出原始回执、无界导出、按 Goal 创建时间漏掉近期请求，甚至写入不推进 epoch 的业务字段，都可能通过。  
建议：补超量、跨时间窗口、近期回执属于旧 Goal 的固定样本；检查原始回执与敏感字段排除、拒绝同意时不生成、业务状态前后不变，并机械核对没有常驻写文件服务。

**13. Electron 指定预算配置的能力未列入工具缺口**

类型：不可执行  
位置：verify S10 前提、G1–G6；指定分支的 verify-archon Electron 入口。  
问题：S10 要求为 `electron up` 设置 `defaultMainTurns=3、graceSteps=1`，但现有 Electron 启动链没有接入该配置能力。  
依据：Electron 使用说明仅列 `electron up [--no-proxy] [--evidence-dir <dir>]`；启动脚本虽可传递 `VERIFY_ARCHON_CONFIG`，`electron-server.mjs` 没有读取并应用它。S10 的执行状态只登记了悬停缺口 G4。  
影响：场景可能使用默认无次数上限配置，始终无法进入预期预算终态，无法区分配置未生效与产品错误。  
建议：新增 Electron 隔离配置注入缺口，明确配置应用路径，并要求启动后回读有效预算配置；S10 在该能力补齐前标为受阻。
